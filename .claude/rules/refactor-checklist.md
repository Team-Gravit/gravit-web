# 리팩터·이전 착수 판단

**구조를 바꾸는 작업(`MIG-` · `REF-`)은 구현보다 착수 판단을 먼저 한다.**
`ai-plan`은 이 문서를 기준으로 영향·검증·되돌리기 계획을 작성한다.

## 1. 착수 전 필수 게이트

아래 질문에 답과 근거를 함께 적는다. 핵심 항목을 설명할 수 없으면 점수로 상쇄하지 않고 보류한다.

| 질문                               | 확인할 것                                                             |
| ---------------------------------- | --------------------------------------------------------------------- |
| 목표와 비목표가 명확한가           | 무엇을 바꾸고 무엇을 보존하는지 한 문장으로 말할 수 있는가            |
| 반복 비용이나 확장 차단이 있는가   | 지금 구조를 바꾸지 않으면 생기는 구체적인 비용이 있는가               |
| 기준선이 있는가                    | 사용자 경로·상태·문구·API 계약 중 보존할 대상을 기록했는가            |
| 검증 방법이 있는가                 | 자동 테스트 또는 재현 가능한 수동 검증을 실행할 수 있는가             |
| 범위를 독립적으로 완료할 수 있는가 | 단계별로 구현·검증·리뷰할 수 있고, 범위 밖 항목을 분리했는가          |
| 위험을 격리했는가                  | 인증·토큰·생성물·라우트 트리 등 경계와 실패 시 복구 방법을 식별했는가 |

답을 작성할 수 없는 항목은 `work/{ID}/spec.md`의 확인 필요 목록으로 남기고 `to-do`에 보류한다.

> 지나가다 인접 코드를 정리하는 보이스카우트 작업은 계획에 명시된 경우에만 허용한다.

## 2. 자동 보류 신호

다음 중 하나라도 해당하면 작업을 멈추고 범위를 다시 정한다.

- 동작 변경과 구조 변경이 같은 계획에 섞여 있다 → `FEAT-` 또는 `FIX-`로 분리한다
- 한 단위로 완료·검증할 수 없는 범위다 → 실행 가능한 단계로 쪼갠다
- 자동 생성물을 직접 수정해야 한다 → 재생성 명령이나 upstream 수정으로 전환한다
- 기존 검증 실패의 원인·영향 범위를 설명할 수 없다 → 기준선과 실패 원인부터 기록한다
- 작업 중 새로운 범위 밖 문제가 발견됐다 → 그 자리에서 고치지 말고 새 작업으로 분리한다

기존에 기록된 실패는 무시하지 않는다. 영향 범위와 이번 작업의 관련성을 확인하고, 새로 생긴
실패인지 기존 기준선인지 구분한다.

## 3. 보류 시 다음 행동

구조를 바꾸지 못하더라도 `refactor-baseline`으로 관찰 가능한 동작과 외부 계약을 먼저 기록할 수
있다. 기준선에는 다음을 남긴다.

- 진입 경로와 사용자 행동
- 빈 값·로딩·에러·권한 등 상태
- 화면에 보이는 문구와 결과
- 네트워크 요청 순서와 실패 처리
- 나중에 동일성을 확인할 검증 방법

기준선이 생기면 보류 원인을 다시 평가한다.

## 4. 착수 후 원칙

- 계획에 적힌 구조 변경만 한다. 개선·스타일 변경은 별도 작업으로 분리한다
- Legacy는 관찰 기준으로만 사용하고 구조·네이밍·결함을 새 코드에 복사하지 않는다
- 줄 수·파일 수·변경량을 동작 동일성의 증거로 사용하지 않는다
- 기준선의 사용자 경로·상태·문구·API 계약을 자동 테스트 또는 명시적 수동 검증으로 대조한다
- 범위를 넘는 문제는 `work/to-do/`에 새 항목으로 기록한다

## 5. 작업 중 점검

`ai-plan`에서 사전 평가하고, `ai-orchestrate`에서 매 매핑 단위마다 아래를 확인한다.

| 축     | 합격 기준                                                                        |
| ------ | -------------------------------------------------------------------------------- |
| FSD    | 레이어 방향·cross-slice·segment·배럴·생성물 격리·별칭 규칙을 지킨다              |
| 가독성 | `code-quality.md`의 네이밍·중첩·주석 기준을 지킨다                               |
| 모듈화 | 슬라이스 외부에는 public API만 노출하고, 책임이 다른 코드를 억지로 합치지 않는다 |
| 동작   | 기준선에 기록한 사용자 경로와 상태가 의도대로 보존되거나 승인된 명세로 바뀐다    |
| 성능   | 추측하지 않고 측정 결과가 있을 때만 최적화한다                                   |

### 공통화 판단

- 단발성 헬퍼는 같은 파일에 비-export로 둔다
- 반복됐다는 사실만으로 공통화하지 않는다. 개념·입력·변경 이유·수명이 같은지 확인한다
- 공통 책임이 확인되면 사용하는 모든 슬라이스를 포함하는 가장 낮은 레이어로 승격한다
- 컴포넌트 추출과 값의 상수화는 서로 다른 판단이며, 각각의 전용 규칙을 따른다

### 성능 판단

- `memo`·`useMemo`·`useCallback`은 측정 후에만 추가한다
- 상태 구독과 Query 옵션은 `state-convention.md`·`api-convention.md`를 따른다
- 동적 import는 실제로 초기 로드 비용을 줄이는 무거운 기능에만 사용한다
