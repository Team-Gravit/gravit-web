# 테스트 정책

**무엇에 테스트를 쓰고 무엇에 안 쓰는가.** 테스트를 안 쓰는 이유가 더 중요한 규칙이다.

실행: `pnpm test` (전체) / `pnpm --filter @repo/web exec vitest run -t "테스트 이름"` (단건)
도구: Vitest 3 + jsdom + React Testing Library + jest-dom + user-event

---

## 1. 대상별 판정

| 대상                                           | 테스트  | 이유                                              |
| ---------------------------------------------- | :-----: | ------------------------------------------------- |
| 순수 함수 / 커스텀 훅 (계산·변환·상태 전이)    | ✅ 우선 | 분기·경계·회귀 위험이 있으면 가장 싸게 검증 가능  |
| 확정된 명세의 분기 조건 (빈 값·경계·중복·권한) |   ✅    | 명세를 코드로 고정하는 유일한 수단                |
| API 계약 (요청 도달·중복 호출·성공/실패 흐름)  | ✅ MSW  | 응답 본문보다 **흐름**을 검증한다                 |
| 컴포넌트 렌더링                                | ⚠️ 선별 | 사용자 인터랙션이 있는 것만                       |
| 시각 스타일 · 레이아웃 · 간격                  |   ❌    | Storybook + Figma 대조의 영역                     |
| legacy의 관찰 가능한 핵심 동작                 | ⚠️ 선별 | 기준선의 가치와 잘못된 동작 고착 위험을 함께 판단 |

**로직을 먼저 순수 함수/훅으로 추출**하면 대부분의 검증이 가벼워진다.
다만 테스트를 위해 제품 코드를 불필요하게 추상화하지 않는다. 컴포넌트는 책임이 분리될 때만 나눈다.

## 2. Storybook은 테스트가 아니다

`*.stories.tsx`는 **PM·디자이너가 열어보는 컴포넌트 상태 문서**다.
동작 검증을 story로 대체하지 않는다. 검증은 `*.test.ts(x)`로 쓴다.

컴포넌트당 대표 상태 story는 문서로서 따로 관리하지만, 그건 테스트 산출물이 아니다.

## 3. 이전할 때는 무엇을 고정하는지 먼저 결정한다

legacy 코드를 그대로 보고 쓴 테스트는 의도하지 않은 결함까지 고정할 수 있다. 반대로 인증 분기,
데이터 손실 방지, 핵심 사용자 경로처럼 회귀 비용이 큰 동작은 자동화된 characterization test가
문서 기준선보다 안전할 수 있다.

두 걱정은 서로 다른 도구가 잡는다.

| 걱정                       | 정체       | 잡는 도구                                     |
| -------------------------- | ---------- | --------------------------------------------- |
| 옮기다 동작이 깨짐         | regression | 문서 기준선 또는 선별한 characterization test |
| 원래부터 명세가 반영 안 됨 | spec gap   | **Figma·기획과의 문서 대조** (`design-diff`)  |

**그래서 순서가 이렇다.**

```
1. 현행 동작을 문서로 기록
2. Figma·기획과 대조해 차이 목록 만들기
3. [GATE] 사용자가 고침/유지/나중 판정
4. 확정 명세를 검증 기준으로 작성
5. 회귀 비용과 자동화 가치가 큰 동작에 테스트 작성
6. 이전
```

테스트 여부는 legacy의 구현 형태가 아니라 **확정된 계약, 회귀 위험, 자동화 비용**으로 결정한다.

## 4. 테스트 작성 규칙

**위치** — 대상과 같은 폴더에 co-locate. `button.tsx` → `button.test.tsx`

**이름** — 한국어 BDD. `[조건]일 때 [동작]하면 [기대 결과]한다`
조건이 자명하면 생략한다. 값·식별자는 **원문 그대로** 둔다 (`onChange`를 "변경 콜백"으로 옮기지 않는다).

```ts
it('isLoading 이면 클릭해도 onClick 이 호출되지 않는다', ...)
it('[]를 넘기면 []를 반환한다', ...)
```

**import** — `globals: false`이므로 명시적으로 가져온다.

```ts
import { describe, it, expect, vi } from 'vitest';
```

**격리** — 전역 모킹이 다른 테스트로 새지 않게 한다.
`vitest.setup.ts`가 `afterEach`에서 `cleanup()` + `vi.restoreAllMocks()`를 이미 처리한다.

## 5. 금지

- ❌ **스냅샷 테스트 남발.** 무엇이 왜 바뀌었는지 못 알려주고, 깨지면 그냥 갱신하게 된다
- ❌ **테스트를 통과시키려고 구현을 비트는 것.** 테스트가 사양이고 구현이 거기 맞춘다.
  테스트가 틀렸다고 판단되면 멈추고 사용자에게 보고한다
- ❌ **화면 스타일을 CSS 클래스 문자열로 단언.** 시각 검증은 못 하고 리팩터에 취약하다.
  단, `cn()`이나 variant처럼 클래스 조합 자체가 공개 계약인 유틸·디자인 시스템 테스트는 예외다
- ❌ **테스트를 지워서 초록 만들기**

## 6. 알려진 실패를 숨기지 않는다

실패하는 테스트를 삭제하거나 이유 없이 `skip`해서 검증을 초록으로 만들지 않는다. 아직 지원하지
않는 동작은 테스트와 구현 범위에서 함께 제외하고 작업 문서에 남긴다. 이미 보장하기로 한 동작이
깨졌다면 테스트를 통과시키거나, 명세 변경 승인을 받은 뒤 테스트를 함께 수정한다.
