# work/ 작업 문서 규칙

작업 하나 = 폴더 하나. 폴더가 `to-do/ → in-progress/ → done/` 사이를 **통째로** 이동한다.
사람이 읽는 안내는 `work/README.md`, 이 문서는 AI가 지킬 규칙이다.

---

## 1. 어디에 무엇을 쓰는가

|      | `docs/`                              | `work/`                                |
| ---- | ------------------------------------ | -------------------------------------- |
| 성격 | **기준 문서** — 상태 없음, 항상 최신 | **흐름 문서** — 상태 있음, 끝나면 동결 |
| 갱신 | 구현이 바뀌면 덮어씀                 | 이력이 남게 누적                       |
| 예   | design-system, 화면 명세, 컨벤션     | 요구사항, 계획, 검증, 회고             |

**둘을 헷갈리지 않는다.** 회고를 `docs/`에 쓰거나 컨벤션을 `work/`에 쓰지 않는다.

## 2. 폴더 이름

```
{ID}-{짧은-설명}        예) MIG-004-LEARN-01-학습홈-이전
```

ID prefix가 작업 종류를 말한다. **번호는 prefix별이 아니라 전역 통번호다.**

`FEAT-` 신규 기능 · `MIG-` legacy 이전 · `REF-` 구조 리팩터 ·
`FIX-` 시안 대조 수정/버그 · `NAT-` native · `INFRA-` 하네스/빌드/CI

새 작업은 템플릿을 복사해서 시작한다.

```bash
cp -r work/TEMPLATE "work/to-do/MIG-004-LEARN-01-학습홈-이전"
```

## 3. `in-progress/`에는 하나만 둔다

스킬이 `ls work/in-progress/`로 "지금 하는 일"을 읽는다.
여러 개가 있으면 어느 것을 작업 중인지 판단할 수 없다.

새 작업을 시작하기 전에 **이전 작업을 `done/`으로 옮겼는지 확인**한다.

## 4. 파일별 소유자 — 남의 산출물을 덮어쓰지 않는다

| 파일            | 누가 쓰나                                                                                                           |
| --------------- | ------------------------------------------------------------------------------------------------------------------- |
| `spec.md`       | 사람이 시작. `refactor-baseline`이 현행 동작 기준선을, `design-diff`가 시안 대조 결과를 **각자 자기 섹션에만** 추가 |
| `plan.md`       | `ai-plan`                                                                                                           |
| `issues.md`     | `feature-planner`                                                                                                   |
| `issue-{N}.md`  | 향후 `test-scenarios` — 스킬 도입 전에는 사용하지 않는 예약 템플릿                                                  |
| `checklist.md`  | `ai-validate`                                                                                                       |
| `retrospect.md` | 선택 회고. 향후 `ai-retrospect` 도입 시 **덮어쓰지 않고 `---` 아래에 회차를 누적**                                  |

큰 `FEAT-`·`NAT-` work task는 여러 실행 이슈로 나눌 수 있다. 실행 이슈 하나는 GitHub Issue
하나와 정확히 연결한다. 파일명은 work task 내부 순번(`issue-01.md`)을 사용하고, GitHub Issue
번호는 파일명이 아니라 `github_issue` frontmatter에 기록한다.

## 5. 상태 이동 규칙

| 이동                      | 조건                                                         |
| ------------------------- | ------------------------------------------------------------ |
| `to-do/` → `in-progress/` | `ai-plan`이 계획을 세우고 **사용자가 승인**했을 때           |
| `in-progress/` → `done/`  | 검증(`checklist.md`) 완료 + 필요한 `docs/` 기준 문서 갱신 후 |

**폴더를 옮길 때 `git mv`를 쓴다.** rename으로 인식되어 이력이 유지된다.

`done/`으로 옮긴 뒤에는 그 폴더를 수정하지 않는다. 후속 작업이 필요하면 새 ID를 딴다.

## 6. `docs/`로의 승격 — 빠뜨리면 안 되는 마지막 단계

작업이 끝나면 **확정된 것을 기준 문서로 올린다.** 이걸 건너뛰면 다음 작업이 그 결정을 모른 채 시작한다.

| work/의 산출                       | →   | docs/의 기준 문서                          |
| ---------------------------------- | --- | ------------------------------------------ |
| 화면 구현·검증 상태                | →   | `docs/implementation-status.md`            |
| **`MIG-`의 legacy 대체 완료 사실** | →   | **`docs/migration-status.md`** — 생략 금지 |
| `spec.md`의 확정 명세 · 검증 기준  | →   | `docs/fe-implement-spec/{화면ID}/`         |
| 새로 정한 토큰 · 컴포넌트 규격     | →   | `docs/design-system/`                      |
| 새로 합의된 코드 규칙              | →   | `docs/conventions/` + `.claude/rules/`     |

## 7. 작업 중 발견한 별개 문제는 새 항목으로 뽑는다

작업하다 범위 밖의 문제를 발견하면 **그 자리에서 고치지 않는다.**
`work/to-do/`에 새 폴더를 만들고 `spec.md`에 재현·원인·범위를 적는다.

범위 밖 수정을 끼워 넣으면 검증에서 "무엇 때문에 깨졌는지" 구분이 안 되고,
동작 보존이 목표인 이전 작업에서는 특히 위험하다.

> 실제 사례: 테스트 하네스를 켜자마자 `FIX-001`(Button asChild) · `REF-002`(steiger) ·
> `REF-003`(prettier)이 나왔다. 셋 다 그 자리에서 고치지 않고 항목으로 뽑은 뒤,
> 파이프라인을 막는 `REF-002`만 사용자 승인을 받아 처리했다.
