# apps/legacy-web 정책 — 참조 전용, 편집 금지

`apps/legacy-web`은 **읽기만 한다.** 새 코드는 전부 `apps/web`에 쓴다.

---

## 왜 편집하면 안 되는가

1. **워크스페이스에서 제외돼 있다.** `pnpm-workspace.yaml`에 `!apps/legacy-web`이 있어
   `turbo run lint / check-types / build`가 **legacy-web을 검사하지 않는다.**
   → 여기 코드를 고쳐도 루트 검증 명령이 실패를 알려주지 않는다.
2. **이전이 진행 중이다.** 옛집을 고치면 새집으로 옮길 대상이 계속 움직여
   현행 동작 기준선(`refactor-baseline`)이 무의미해진다.
3. `.prettierignore`에도 들어 있어 포맷 검사 대상이 아니다.

## 무엇을 위해 읽는가

legacy-web은 **이전 작업(`MIG-`)의 입력**이다. 아래 목적으로만 읽는다.

| 목적                  | 무엇을 읽나                                             |
| --------------------- | ------------------------------------------------------- |
| 현행 동작 기준선 작성 | 화면이 **관찰 가능하게** 무엇을 하는지 (분기·상태·문구) |
| 이전 매핑 작성        | 파일이 어느 레이어·슬라이스에 있고 어디로 가야 하는지   |
| API 사용 확인         | 어떤 엔드포인트를 어떤 순서로 부르는지                  |

## 읽을 때 주의 — 구조를 따라 하지 않는다

legacy-web의 폴더·이름·상태 관리·컴포넌트 패턴은 새 구조의 근거가 아니다. 관찰 가능한 동작과
외부 계약만 기준선으로 삼고, 새 코드의 배치는 `fsd-*.md`와 코드 작성 규칙에 따라 다시 판단한다.

## 예외 — 편집이 필요할 때

legacy-web을 실제로 고쳐야 하는 상황(예: 이전 전까지 운영해야 하는 치명적 버그)이라면,
**임의로 고치지 말고 사용자에게 확인을 받는다.** 확인 후 고칠 때는:

- 루트 검증 범위 밖이므로 변경 전에 해당 앱에서 실행 가능한 검증 방법을 먼저 확인한다
- 같은 수정이 `apps/web` 이전분에도 필요한지 함께 판단한다

## 최종 처리

legacy-web은 `docs/migration-status.md`의 폐기 조건이 모두 충족되고 사용자가 승인한 뒤 별도 작업에서
제거한다. 일부 파일을 이전 진행 중에 개별 삭제하지 않는다.
