# feature-planner

**legacy에 없는 것을 새로 만들 때** 쓴다. 이미 있는 것을 옮기는 건 `MIG-`이고 이 스킬이 아니다.

```
아이디어
  ↓ 1단계 — 요구사항 인터뷰            [GATE]
spec.md 의 배경·범위·Out of Scope·용어
  ↓ 2단계 — 기술 결정 (3안 비교 → ADR)  [GATE]
spec.md 의 기술 결정 섹션
  ↓ 3단계 — 이슈 분해                   [GATE]
issues.md
```

산출물은 전부 `work/to-do/{ID}/` 안에 쓴다. 새 작업이면 `work/TEMPLATE/`을 복사해 시작한다.
계획이 승인되기 전에는 `in-progress/`로 옮기지 않는다 (`work-management.md`).

**게이트를 건너뛰면 후속 단계가 전부 잘못된 전제 위에 쌓인다.**

---

## 1단계: 요구사항 인터뷰

### 진행 방법

아래 표는 빠짐없이 질문하는 설문지가 아니라 **요구사항 누락 검사표**다. 저장소와 사용자 설명으로
확정된 항목은 다시 묻지 않는다. 결정을 막는 항목만 한 번에 하나씩 묻고, 선택 가능한 사안이면
추천안과 이유를 함께 제시한다.

| #   | 질문                                                         |
| --- | ------------------------------------------------------------ |
| 1   | 이 기능의 주 사용자는 누구인가                               |
| 2   | 최소 동작 시나리오 3개는? (가장 기본적인 흐름)               |
| 3   | 데이터는 어디서 오고 어디에 저장되나? 기존 구조와의 관계는?  |
| 4   | 경계 조건 — 최대값, 빈 값, 중복, 동시성                      |
| 5   | 실패하면 사용자에게 무엇이 보이나                            |
| 6   | 기존 UI 패턴 중 재사용할 것은? (`shared/ui/`에 이미 있는 것) |
| 7   | 성능 제약 — 허용 응답 시간, 데이터 크기                      |
| 8   | 이 결정이 다음 기능에 영향을 주나                            |

### gravit 전용 질문

| #   | 질문                                                                                           |
| --- | ---------------------------------------------------------------------------------------------- |
| 9   | **FSD 위치** — `shared` 프리미티브 수정인가, `entities`/`features` 신설인가, `pages` 조립인가  |
| 10  | **디자인 근거** — Figma 시안이 있나? 없으면 무엇을 기준으로 만드나 (`design-source-policy.md`) |
| 11  | **web / native 경계** — 웹 화면만인가, native 셸이 관여하나? 관여하면 무엇을 누가 갖나         |
| 12  | **검증 가능성** — 자동화할 계약과 수동으로 확인할 항목은 무엇인가                              |

> 11번은 이 프로젝트의 구조상 자주 걸린다. native는 web을 WebView로 감싸는 셸이라
> 토큰·딥링크·푸시처럼 **경계를 넘는 것**은 누가 소유하는지 먼저 정해야 한다.

### 용어 고정 (Ubiquitous Language)

인터뷰 중 나온 핵심 용어를 확정한다. **코드·문서·대화에서 같은 단어가 같은 것을 가리켜야 한다.**
`spec.md`의 `용어 정의` 표에 적는다.

### 산출

`work/to-do/{ID}/spec.md`의 **배경·목표 / 범위 / 용어 정의**를 채운다.

```
[GATE] 사용자가 읽고 "확정"할 때까지 2단계로 넘어가지 않는다.
```

## 2단계: 기술 결정 (ADR)

### 2-1. 최소 3안을 제안하고 비교표를 만든다

| #   | 비교 기준                                                                           |
| --- | ----------------------------------------------------------------------------------- |
| 1   | 데이터 구조 — 어떤 형태로 저장/표현하는가                                           |
| 2   | API 변경 지점 — 기존 명세에서 무엇이 바뀌나 (orval 재생성이 필요한가)               |
| 3   | 상태 변경 지점 — Query / Zustand 중 무엇이 늘어나나                                 |
| 4   | 핵심 동작 — 가장 중요한 동작이 어떻게 구현되나                                      |
| 5   | 컴포넌트 구조 — 무엇이 추가·수정되나                                                |
| 6   | 기존 패턴과의 일관성                                                                |
| 7   | 테스트 용이성                                                                       |
| 8   | **FSD 경계** — `shared`/`entities`/`features`/`widgets`/`pages` 중 어느 책임인가    |
| 9   | **토큰 정합성** — `tokens.css`의 토큰으로 표현 가능한가 (`design-source-policy.md`) |
| 10  | **web / native 분담** — 각 안에서 native가 무엇을 맡나                              |

### 2-2. 고른 안을 ADR로 쓴다

`spec.md`의 `기술 결정 (ADR)` 섹션을 채운다. 4요소 전부 필수다.

- **Context** — 이 결정이 필요한 맥락
- **Decision** — 무엇을 선택했는가
- **Alternatives** — 거부한 안과 **각각의 거부 이유**. 이유 없는 거부는 적지 않는다
- **Consequences** — 트레이드오프. **단점 없는 ADR은 신뢰할 수 없다**

> ADR을 쓰는 이유는 지금 설득하기 위해서가 아니라, **3개월 뒤에 "왜 이렇게 했지"에 답하기 위해서**다.
> 거부한 안의 이유가 특히 그렇다.

### 2-3. Out of Scope를 확정한다

**"이번에 하지 않을 것"을 구체적으로 나열한다.**
명시하지 않으면 범위를 확장 해석하게 된다.

```
[GATE] 3안 중 하나를 선택하고 Out of Scope를 확정할 때까지 대기한다.
```

## 3단계: 이슈 분해

### 수직 슬라이싱 — 이 단계의 전부

> **"이 이슈만 완료하면 사용자에게 보여줄 수 있는 동작이 있는가?"**
>
> - **Yes** → 수직 슬라이스
> - **No** → 다른 이슈와 합치거나 다시 나눈다

**수평 슬라이싱 금지.** 레이어별로 쪼개면(API 이슈 → 상태 이슈 → UI 이슈)
**마지막 이슈까지 끝나야 처음으로 동작이 나온다.** 중간에 멈추면 아무것도 없다.

- **크기**: 반나절~하루
- **의존성**: 실제 선행 결과가 필요한 경우에만 선언한다. 독립 이슈는 병렬 실행 가능하게 둔다

### 이슈 형식

`work/to-do/{ID}/issues.md`에 쓴다. 템플릿은 `work/TEMPLATE/issues.md`.

하나의 work task는 여러 실행 이슈를 가질 수 있다. 각 실행 이슈에는 work task 내부 순번을
부여하고, 사용자 승인 후 GitHub Issue 하나와 1:1로 연결한다 (`work-management.md`).

```markdown
## Issue N: [태그] 제목

### 설명

사용자 가치 중심으로 1~3문장.

### 구현 범위

건드리는 파일 / 레이어.

### 완료 조건 (Acceptance Criteria)

☐ AC-1 (범위: 단위|통합)
Given [실제 데이터값]
When [관찰 가능한 행동]
Then [값·개수·문구]
```

**AC 작성 규칙**

- `시나리오` 섹션을 따로 두지 않는다. **AC 자체가 Given-When-Then이다**
- 범위 레이블: `단위`(순수 함수·훅) / `통합`(RTL 렌더링 + 인터랙션)
- **Given에 실제 값을 넣는다.** "데이터가 있을 때"❌ → `[{ id: 1, name: '홍길동' }]`✅
- **Then에 값·개수·문구를 쓴다.** "필터링된다"❌ → `items.length === 1`✅
- **Then 금지어**: `정상적으로` `적절히` `올바르게` `보여진다` `처리된다` `업데이트된다` `반영된다`
  — 결과값 없이 결과를 서술하므로 테스트로 1:1 변환이 불가능하다

### GitHub Issue 연결

`work/to-do/{ID}/issues.md`가 **정본**이고 GitHub Issue는 실행·협업을 위한 외부 표현이다.
이슈 목록이 승인되면 각 실행 이슈를 GitHub Issue 하나와 연결한다.

외부 상태를 바꾸는 작업이므로 사용자가 생성을 요청하거나 승인하기 전에는 `gh issue create`를
실행하지 않는다. 승인 전에는 `GitHub Issue: 미등록`으로 두고, 생성 후 번호와 링크를
`issues.md`에 기록한다. 이후 AC나 범위가 바뀌면 정본과 GitHub Issue가 어긋났음을 보고하고
동기화 승인을 받는다.

```bash
gh issue create --title "제목" --body "설명 + AC + 의존성"
```

```
[GATE] 사용자가 이슈 목록을 읽고 수직 슬라이스·AC 구체성·의존성 순서를 확인할 때까지 대기한다.
```

## 다음 단계

이슈가 확정되면 `issue-reviewer`로 검토한 뒤 구현으로 넘어간다.
필수 수정 사항이 없고 사용자가 이슈 목록을 승인하면 `ai-plan`으로 구현 계획을 세운다.
`issue-{N}.md`와 `test-scenarios`는 아직 도입 전이므로 현재 흐름에서 사용하지 않는다.

## 하지 않는 것

- ❌ **게이트 건너뛰기** — 세 번 멈춘다
- ❌ **`MIG-` 작업에 쓰기** — legacy에 이미 있는 건 `refactor-baseline`부터
- ❌ **질문을 한꺼번에 던지기**
- ❌ **단점 없는 ADR** — Consequences가 장점뿐이면 아직 안 따져본 것이다
- ❌ **수평 슬라이싱**
- ❌ 코드 작성 — 이 스킬의 산출물은 문서뿐이다
