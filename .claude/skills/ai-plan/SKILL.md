# ai-plan

## 0. 컨텍스트

`work/in-progress/`와 `work/to-do/`를 확인한다. `in-progress/`에 둘 이상 있으면 어느 작업을
대상으로 할지 임의로 고르지 않고 상태부터 정리한다.

대상 작업 폴더의 `spec.md`를 읽는다. 종류별로 선행 조건이 다르다.

| 종류             | 선행 조건                                                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `MIG-`           | **현행 동작 기준선이 있어야 한다.** 없으면 `refactor-baseline`을 먼저 돌리라고 안내하고 멈춘다                                  |
| `REF-`           | 기준선 문서는 **필수가 아니다.** 대상 코드에 테스트가 있으면 그게 기준선이다. 없으면 "동작을 무엇으로 고정할지"를 계획에 적는다 |
| `FEAT-` · `NAT-` | `feature-planner`의 3단계가 끝나 있어야 한다                                                                                    |

**규모가 크면(파일 10개 초과 · 여러 슬라이스) `refactor-planner`가 먼저다.**
그게 실행 이슈로 쪼개 주고, `ai-plan`은 승인된 이슈를 빠짐없이 포함하는 **work task 전체**의
구현 계획을 세운다. 여러 이슈가 있으면 각 체크리스트 항목에 `Issue N`을 표시하고 실제 의존성
순서로 배치한다. `plan.md`를 이슈마다 덮어쓰지 않는다.

---

## 1. 작업 종류 판정

ID prefix가 곧 종류다. 새 작업이면 prefix를 정하고 근거를 한 줄로 밝힌다.

| prefix   | 판단 기준                                  |
| -------- | ------------------------------------------ |
| `FEAT-`  | 없던 기능을 새로 만든다                    |
| `MIG-`   | legacy-web에 있는 것을 apps/web으로 옮긴다 |
| `REF-`   | apps/web 안에서 구조만 바꾼다 (동작 불변)  |
| `FIX-`   | 시안과 다르거나 버그다                     |
| `NAT-`   | apps/native                                |
| `INFRA-` | 하네스·빌드·CI                             |

**번호는 전역 통번호다.** 새 번호가 필요하면 `work/` 전체의 현재 최댓값을 확인해 다음 번호를
제안하고 사용자에게 확정받는다. 다른 브랜치에서 동시에 번호를 만들 수 있으므로 자동 확정하지 않는다.

> 동작 변경과 구조 변경이 **한 작업에 섞이면 쪼갠다.** 검증에서 "무엇 때문에 깨졌는지"
> 구분이 안 되고, 이전 작업에서는 특히 위험하다.

---

## 2. 착수 판단 (`MIG-` · `REF-` 필수)

**`.claude/rules/refactor-checklist.md`를 읽고 그대로 적용한다.** 여기서 다시 서술하지 않는다 —
두 곳에 같은 기준이 있으면 한쪽만 고쳐진다.

`plan.md`에 남길 것:

- 정본의 **착수 전 필수 게이트**에 대한 답과 근거. 점수로 상쇄하지 않는다
- **자동 보류 신호** 해당 여부
- 보류가 났으면 → **`refactor-baseline`만 먼저 뜨는 것을 제안**하고 멈춘다

> 파일 수가 적다고 안전한 게 아니다. 크기보다 **영향과 검증 가능성**을 본다.

## 3. 영향 분석

```bash
# 이전 대상이 참조되는 곳
rg -l "<대상 경로>" <조사 범위> -g "*.ts" -g "*.tsx"
```

| 구분 | 파일 |
| ---- | ---- |
| 신규 |      |
| 수정 |      |
| 삭제 |      |

### `MIG-` · `REF-`는 이전 매핑표를 만든다

| 현재 위치 | 목표 위치 | 변경 종류 | import 영향 |
| --------- | --------- | --------- | ----------- |

목표 위치는 현재 `.claude/rules/fsd-*.md`, `import-convention.md`,
`component-convention.md`를 기준으로 판정한다. 과거 작업의 경로를 관행처럼 복사하지 않는다.

---

## 4. 구현 계획 체크리스트

적용되는 레이어는 `shared → entities → features → widgets → pages → app` 순서로 계획한다.
아래를 먼저 만들어야 위가 참조할 수 있고, 반대로 하면 매 단계 빌드가 깨져
"지금 깨진 게 내 탓인지 순서 탓인지" 구분이 안 된다.

```markdown
- [ ] `[shared]` …
- [ ] `[widgets]` …
- [ ] `[pages]` …
- [ ] `[app]` 라우트 등록 + **라우트 트리 재생성**
```

라우트를 추가하는 계획이면 **트리 재생성 단계를 명시적으로 넣는다.** 빼먹으면 검증이 실패한다
(`ai-orchestrate` §4 참고).

| ------ | ---- | ---- |

특히 확인할 것: 토큰·인증 흐름 / orval 재생성 필요 여부 / 라우트 트리 / 레거시 호환 토큰.

### `MIG-` · `REF-`는 **동일성을 무엇으로 확인할지** 여기 적는다

`spec.md`의 `동일성 확인 방법`을 구체적인 실행 계획으로 옮긴다.
"수동 확인"만 적으면 나중에 아무도 안 한다.

| 방법        | 예                              |
| ----------- | ------------------------------- |
| 라우트 진입 | `/terms` 열어 h1·h2 개수 확인   |
| 수동 스모크 | 로그인 → 새로고침 → 세션 유지   |
| 자동 테스트 | 확정 명세 중 로직성 항목만      |
| 명시적 대조 | 계약·문구·분기별 이전 전후 비교 |

## 6. ⏸ 게이트 — 승인 없이 넘어가지 않는다

계획을 `work/to-do/{ID}/plan.md`로 **저장한 뒤** 사용자에게 제시한다.

> 계획을 대화에만 두면 세션이 끊길 때 사라진다. 파일로 남긴다.

승인되면:

- 작업 폴더를 `work/to-do/` → `work/in-progress/`로 `git mv`
- `ai-orchestrate`로 넘어간다

**승인 전에 코드를 건드리지 않는다.**

---

## 하지 않는 것

- ❌ 승인 전 구현 시작
- ❌ 착수 게이트를 형식적으로 채우기 — 답의 근거를 적지 못하면 아직 모르는 것이다
- ❌ 보류 판정을 뒤집어 밀어붙이기 — 대신 기준선을 제안한다
- ❌ 계획을 대화에만 두기
- ❌ 실측 없이 "영향이 클 것 같다"고 추정하기 — `rg -l`의 현재 파일 목록으로 확인한다
