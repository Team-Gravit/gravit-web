# refactor-planner

**동작을 바꾸지 않으면서** 구조를 옮기는 작업을, 실행 가능한 이슈로 쪼갠다.

```
spec.md 의 현행 동작 기준선
  ↓ 1. 기준선 확인            [GATE]
Refactor Brief
  ↓ 2~3. Brief + ADR          [GATE]
이전 매핑
  ↓ 4. Migration Map          [GATE]
issues.md
  ↓ 5. 동작 보존 단위 이슈    [GATE]
```

## 언제 쓰나 / 안 쓰나

| 상황                                                       |                                                    |
| ---------------------------------------------------------- | -------------------------------------------------- |
| 파일 10개 초과 · 여러 슬라이스 · 도메인 하나를 통째로 이전 | ✅ 쓴다                                            |
| 파일 몇 개, 한 슬라이스 안 (REF-002 아이콘 이동 정도)      | ❌ `ai-plan`으로 바로                              |
| 새 기능                                                    | ❌ `feature-planner`                               |
| 동작 변경이 섞임                                           | ❌ `FEAT-`/`FIX-`로 분리 (`refactor-checklist.md`) |

---

## 1. 기준선 확인

`work/to-do/{ID}/spec.md`의 **현행 동작 기준선**과 **동작 계약**을 읽는다.

- **`MIG-`인데 기준선이 없으면** → `refactor-baseline`을 먼저 돌리라고 안내하고 **멈춘다**
- **`REF-`이고 대상 코드에 테스트가 있으면** → 그 테스트가 기준선이다. 문서를 새로 안 만들어도 된다.
  테스트가 없으면 재현 가능한 문서 기준선과 검증 방법부터 만든다. 이 스킬에서 코드를 작성하지 않는다

> 기준선의 형태는 출처가 아니라 위험과 기존 검증 자산에 따라 고른다. legacy도 신뢰할 수 있는
> 테스트가 있을 수 있고, `apps/web`도 테스트가 없을 수 있다. 문서 기준선과 선별 테스트를
> 함께 사용할 수 있다 (`test-policy.md`).

출력:

```markdown
## Baseline Summary

- 기준선: work/to-do/{ID}/spec.md 의 A1~A11 / 테스트 `xxx.test.ts`
- 보존해야 할 계약: C1 토큰 저장 위치 · C2 401 재시도 순서 …
- 변경 금지: 생성물(`routeTree.gen.ts`·`shared/api/generated/`), 사용자 문구
```

```
[GATE] 기준선이 맞는지 사용자에게 확인받는다.
```

## 2. Refactor Brief

"무엇을 새로 만드나"가 아니라 **"왜 구조를 바꾸며 무엇은 보존하나"**를 적는다.
`spec.md`의 배경·범위·Out of Scope를 채운다.

- **목적** — FSD 위반 제거 / import 경계 정리 / 중복 슬라이스 병합 등
- **범위** — 다룰 도메인·슬라이스·파일군. 어떤 동작 계약을 보존하는지 연결
- **Out of Scope** — 이번에 하지 않을 동작 변경·UI 변경·성능 최적화. **구체적으로**
- **성공 기준** — 매핑 전량 반영 · 동작 보존 AC 통과 · `check-types`/`lint`/`test`/`build` 통과

**Out of Scope를 대충 쓰면 리팩터가 기능 개선으로 번진다.**

## 3. ADR — 목표 구조가 둘 이상이면 필수

`spec.md`의 `기술 결정 (ADR)` 섹션에 쓴다. 최소 2안, 복잡하면 3안을 비교한다.

| 비교 기준       | 설명                                       |
| --------------- | ------------------------------------------ |
| FSD 적합성      | 목표 위치가 레이어·슬라이스 규칙에 맞는가  |
| import 영향     | 갱신 범위와 위험도                         |
| 동작 보존성     | 동작 계약을 안전하게 지킬 수 있는가        |
| 테스트 용이성   | 보존 시나리오를 테스트로 검증하기 쉬운가   |
| **점진 이전성** | **작은 이슈 단위로 나눠 진행할 수 있는가** |

**단점 없는 ADR은 신뢰하지 않는다.** Consequences에 트레이드오프를 반드시 적는다.

> 실제 사례 — 로고를 `shared/ui/icon/`에 넣을지 `shared/ui/logo/`를 신설할지가 ADR 감이었다.
> `Icon`이 정사각형을 강제하고 gradient 로고가 아이콘 의미론에 안 맞는다는 게 결정 근거였다.

```
[GATE] 방향을 확정받는다.
```

## 4. Migration Map

현재 경로 → 목표 경로를 표로 만든다. **import 영향을 실측한다.**

```bash
rg -l "<대상 경로>" <조사 범위> -g "*.ts" -g "*.tsx"
```

명령 결과의 파일 목록을 근거로 영향 수를 기록한다. `MIG-`는 legacy와 새 앱 양쪽을,
`REF-`는 실제 변경 대상 앱을 조사한다.

| 현재 경로                        | 목표 경로                      | 변경 종류 | import 영향 | 보존 AC |
| -------------------------------- | ------------------------------ | --------- | ----------: | ------- |
| `shared/model/use-responsive.ts` | `shared/lib/use-responsive.ts` | move      |        15곳 | AC-2    |

목표 위치는 `.claude/rules/fsd-*.md`, `import-convention.md`, `component-convention.md`의
현재 규칙으로 판정한다. 과거 작업의 경로나 수치를 복사하지 말고 현재 코드에서 다시 측정한다.

```
[GATE] 매핑을 확정받는다.
```

## 5. 동작 보존 단위로 이슈를 쪼갠다

**이 단계가 이 스킬의 전부다.**

> **"이 이슈만 끝나도 기존 사용자 동작이 그대로 유지되는가?"**

레이어별 수평 분할이 아니다. 신규 기능의 수직 슬라이싱과 같은 원리인데,
**"보여줄 동작이 있는가" 대신 "동작이 유지되는가"**로 판단한다.

|              | 예                                                    |
| ------------ | ----------------------------------------------------- |
| ✅ 좋은 이슈 | `토큰 매니저 위치 이전 + 401 재시도 동작 동일성 검증` |
| ✅           | `Footer 위젯 이전 + 링크 2개·mailto 유지 검증`        |
| ✅           | `학습 목록 화면 이전 + 빈 상태·에러 상태 유지 검증`   |
| ❌ 나쁜 이슈 | `shared 전체 정리`                                    |
| ❌           | `entities 전부 이동`                                  |
| ❌           | `API 레이어만 이동` — 이 상태로는 화면이 안 돈다      |

**크기 목표**: 반나절~하루. 실제 선행 결과가 필요한 경우에만 의존성을 선언하고,
독립 이슈는 병렬로 진행할 수 있게 둔다. 순환·역방향 의존은 금지한다.

이슈는 `work/to-do/{ID}/issues.md`에 쓴다. 형식은 `work/TEMPLATE/issues.md`에 더해:

```markdown
### 관련 결정

- 기준선: `spec.md` 의 A1~A5 / 동작 계약 C2
- ADR: `spec.md` 의 기술 결정

### 이 이슈가 담당하는 매핑

| 현재 경로 | 목표 경로 | 변경 종류 |
| --------- | --------- | --------- |
```

### ⚠️ AC는 "동작이 보존됐다"를 검증한다

```
❌ Then 파일이 shared/lib/ 로 이동한다        ← 구조가 바뀐 것
✅ Then useResponsive() 가 768px 미만에서 true 를 반환한다   ← 동작이 유지된 것
```

**"구조가 바뀌었다"는 AC가 아니다.** 그건 매핑표가 이미 말한다.

```
[GATE] 이슈 목록을 확정받는다.
```

확정된 실행 이슈는 `work-management.md`에 따라 GitHub Issue와 1:1로 연결한다. 외부 상태를
바꾸는 작업이므로 사용자가 생성 또는 동기화를 승인하기 전에는 GitHub Issue를 만들거나 수정하지 않는다.

## 게이트에서 확인할 것

- 모든 이슈가 **동작 보존 단위**인가
- Out of Scope가 이슈에 슬쩍 들어가 있지 않은가
- ADR에 **대안과 트레이드오프**가 있는가
- 각 이슈가 매핑표의 어느 부분을 담당하는지 명확한가
- 각 AC가 **동작 계약을 검증**하는가 (구조 변경 서술이 아니라)
- 변경 범위가 구조에 머무는가 (동작 변경이 안 섞였는가)

## 다음 단계

이슈가 확정되면 `issue-reviewer`로 검토하고, 이슈 하나씩 `ai-plan` → `ai-orchestrate` → `ai-validate`.

## 하지 않는 것

- ❌ 게이트 건너뛰기 — **네 번 멈춘다**
- ❌ 동작 변경과 구조 이전을 한 이슈에 섞기
- ❌ 레이어별 수평 분할
- ❌ import 영향을 추측으로 적기 — `rg -l`의 현재 파일 목록으로 센다
- ❌ 코드 작성 — 산출물은 문서뿐이다
