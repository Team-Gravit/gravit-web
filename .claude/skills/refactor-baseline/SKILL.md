# refactor-baseline

이전하기 전에 **"지금 무엇이 일어나는가"를 문서로 고정**한다.

## 왜 이걸 먼저 하는가

이 단계의 기본 산출물은 **문서 기준선**이다. 회귀 비용이 큰 확정 계약은 이후 선별한
characterization test로 함께 고정할 수 있다. 시안 대조 전에 legacy 구현을 그대로 테스트하면
의도하지 않은 결함까지 계약으로 굳힐 수 있으므로, 무엇을 보존할지 먼저 판정한다 (`test-policy.md` §3).

그래서 순서가 이렇다.

```
기준선(문서)  →  시안 대조  →  [GATE] 사용자 판정  →  확정 명세  →  테스트
```

**이 단계에서는 옳고 그름을 판단하지 않는다.** 판단은 시안 대조와 게이트에서 한다.

## 이전과 분리해서 쓸 수 있다

기준선만 뜨고 이전은 보류하는 것도 정당한 선택이다. 착수 게이트에서 보류되더라도 여러 화면이
의존하는 영역은 **흐름을 문서로 남겨야 나중에 판단할 근거가 생긴다.**

위험이 높아 착수를 못 하는 영역일수록 기준선을 먼저 떠두는 게 낫다.

---

## 절차

### 0. 범위 확정

무엇을 읽을지 먼저 정한다. 화면 단위면 라우트에서 시작해 타고 내려간다.

```bash
# 대상 화면 후보
rg -l "<라우트 또는 화면 키워드>" apps/legacy-web/src/pages -g "*.tsx"

# 선택한 진입 파일의 import
rg "^import" <라우트 파일>
```

인증 게이트(`_authenticated`) 안인지 밖인지 확인한다. 안이면 인증이 전제조건이다.

### 1. 범위 안의 의존 파일을 끝까지 읽는다

진입점에서 사용자 동작에 영향을 주는 의존 경로를 추적하고, 선택한 파일은 발췌가 아니라 전문을
읽는다. 범위 밖 공용 모듈 전체로 조사를 무한 확장하지 말고, 이번 동작과 연결된 분기·에러 처리까지만 본다.

레이어를 따라간다: 라우트 → 페이지 → 위젯 → 피처 → 엔티티 → shared.

**사용자가 관찰할 수 있는 효과**를 특히 찾는다. 코드를 읽다 보면 구조에 눈이 가는데,
기준선에 필요한 건 구조가 아니라 이것들이다.

- `localStorage` · `sessionStorage` 키 이름과 저장 시점
- 환경변수 (`VITE_*`)에 따라 달라지는 동작
- toast · modal · redirect — 사용자에게 보이는 반응
- API 호출 **순서**와 실패 시 분기
- query 무효화 시점

> 탐색 결과는 판단에 쓰되, **산출물에는 동작 계약에 필요한 것만 남긴다.**
> 읽은 걸 다 적으면 나중에 무엇이 중요한지 안 보인다.

### 2. 관찰 가능한 동작만 표로 적는다

`work/to-do/{ID}/spec.md`의 `## 현행 동작 기준선` 섹션에 쓴다.

| 쓰는 것                         | 쓰지 않는 것               |
| ------------------------------- | -------------------------- |
| 화면에 무엇이 보이는가          | 어떤 컴포넌트로 만들었는가 |
| 어떤 조건에서 무엇이 달라지는가 | 상태를 어디에 저장하는가   |
| 클릭하면 어디로 가는가          | 그 함수 이름이 무엇인가    |
| 실패하면 무엇이 표시되는가      | 어떤 라이브러리를 썼는가   |

**"확인한 위치" 열을 반드시 둔다.** 나중에 "이거 진짜야?"를 되짚을 수 있어야 한다.

```markdown
| #   | 동작                                                     | 확인한 위치          |
| --- | -------------------------------------------------------- | -------------------- |
| 1   | `/terms` 진입 시 "서비스 이용약관" 제목과 13개 조항 표시 | `pages/terms.tsx`    |
| 2   | 헤더 로고를 클릭하면 `/`로 이동                          | 두 파일의 `<header>` |
```

항목이 많으면 **A/B/C 그룹으로 나눈다** (예: 토큰 저장 / 라우트 게이트 / HTTP 인터셉터 /
OAuth / 로그아웃). 26항목쯤 되면 그룹 없이는 읽히지 않는다.

### 2-1. 그중 **바뀌면 안 되는 것**을 따로 뽑는다 (Behavior Contract)

기준선 전부가 같은 무게는 아니다. **깨지면 사용자에게 사고가 되는 것**을 별도 절로 뽑는다.

```markdown
## 동작 계약 (바뀌면 안 되는 것)

| #   | 계약                                      | 깨지면 무슨 일이 생기나         |
| --- | ----------------------------------------- | ------------------------------- |
| C1  | 기존 세션과 호환되는 토큰 계약을 유지한다 | 기존 사용자가 전부 로그아웃된다 |
| C2  | 401 → 갱신 → 원요청 1회 재시도 순서       | 요청이 조용히 실패한다          |
| C3  | 갱신 중 403이면 토큰을 지우지 않는다      | 권한 문제인데 로그아웃돼 버린다 |
```

**"깨지면 무슨 일이 생기나" 열이 핵심이다.** 그게 안 써지면 계약이 아니라 그냥 구현 디테일이다.

이 표가 나중에 `ai-validate`의 동작 동일성 확인 대상이 된다.

### 2-2. 확인이 필요한 제약 (Known Constraints)

외부 계약, 생성물, 플랫폼 경계처럼 이전 중 임의로 바꾸면 안 되는 조건을 적는다.

비표준 구조나 임시 구현을 자동으로 복사한다는 뜻은 아니다. 관찰 가능한 계약과 단순 구현 부채를
구분하고, 보존 여부를 사용자가 판단할 수 있게 근거를 남긴다.

### 2-3. 동일성 확인 방법 (Verification Ideas)

**이전 후 무엇으로 같음을 확인할지**를 미리 적는다. 여기서 나온 문장이
나중에 `확정 명세 · 검증 기준`의 Given-When-Then 원본이 된다.

```markdown
## 동일성 확인 방법

- 라우트 진입: `/terms` 열어 h1이 "서비스 이용약관"이고 h2가 13개인지
- 수동 스모크: 로그인 → 새로고침 → 세션 유지되는지
- 기존 테스트: 없음 (legacy에 테스트가 없다)
```

**"수동으로 확인"만 적지 말고 무엇을 보고 판단할지 쓴다.** 그래야 다른 사람도 같은 확인을 할 수 있다.

### 3. 토큰 호환성을 확인한다 (UI가 있는 화면)

legacy와 `apps/web`의 토큰 체계가 달라 **같은 클래스가 다른 색을 낼 수 있다.**
이전 후 조용히 어긋나는 대표적인 지점이다.

```bash
rg -n -- "--color-<이름>|--color-<그룹>-\\*: initial" \
  apps/legacy-web/src/app/styles/tokens.css apps/web/src/app/styles/tokens.css
```

확인 결과를 표로 남긴다. 호환 토큰의 현재 상태와 제거 조건은
`docs/design-system/README.md`를 기준으로 확인한다.

### 4. 발견사항은 기준선과 **분리해서** 적는다

읽다 보면 "이건 좀 이상한데" 싶은 게 나온다. 그건 현행 동작이 아니라 **관찰**이므로
`## 기준선을 쓰면서 발견한 것` 절에 따로 적는다.

실제로 나왔던 것들:

- **저장만 하고 읽지 않는 값** — `localStorage.returnTo`를 쓰기만 하고 읽는 코드가 없었다
- **전체가 주석 처리된 파일** — `use-refresh-token.tsx`. 주석 안의 코드조차 깨져 있었다
- **주석에 "핵심"이라고 강조된 예외 처리** — 실제로 겪은 버그를 고친 흔적이다. 이전 시 반드시 보존해야 한다
- **apps/web에 이미 있는 대응물** — 같은 문제를 더 낫게 푼 코드가 있는지 확인한다

이런 건 **판단하지 말고 `확인 필요`로 올린다.** "왜 이렇게 했는지"는 코드에 안 적혀 있고
사람 머릿속에만 있다.

### 5. `확인 필요`를 채운다

**임의로 결정하면 안 되는 것만** 적는다. 기준은 하나다 —
_내가 여기서 고르면, 그게 제품 결정이 되는가?_

```markdown
### 확인 필요

1. **`returnTo` 미완성 기능** — 로그인 후 원래 화면으로 돌아가는 것이 의도인가?
2. **403 특례가 의도된 동작인가?** 주석에 "핵심"이라고 강조돼 있어 실제 겪은 문제로 보인다
```

없으면 `없음`이라고 쓴다. 비워두지 않는다.

### 6. 보고

기준선 항목 수, 발견사항, `확인 필요` 건수를 요약한다.
**이전은 여기서 하지 않는다.** 다음 단계(시안 대조 또는 `ai-plan`)로 넘긴다.

## 하지 않는 것

- ❌ **코드 수정** — `apps/legacy-web`은 편집 금지다 (`legacy-web-policy.md`). 훅이 차단한다
- ❌ **구현 방식 기록** — "useState로 관리한다"는 동작이 아니라 구현이다.
  이전하면 어차피 바뀌는 것을 기준선에 넣으면 나중에 "동작이 달라졌다"는 오탐이 된다
- ❌ **좋고 나쁨 판단** — "이건 안티패턴이다"는 여기서 쓰지 않는다. 관찰만 적는다
- ❌ **테스트 작성** — 기준선은 문서다. 테스트는 명세가 확정된 뒤에 붙인다
- ❌ **빠진 걸 상상으로 메우기** — 조사 범위에서 근거를 찾지 못했다면 "없다"고 단정하지 말고,
  확인한 범위와 함께 `확인 필요`로 남긴다
