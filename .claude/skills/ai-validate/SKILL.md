# ai-validate

## 1. 자동 검사

```bash
pnpm lint            # eslint + steiger
pnpm check-types
pnpm test
pnpm build
```

### ⚠️ `pnpm format:check`는 전체를 보지 않는다

저장소 전체 포맷 검사는 **커밋된 6개 파일 때문에 이미 실패 중**이다 (`REF-003`).
전체를 돌리면 항상 빨간불이라 신호가 되지 않는다. **변경 파일만** 본다.

`plan.md`의 영향 파일과 `git status --short`를 대조해 **이번 작업이 변경한 파일만** 골라낸 뒤,
그 명시적 목록을 `pnpm exec prettier --check <파일...>`에 넘긴다. 셸별 명령 치환에 의존하거나
사용자의 범위 밖 변경을 검사·수정 대상에 섞지 않는다.

루트 명령은 저장소 기준 경로를 받는다. `pnpm --filter @repo/web exec ...`를 별도로 실행하면
작업 디렉터리가 `apps/web`이므로 그때만 앱 기준 상대경로를 사용한다.

### 라우트를 추가했는데 `check-types`가 실패하면

`routeTree.gen.ts`가 아직 새 라우트를 모르는 것이다. `ai-orchestrate` §4를 참고해
`pnpm --filter @repo/web exec vite build`로 트리를 먼저 생성한다.
**타입 오류가 아니라 순서 문제**이므로 코드를 고치지 않는다.

### generated 직접 참조 검사

```bash
rg -n "shared/api/generated" apps/web/src/pages apps/web/src/widgets -g "*.ts" -g "*.tsx"
```

화면(`pages`/`widgets`)이 생성 코드를 직접 참조하면 위반이다 (`api-convention.md`).

### 실패 시

이번 작업이 만든 실패이고 계획 범위 안에서 안전하게 수정할 수 있을 때만 수정 후 재검증한다.
재검증은 **최대 3회.** 초과하면 멈추고 보고한다.
기존 실패는 원인과 이번 작업의 관련성을 기록하되 범위 밖에서 고치지 않는다.
같은 실패가 3번 반복되면 접근이 틀린 것이지 노력이 부족한 게 아니다.

## 2. 요구사항 ↔ 구현 대조

`spec.md`의 AC를 하나씩 대조한다.

| #   | 요구사항 (AC) | 구현 위치 | 상태 |
| --- | ------------- | --------- | ---- |

**`구현 위치`에는 구현을 특정할 수 있는 정보를 쓴다** — 테스트 파일 경로, 함수명, 컴포넌트명.
"구현함", "완료"는 대조가 불가능하므로 쓰지 않는다.

AC를 테스트로 고정했으면 그 테스트 파일을 적는다. 그게 가장 강한 근거다.

## 3. 이전 검증 (`MIG-` · `REF-` 전용)

| 항목                                 | 확인 방법                         |
| ------------------------------------ | --------------------------------- |
| 이전 매핑이 **전량** 반영되었나      | `plan.md`의 매핑표를 한 줄씩 대조 |
| 동작 동일성 — 기준선 항목이 유지되나 | `spec.md`의 기준선 표를 한 줄씩   |
| 의도적으로 바꾼 것만 바뀌었나        | 아래 표를 별도로 작성             |
| 남은 legacy 참조가 없나              | `rg -n "<옛 경로>" apps/web/src`  |

줄 수·파일 수·변경량은 누락을 조사할 힌트로만 쓸 수 있고, 동작 동일성의 증거로 기록하지 않는다.
기준선 계약별 자동 테스트 또는 재현 가능한 수동 검증 결과를 근거로 남긴다.

### 의도적으로 바꾼 것을 표로 남긴다

| 항목 | 이유 |
| ---- | ---- |

**이유를 적을 수 없는 변경은 범위 밖이다.** 되돌리거나 별도 작업으로 뺀다.

## 4. 시안 대조 재확인 (`FIX-` · `MIG-`)

`spec.md`에서 "고침"으로 판정한 항목이 실제로 반영됐는지 확인한다.

시안이 없던 작업이면 **`해당 없음`이라고 명시**한다. 비워두면 나중에
"대조를 안 한 건지 시안이 없었던 건지" 구분이 안 된다.

## 5. 산출물

`work/in-progress/{ID}/checklist.md`를 **반드시 만든다.** 템플릿은 `work/TEMPLATE/checklist.md`.

### 중간에 막혔던 지점을 기록한다

이게 이 문서에서 가장 오래 남는 부분이다. 검사 결과는 다음 작업에 쓸모없지만,
**어디서 어떻게 막혔는지는 다음 작업에서 또 막힐 자리**다.

```markdown
### 중간에 막혔던 지점 — 스킬에 반영할 것

`check-types`가 한 번 실패했다. 라우트를 추가해도 routeTree.gen.ts가 갱신되지 않아…
→ ai-orchestrate 스킬에 "라우트 추가 후 트리 재생성" 단계를 넣어야 한다.
```

실제로 이 절 덕분에 `ai-orchestrate` §4가 만들어졌다.

## 6. 완료 처리

회고는 선택 사항이며 완료 조건이 아니다. 먼저 `checklist.md`를 완성하고 `spec.md`의 AC,
Changelog, 아래 기준 문서를 모두 갱신한다.

### 기준 문서를 갱신한다 — 생략 금지

사용자 화면의 구현·검증 상태가 바뀌면 `docs/implementation-status.md`를 갱신한다.
`MIG-`이면 여기에 더해 `docs/migration-status.md`의 legacy 대체·폐기 상태도 갱신한다.

- implementation: Figma ID가 확인된 화면만 연결하고 WebView와 네이티브 구현을 구분한다
- migration: `기준선` · `대체 구현` · `동작 검증`을 실제 완료된 단계까지만 표시한다
- 함께 옮긴 공용 런타임 기반이 있으면 해당 기능 행을 갱신한다
- 새 폐기 차단 요소가 생기면 상세는 `work/`에 두고 대장에는 링크만 남긴다
- 각 문서의 `갱신 이력`에 한 줄 추가한다
- 토큰 사용·제거 상태는 `docs/design-system/README.md`에서만 갱신한다

### 그 외 `docs/` 승격

확정된 화면 명세는 `docs/fe-implement-spec/{화면ID}/`로, 새로 정한 토큰·컴포넌트 규격은
`docs/design-system/`으로 올린다 (`work-management.md` §6). 이걸 건너뛰면
다음 작업이 그 결정을 모른 채 시작한다.

필수 산출물과 기준 문서 갱신이 끝난 뒤 **마지막 단계로** 폴더를 옮긴다.

```bash
git mv work/in-progress/{ID} work/done/{ID}
```

`done/`으로 옮긴 뒤에는 수정하지 않는다.

## 하지 않는 것

- ❌ 체크리스트 파일 생략
- ❌ `pnpm format:check` 전체 결과를 실패로 보고하기 — REF-003이 원인이면 그렇게 적는다
- ❌ 검사 실패를 "통과"로 적기 — 실패는 실패로 적고 원인을 밝힌다
- ❌ 재검증 3회 초과
- ❌ 커밋 (사용자가 요청할 때만)
