# 화면 구현 명세 규격

`docs/fe-implement-spec/{화면ID}/`의 문서는 **기획 · Figma · 확정 라우트 · API 계약을
한곳에서 대조**하기 위한 화면 구현 명세다. 화면 영역과 무관하게 같은 규격을 쓴다.

---

## 1. `work/`와의 관계 — 여기는 도착지다

```
work/{상태}/{ID}/spec.md          흐름 문서 — 상태 있음, 작업이 끝나면 동결
        │  현행 동작 기준선 → 시안 대조 → [GATE] 판정 → 확정 명세
        ↓  승격
docs/fe-implement-spec/{화면ID}/   기준 문서 — 상태 없음, 항상 최신
```

- **작업 중에는 `work/`에 쓴다.** 여기에 직접 쓰지 않는다
- 작업이 끝나면 **확정된 것만** 여기로 올린다 (`work-management.md` §6)
- 구현이 바뀌면 이 문서를 **덮어쓴다.** 이력은 `work/`에 남아 있다

> 승격을 건너뛰면 다음 작업이 그 결정을 모른 채 시작한다. **생략 금지 단계다.**

## 2. 작성 원칙

- 최신 기능 명세를 기준으로 작성한다
- Figma 이미지는 같은 화면 폴더에 두고 상대 경로로 첨부한다
- **`apps/web/src/app/routes/`에 실제로 존재하는 경로만** 확정 라우트로 기록한다.
  후보 라우트나 구현 제안은 넣지 않는다
- **orval 생성 코드(`apps/web/src/shared/api/generated/`)는 근거로만 쓴다** —
  화면이 조회·표시·입력·전송하는 필드명과 제약을 확인하는 용도다
- 서버 요청 시점, 전역 상태 도구, 컴포넌트 구조처럼 **기획으로 확정되지 않은 구현 설계는 다루지 않는다**
- **PNG에서 픽셀값을 역산하지 않고**, `flex`/`grid` 같은 CSS 구현 방식도 지정하지 않는다
- 요소의 순서·정렬·하단 고정 여부·선택/비활성 표현처럼 **이미지에서 관찰 가능한 규칙은 기록한다**
- 정확한 간격·크기·색·타이포는 **Figma Dev Mode 또는 `tokens.css`**를 기준으로 삼는다
- **기획·Figma·라우트·API 계약이 다르면 임의로 결정하지 않고 `확인 필요`에 기록한다**
- `UI States` · `API 영향` · `State` · `Frontend 후보` · `Component 후보` 섹션은 만들지 않는다

> 근거 우선순위와 금지 사항의 정본은 `.claude/rules/design-source-policy.md`다.

### 화면 개요

화면 ID · 화면명 · 경로 · 진입 화면 · 다음 화면을 표로 적고, 화면 목적을 한 문장으로 쓴다.

### 근거 자료

검토에 쓴 기획의 기준일, Figma 링크와 이미지, 실제 라우트 파일, orval 생성 스키마를 상대 링크로 적는다.

> **Figma 링크는 화면별 "Copy link to selection"을 여기에 1회만 기록한다.**
> 여러 문서에 흩어지면 어느 것이 최신인지 알 수 없게 된다.

### 기능 명세

기획에서 전달된 표의 열과 내용을 유지한다.

| 구분 | 기능 ID | 기능명 | 설명 | 참고 | 우선순위 | 상태 | 완료 | 제외 | 수정일 |
| ---- | ------- | ------ | ---- | ---- | -------- | ---- | ---- | ---- | ------ |

### 라우트 및 화면 이동

확정된 URL과 사용자 동작에 따른 이동 목적지를 적는다. 후보 라우트·구현 제안은 넣지 않는다.

파일 라우팅이므로 **파일명이 곧 URL이다** (`app/routes/learning.$unitId.tsx` → `/learning/:unitId`).
규칙은 `fsd-pages.md` §2.

### 화면 사용 데이터

화면이 API·경로·세션에서 받아 **표시하거나 분기에 쓰는 값**과, 사용자가 입력해 **요청으로 보내는 값**을 적는다.
화면 용어 · 출처(또는 API 필드) · 필수 여부 · 용도·제약 · 값이 없을 때의 처리를 표로 정리한다.
이 화면에서 쓰지 않는 필드는 넣지 않는다.

입력이 없는 조회·완료 화면은 `사용자 입력 없음`을 명시하고 표시·분기 데이터만 적는다.

### Figma 화면

첨부 이미지를 문서에 표시하고, 각 이미지가 어떤 화면이며 핵심 차이가 무엇인지 짧게 적는다.

시안이 없는 화면이면 **"시안 없음"을 확인한 날짜와 함께 명시한다** (`design-source-policy.md` §7).
비워두면 대조를 안 한 건지 시안이 없는 건지 구분되지 않는다.

### 기능별 동작

기능 ID 단위로 노출 조건 · 사용자 입력 · 활성화 조건 · 이동 결과를 적는다.

### 검증 기준

**관찰 가능한 결과만** 체크리스트로 쓴다.

금지어(Then): `정상적으로` `적절히` `올바르게` `보여진다` `처리된다` `업데이트된다` `반영된다`
— 결과값 없는 서술은 테스트로 1:1 변환이 불가능하다.

이 중 **로직성인 것만** 테스트가 된다. 시각 스타일은 테스트하지 않는다 (`test-policy.md`).

### 확인 필요

근거 자료 사이의 충돌이나, 구현 전에 기획 결정이 필요한 것만 적는다. 없으면 `없음`.

## 4. 화면 ID 체계 — 확정 (2026-09-11 · 계층 네이밍)

**Figma 프레임 이름이 곧 화면 ID다.** 새로 만들지 않고 그대로 쓴다.
정본은 `Screen Design` 페이지(`11246:4859`)의 **`SCREEN` 섹션(`13750:65506`)** 이다.
같은 페이지의 `WEB`(`11802:29211`) · `AOS`(`11802:29212`) 섹션은 **구버전**이며 참조하지 않는다.

```
{GROUP}-{NN}[/{STATE}]-{WEB|MOB}
MAIN-01-WEB          화면 MAIN-01 의 WEB 프레임
ONB-01/A-MOB         화면 ONB-01 의 상태 A, MOB 프레임
SUPPORT-02/DROPDOWN-WEB
MY-04/MODAL/FOLLOW-MOB
```

| 조각           | 뜻                                        | 문서에서 쓰는 곳                                                  |
| -------------- | ----------------------------------------- | ----------------------------------------------------------------- |
| `{GROUP}-{NN}` | **화면 ID.** 그룹 약어 + 두 자리 번호     | 폴더 `docs/fe-implement-spec/{소문자-id}/`, 기능 ID `MAIN-01-F01` |
| `/{STATE}`     | 같은 화면의 상태 변형. ID를 나누지 않는다 | 「기능별 동작」·「Figma 화면」에 상태로 기록                      |
| `-{WEB\|MOB}`  | 플랫폼 프레임. 문서는 화면당 하나로 쓴다  | 근거 자료의 노드 ID                                               |

폴더 예: `main-01/`, `onb-01/`, `quiz-03/`. 파일은 `{소문자-id}.md`, 이미지는 프레임 이름 그대로
(`MAIN-01-WEB.png`).

| 그룹     | 화면 ID                    | 화면 | 상태 변형                                                                          |

| LEARNING | `LRN-01`~`LRN-04`          |    4 | `LRN-04/A~B` (MOB만)                                                               |

**WEB과 MOB는 같은 ID 체계를 쓴다.** 같은 ID면 같은 화면의 두 플랫폼 버전이다.
문서는 화면당 하나로 쓰고, 두 플랫폼이 다르면 그 차이를 본문에 적는다. MOB에만 있는 것: `SP-01`.

프레임별 노드 ID 전체 목록은 `implementation-status.md` §3 의 각 행에 둔다.

### 같은 화면의 프레임이 여러 개일 때 — 상태 변형이다

`/{STATE}` 가 붙은 프레임은 같은 화면의 상태다. ID를 나누지 않고 문서도 **화면당 하나**로 쓴다.
변형은 「기능별 동작」과 「Figma 화면」에 상태로 기록한다.

> 상태 프레임이 있다는 건 그 상태를 구현해야 한다는 뜻이다. 「상태 커버리지」 대조에서
> 빠뜨리지 않는다 (`design-source-policy.md` §4 ④).

**`ONB-01/A~C` 는 예외적으로 글자가 상태 이름이 아니다.** 같은 글자가 플랫폼마다 다른 상태다.

| 글자 | WEB                 | MOB       |
| ---- | ------------------- | --------- |
| `/A` | 입력 중 (규칙 안내) | 빈 값     |
| `/B` | 유효                | 형식 오류 |
| `/C` | 중복                | 유효      |

다른 그룹처럼 상태 이름(`/EMPTY` `/INVALID` `/VALID` `/DUPLICATE`)으로 바꾸면 이 표가 필요 없어진다.

### 기준 화면 크기

| 플랫폼 | 크기      | 비고                                            |
| ------ | --------- | ----------------------------------------------- |
| WEB    | 1920×1080 | 목록·상세 화면은 세로가 더 길다 (`LRN-02` 1757) |
| MOB    | 360×740   | 스크롤 화면은 세로가 더 길다 (`MY-02` 2009)     |

`AOS` 라는 이름은 옛 섹션에서만 쓴다. 새 체계에서는 `MOB` 이다.

### 확인 필요

- **옛 `A.*`(티어 승급 · 레벨업 애니메이션 모달)는 아직 `SCREEN` 섹션에 없다** — 디자인·PM 컨펌 후
  옮긴다 (2026-09-11 사용자 확인). 옮겨지면 인벤토리에 그룹을 추가한다
- **구버전 `WEB`·`AOS` 섹션이 같은 페이지에 남아 있다** — 삭제 시점. 남아 있는 동안
  `get_metadata` 검색 결과에 옛 프레임이 섞여 나올 수 있다
- **`ONB-01/A~C` 의 글자가 플랫폼마다 다른 상태를 가리킨다** — 상태 이름으로 통일 여부
- `SP-01` 에 플랫폼 접미사가 없다 (MOB 전용) · `QUIZ-05` 의 상태 래퍼가 `-A`/`-B` (리프는 `/A`)
- `약관`·`개인정보` 화면의 시안을 찾지 못했다. `MIG-004`의 "시안 없음" 기록과 일치하지만,
  **없다고 단정하지는 않는다** — 아래 주의대로 metadata 검색은 누락될 수 있다

> ⚠️ **`get_metadata`로 "내용 없음"을 판정하지 않는다.** 섹션 전체를 조회하면 응답 크기 때문에
> 깊은 서브트리가 잘리고 `<frame ... />`로 닫혀 나온다. **self-closing은 "비었다"가 아니라
> "안 펼쳐졌다"** 다. `QUIZ`(11574×9996)는 단독 조회해도 잘린다. 내용 확인은 **`get_screenshot`**,
> 이름·ID 목록은 **`use_figma` 로 자식을 순회**해서 얻는다.
