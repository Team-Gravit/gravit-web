# 느린 원인과 해결법 (사람용)

측정 숫자가 나쁘게 나왔을 때 **어디를 보고, 무엇을 의심하고, 보통 어떻게 고치는지** 정리한 문서다.
측정 방법과 경계값은 `README.md`, AI에게 측정을 맡기는 절차는 `automated-runbook.md`.

> 여기 적힌 해결법은 **후보**다. 고치기 전에 원인을 측정으로 확인하고, 고친 뒤 같은 조건으로 다시 잰다.
> 원인을 모른 채 해결법부터 넣으면 효과가 없거나 다른 지표를 나쁘게 만든다.

## 0. 먼저 세 갈래로 나눈다

| 갈래 | 이렇게 보이면 | 고치는 곳 |
| --- | --- | --- |
| **공통 (앱 셸)** | 화면을 바꿔도 비슷한 시점에 비슷한 긴 작업이 있다 | 진입 JS, 초기화, 세션 복원, 글꼴, 레이아웃 셸 |
| **라우트 · 컴포넌트** | 특정 화면만 첫 렌더가 길거나, Layout이 크거나, 데이터가 많다 | 그 화면과 그 화면이 그리는 컴포넌트 |
| **번들 (트리 셰이킹 · 분할)** | 그 화면에서 안 쓰는 코드를 받아 실행한다 | import 방식, 라이브러리 선택, 청크 나누기 |

### 우리 앱에서 실제로 본 것 (REF-082, 2026-11-11, Windows PC)

- **공통**: 진입 JS 실행 약 0.5~0.6초 → 초기화 → 세션 복원(reissue)이 1.5초에야 시작 → 데이터는 2초쯤 다 왔는데
  첫 렌더 긴 작업이 2.6초쯤부터 0.5~1초. **네트워크보다 메인 스레드가 병목**이다. 그래서 데이터를 더 일찍 부르는 것만으로는 효과가 작다.
- **라우트**: 개념 노트는 LCP가 코드 블록이고 TBT 1.2초, CLS 0.29. `/main`은 첫 렌더에서 JS 0.47초 + Layout 0.41초.
- **번들**: 라우트 코드가 아주 작은 청크 여러 개로 쪼개져 있다. 맥미니에서 다시 잰 뒤 판단한다.

## 1. LCP가 이미지일 때

LCP 이미지까지 걸리는 시간은 네 토막이다. **어느 토막이 긴지 먼저 본다** (`waits.mjs` 또는 Network 패널).

| 토막 | 뜻 | 길면 |
| --- | --- | --- |
| 첫 응답 (TTFB) | HTML이 오기까지 | 서버 · CDN · 리다이렉트 |
| **발견 지연 (load delay)** | HTML은 왔는데 이미지 요청이 늦게 시작 | 이미지 주소가 JS 실행 뒤에야 알려진다 → 미리 알려 준다 |
| 다운로드 | 이미지 받는 시간 | 파일이 크다 → 줄인다 |
| 렌더 지연 | 다 받았는데 그려지지 않음 | 메인 스레드가 바쁘다 · 글꼴 · 숨김 상태 |

> SPA는 `index.html`에 `<img>`가 없어서 이미지 대부분이 **발견 지연**을 가진다. JS를 받고, 실행하고, 렌더해야 이미지 주소를 안다.
> 우리 `/main`은 LCP와 FCP가 같다(4.04초). 이미지는 이미 와 있고 **첫 렌더가 늦은 것**이라, 이미지 최적화로는 거의 안 줄어든다.

### 해결법

| 방법 | 언제 | 왜 | 주의 |
| --- | --- | --- | --- |
| `fetchPriority="high"` | 첫 화면의 가장 큰 이미지 **하나** | 브라우저는 이미지를 처음엔 낮은 우선순위로 받다가 화면 안인 걸 알면 올린다. 처음부터 높게 받게 한다 | 여러 장에 주면 서로 다퉈서 의미가 없다 |
| `loading="lazy"` **빼기** | LCP 이미지에 lazy가 붙어 있을 때 | lazy는 레이아웃을 계산한 뒤에야 요청한다. 첫 화면 이미지를 늦춘다 | 화면 아래쪽 이미지에는 lazy를 유지한다 |
| **preload** | 이미지 주소가 JS 실행 · 데이터 응답 · CSS 배경 뒤에야 알려질 때 | 주소를 미리 알려 발견 지연을 없앤다 | 미리 받는 만큼 다른 요청과 대역폭을 나눈다. 정말 첫 화면에 쓰는 것만 |
| 크기 줄이기 · `srcset`/`sizes` | 다운로드가 길 때 | 표시 크기보다 큰 이미지를 받지 않는다 | **포맷보다 크기가 먼저다.** 1200px를 webp로 바꾸는 것보다 표시 크기로 줄이는 효과가 크다 |
| webp · avif | 사진 · 큰 일러스트 | 같은 화질에 파일이 작다 | avif는 디코딩이 무겁다. 작은 아이콘엔 이득이 적다 |
| `decoding="async"` | 크고 화면 아래쪽인 이미지 | 디코딩(압축 풀기)을 다른 그리기와 묶지 않아, 큰 이미지 때문에 다른 내용이 늦게 그려지는 걸 막는다 | **LCP를 줄이는 방법이 아니다.** 브라우저가 이미 비동기로 하는 경우가 많아 효과가 작다. LCP 이미지는 기본값(`auto`)으로 둔다 |
| `width` · `height` 주기 | 모든 `<img>` | 받기 전부터 자리를 잡아 CLS를 막는다 | LCP 시간과는 상관없다 |

preload 쓰는 법:

```html
<!-- index.html: 빌드할 때 주소를 아는 이미지 -->
<link rel="preload" as="image" href="/hero.avif" fetchpriority="high" />
```

```tsx
// React 19: JS에서 주소를 아는 이미지 (다음 화면, 데이터에 딸린 이미지)
import { preload } from 'react-dom';
preload(heroImage, { as: 'image', fetchPriority: 'high' });
```

## 2. LCP가 글자 · 코드 블록일 때

글자는 받을 파일이 없으니 **그릴 수 있게 되는 순간**이 LCP다. 늦으면 대개 이 둘이다.

| 원인 | 확인 | 해결 |
| --- | --- | --- |
| 화면이 JS 렌더 뒤에야 생긴다 | CPU 감속을 끄고 다시 재서 크게 줄면 JS 탓 | §4 (JS 줄이기), §5 (렌더 줄이기) |
| 글꼴을 기다린다 | 글꼴 요청이 LCP 직전에 끝난다 | §3 |

**개념 노트의 코드 블록**처럼 구문 강조(syntax highlighting)가 붙은 글은, 강조 처리 자체가 무거워 렌더가 길어진다.
먼저 강조 없이 글만 보여 주고 나중에 강조하거나, 강조 결과를 미리 만들어 두는 방법이 있다. 어느 쪽이든 측정으로 효과를 확인한다.

## 3. 글꼴

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| 글자가 늦게 보인다 | 글꼴 파일이 크다 (Pretendard 638KB) | 필요한 글자만 나눠 받기(dynamic subset), 첫 화면 글꼴만 preload |
| 글자가 바뀌면서 줄이 밀린다 (CLS) | `font-display: swap`은 대체 글꼴로 먼저 그렸다가 바꾼다. 두 글꼴 폭이 다르면 밀린다 | 대체 글꼴의 `size-adjust` · `ascent-override`를 맞춘다, 또는 `optional` |
| 다른 서버 글꼴이 늦다 | 외부 CDN 글꼴(MBC1961GulimM 128KB)은 새 연결(DNS · TLS)이 필요하다 | `<link rel="preconnect">` 또는 우리 서버에서 직접 제공 |

## 4. JS가 크거나 실행이 길 때

### 4-1. 코드 나누기 (code splitting)

- 라우트별로 나누면 첫 화면에 필요 없는 화면 코드를 늦게 받는다.
- 반대로 **너무 잘게 나누면** 요청이 늘고, 앞 청크를 받아야 다음 청크를 아는 폭포(waterfall)가 생긴다.
  우리 앱은 작은 청크가 많다. 자주 같이 쓰이는 것은 묶는 게 나을 수 있다 (Vite `manualChunks`).
- 동적 import는 **실제로 무거운 기능**에만 쓴다 (`refactor-checklist.md`).

### 4-2. 트리 셰이킹이 안 되는 흔한 이유

트리 셰이킹은 빌드가 **안 쓰는 export를 빼는 것**이다. 아래면 빼지 못한다.

| 원인 | 예 | 해결 |
| --- | --- | --- |
| CommonJS 라이브러리 | `require`로 된 패키지는 무엇을 쓰는지 정적으로 알 수 없다 | ESM 버전을 쓴다 (`lodash` → `lodash-es`, 또는 필요한 함수만) |
| 부수 효과(side effect)가 있는 모듈 | import만 해도 실행되는 코드가 있으면 빌드가 지우지 못한다 | 패키지 `"sideEffects": false`, 모듈 최상단 실행 코드 없애기 |
| 배럴이 무거운 걸 다시 내보냄 | `index.ts`가 큰 모듈을 같이 export하고, 그 모듈에 부수 효과가 있다 | 무거운 것은 배럴에서 분리하거나 직접 경로로 |
| 전체 목록 import | 아이콘 전체 목록(`icon-catalog.generated.ts`)을 앱 코드에서 import하면 모든 아이콘이 첫 청크에 실린다 | 아이콘별 컴포넌트를 쓴다 (`CLAUDE.md` 함정 4) |
| 개발용 코드가 남음 | 목 데이터 · 디버그 도구가 운영 빌드에 들어감 | `import.meta.env.DEV` 조건 안으로 |

### 확인하는 법

1. **Coverage** — 그 화면에서 실행되지 않은 코드 비율 (`README.md` §4-1)
2. **번들 지도** — `apps/web`에서 `pnpm dlx vite-bundle-visualizer`. 누가 무엇을 끌고 왔는지
3. **`vite build` 출력** — 청크 크기 목록. 갑자기 커진 청크를 본다

## 5. 첫 렌더 · 메인 스레드가 길 때 (TBT · 렌더 지연)

`profile.mjs`가 긴 작업 안을 JS · Layout · Style로 나눠 준다.

| 큰 것 | 의심 | 해결 |
| --- | --- | --- |
| **JS (스크립트 실행)** | 첫 화면에 필요 없는 컴포넌트까지 렌더, 무거운 계산, 초기화가 몰림 | 첫 화면 밖 위젯은 나중에 렌더, 계산은 측정 후 `useMemo`, 긴 작업 쪼개기 |
| **Layout** | DOM이 크다, 화면 밖 요소까지 계산, 읽기 · 쓰기를 번갈아 해서 계산이 반복된다(layout thrashing) | 요소 수 줄이기, 긴 목록 가상화, 화면 밖 구역 `content-visibility: auto` |
| **Style** | 선택자가 복잡하거나 요소가 많아 스타일 재계산이 크다 | 요소 수 줄이기, 큰 범위 클래스 토글 피하기 |

> `memo` · `useMemo` · `useCallback`은 **측정 후에만** 넣는다 (`refactor-checklist.md`).

## 7. CLS (레이아웃이 밀림)

| 원인 | 해결 |
| --- | --- |
| **스켈레톤과 실제 내용 크기가 다르다** | 스켈레톤을 실제 내용과 같은 높이로, 또는 `min-height`로 자리 확보 |
| 이미지 · 영상 크기를 몰라서 받고 나서 밀림 | `width` · `height` 또는 `aspect-ratio` |
| 데이터가 오면 위쪽에 배너 · 알림이 끼어든다 | 자리를 미리 잡거나 아래쪽에 넣는다 |
| 글꼴 교체로 줄 폭이 바뀐다 | §3 |
| 애니메이션이 `top` · `height`를 바꾼다 | `transform`으로 움직인다 (레이아웃을 밀지 않는다) |

- 사용자가 누른 뒤 **500ms 안의 이동은 CLS 점수에서 빠진다.** 탭을 눌러 이동한 직후 스켈레톤이 바뀌는 건 점수엔 덜 잡혀도 눈에는 보인다.
  그래서 측정은 점수 값과 눈에 보이는 전체 값을 같이 적는다.
- **눈에 보이는 바뀜과 CLS는 다르다.** CLS는 바뀌기 전과 후에 **둘 다 있는 요소가 움직인 것**만 센다. 스켈레톤이 사라지고
  실제 내용이 그 자리에 들어오면서 아래에 밀릴 요소가 없으면(하단 탭은 고정이라 안 밀린다) 크기가 달라도 CLS는 0이다.
  우리 앱의 앱 안 이동이 그랬다 (REF-082, `evidence/2026-11-11_ref082/shots/nav/`). 이런 깜빡임은 성능 지표가 아니라
  스켈레톤 모양을 실제 내용과 맞추는 UI 문제로 다룬다.
- 스텁이 빨라 스켈레톤이 안 보이면 CLS가 0으로 나올 수 있다. 응답을 일부러 늦춰(`DELAY=600`) 한 번 더 잰다.

## 8. INP (반응이 느림)

구간별 의심 대상은 `README.md` §4 표에 있다. 해결 방향만 모은다.

| 긴 구간 | 해결 |
| --- | --- |
| Input delay | 그 순간 돌던 다른 긴 작업을 쪼갠다. 로딩 직후 렌더, 타이머, 큰 JSON 파싱 |
| Processing | 다시 그리는 범위를 좁힌다 (store selector, 상태를 쓰는 곳 가까이로), 급하지 않은 갱신은 `startTransition` |
| Presentation | DOM을 줄인다, 긴 목록 가상화, 무거운 CSS(그림자 · blur) 줄이기 |

글자 입력마다 느리면 입력값 갱신과 무거운 처리(검색 · 검사)를 분리하고, 무거운 쪽은 입력이 멈춘 뒤 한다(debounce).

## 9. CDN · 캐시 · 압축

**CDN(Content Delivery Network)** — 정적 파일(JS · CSS · 이미지 · 글꼴) 사본을 사용자와 가까운 서버 여러 곳에 두고 거기서 보내는 것.

| 언제 효과가 있나 | 왜 |
| --- | --- |
| 사용자와 원본 서버가 멀다 | 왕복 시간(지연)이 줄어 첫 응답 · 모든 파일 요청이 빨라진다 |
| 정적 파일이 많고 크다 | 원본 서버 부담이 줄고, 가까운 곳에서 캐시로 바로 준다 |
| 재방문이 많다 | 파일 이름에 해시가 있는 빌드 산출물은 `Cache-Control: immutable`로 오래 캐시한다 |
| 이미지를 기기마다 다른 크기로 줘야 한다 | 이미지 CDN은 요청할 때 크기 · 포맷을 바꿔 준다 |

- **localhost 측정으로는 CDN 효과를 볼 수 없다.** 실제 배포 주소에서, 또는 실사용자 측정(RUM)으로 본다.
- 지금 배포 환경이 CDN을 쓰는지, 캐시 헤더가 어떤지는 **확인 필요**다. REF-082 범위 밖이다.
- 압축: 텍스트 파일(JS · CSS · HTML · JSON)은 gzip 또는 brotli로 보내는지 응답 헤더 `content-encoding`으로 확인한다.

## 10. 하지 말 것

- 원인을 확인하기 전에 해결법부터 넣기
- 측정 조건이 다른 숫자끼리 비교하기 (기계 · MSW 여부 · CPU 감속 · 다른 앱 사용 여부)
- 이미지 여러 장에 `fetchPriority="high"` 주기, preload 남발
- 첫 화면 이미지에 `loading="lazy"`
- 측정 없이 `memo`부터 넣기
- dev 서버 숫자를 믿기 (원인 찾기용으로만)
