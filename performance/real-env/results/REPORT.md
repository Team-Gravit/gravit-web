### iPhone 실기기 확인 (`../README.md` §4)

**방법:** `../device/`. 앱 코드는 바꾸지 않았다. 빌드 결과 HTML에 측정 스크립트만 끼워 넣는 서버(`device-server.cjs`)를 쓰고, iPhone 14 Safari로 메인 · 학습 · 레슨을 열었다.

- 같은 Wi-Fi를 쓰고 네트워크 제한은 없다.
- 2회 했고 회당 화면마다 5번 열었다.
- UA는 `Version/26.6`이다. Safari 26이라 LCP를 실기기에서 직접 잴 수 있었다.

같은 순서를 맥 Chrome(390×844)에서도 돌렸다. 아래는 가운데 값(ms)이다.

- iPhone 값은 LCP를 함께 잰 2회차다. 1회차도 FCP 254~290 · 클릭 8~35로 비슷했다.
- 측정 스크립트에서 LCP를 늦게 더했기 때문에, Chrome 6배는 LCP 없이 쟀다.

| 기기 | 화면 | FCP | LCP | 클릭→다음 그리기 |
| --- | --- | --: | --: | --: |
| iPhone 14 Safari | main | 217 | 276 | 29 |
| | learning | 288 | 328 | 33 |
| | lesson | 271 | 336 | 10 |
| 맥 Chrome CPU 1.5배 | main | 76 | 68 | 4 |
| | learning | 76 | 76 | 3 |
| 맥 Chrome CPU 6배 | main | 180 | - | 18 |
| | learning | 196 | - | 12 |

**해석:**

- **iOS 프로필 1.5배는 iPhone보다 빠르다.** 6배로 늦춰도 iPhone이 더 느렸다. 보정 테스트(`../calibration/`)에서 맥 Safari DOM이 Chrome의 약 6배였던 것과 같은 방향이다. 엔진(WebKit) 차이가 크다.
- **판정은 바뀌지 않는다.** iPhone이 더 걸린 만큼(로딩 +0.2~0.3초, 클릭 +25~35ms)을 iOS 표에 더해 본다.
  - 가장 느린 LCP: 1.56 → 약 1.9초. 좋음 기준 2.5초 안이다.
  - 가장 느린 INP: 168 → 약 200ms. 경계에 닿는 화면은 2차에서도 흔들림으로 무효 처리된 `lesson-result` 1회뿐이고, 가운데 값은 48ms다.
- **이 확인의 한계:**
  - LTE에서는 재지 않았다. iPhone 개발자 설정의 Network Link Conditioner로 할 수 있다.
  - Safari 26의 INP는 사람이 직접 눌러야 잡혀서 재지 않았다. 클릭→다음 그리기는 그 근사값이다.
  - 앱 WebView도 같은 WebKit이지만 따로 재지는 않았다.

## 3. CLS 원인

원인 확인 스크립트는 `../scripts/cls-probe.mjs`, 출력은 `cls-probe/`. 레이아웃 이동마다 움직인 요소와 블록 높이 변화를 시간 순으로 적었다.

### ① 메인 (모바일 · iOS) — 0.35~0.36, 응답이 늦을 때만

**무엇이 움직이나:** 응답이 오면 맨 위 연속 학습 카드(`LearningStreak`)가 147px → 138px로 **9px 줄어든다**. 그 아래 「오늘의 미션 · 추천」 줄과 「이어서 학습하기」 카드가 7~9px 위로 올라온다.

**왜 점수가 큰가:** 7~9px 이동만으로는 0.01도 안 나와야 한다. 그런데 움직인 블록 안에 반짝임 중인 스켈레톤 `::after`(`animation: wave`)가 있고, Chrome이 이를 크게 움직인 것으로 함께 셌다.

- 동작 줄이기(`prefers-reduced-motion`)를 켜서 반짝임을 끄고 같은 조건으로 재면 **0.361 → 0.007**이다(2회 모두 같음).
- 출력: `cls-probe/main-mweb-delay600.txt`, `cls-probe/main-mweb-delay600-reduced.txt`

**사용자 영향:** 눈에 보이는 건 9px 정도의 작은 움찔임이다.

- 다만 Chrome 사용자(모바일 웹 · 데스크톱)의 실측 CLS에는 이 큰 값이 그대로 들어간다. 검색 순위 지표(CrUX)도 이 값을 쓴다.
- iOS Safari는 CLS를 내지 않는다.

**분류(§7):** 화면 고유(메인)와 공용 컴포넌트(`shared/ui/skeleton`의 wave)가 겹친 문제다.

- 같은 wave가 `inquiry`(0.038~0.045), 데스크톱 `main`(0.049)에도 작게 섞여 있다. 둘 다 좋음 범위다.

### ② 공지 목록 (데스크톱) — 0.410, 응답이 빨라도

**무엇이 움직이나:** 로딩 중에는 `NoticeList`가 아무것도 그리지 않는다(`isPending`이면 `return null`). 이때 Footer가 화면 가운데(y524)에 보인다. 목록이 그려지면 Footer가 **y1936으로 밀려 내려간다**.

- 반짝임과 관계없다. 동작 줄이기를 켜도 0.410이다.
- 출력: `cls-probe/notice-desktop.txt`

**왜 공지 상세는 괜찮은가:** 공지 상세(0.03)는 바깥 상자가 `min-h-svh`라 Footer가 처음부터 화면 아래에 있다. 공지 목록은 `min-h-full`이고, 이 높이가 화면을 채우지 못한다.

- 모바일은 Footer를 숨기므로(`hidden md:block`) 해당하지 않는다.

**분류(§7):** 화면 고유(공지 목록).

### ③ CLS가 못 잡는 흔들림 — 마이그래빗 · 리그 (사용자 질문으로 추가 확인, 11-19)

마이그래빗과 리그는 CLS가 0.000~0.007(좋음)인데 눈으로는 흔들린다. **수치가 틀린 게 아니라, CLS가 세지 않는 종류의 흔들림이다.**

CLS는 「이미 화면에 있던 요소의 시작 위치가 바뀐 것」만 센다. 다음 두 경우는 세지 않는다.

- 요소가 **새 요소로 바뀌는** 경우(스켈레톤 → 내용)
- 맨 아래 카드처럼 **아래에 밀릴 것이 없는** 상태에서 크기만 바뀌는 경우

확인 방법: mweb · 응답 0.6초 지연으로 0.4 · 0.7 · 0.9 · 1.2 · 1.5 · 1.9 · 2.4초에 화면을 찍었다(`cls-probe/film_*/`, `../scripts/filmstrip.mjs`).

## 5. 측정 중 있었던 일

- **멈춤 1회:** `mweb-inp-B`의 `incorrect` 4회차가 3분을 넘겨 멈췄다. 이어서 브라우저 탭이 열리지 않는 오류가 2회 났다. 7회차는 정상이었다.
  - 단계는 스스로 끝났고, 1차 재측정에서 7회를 다시 받았다(48ms · 안정).
- **데스크톱 공지 상세 INP 측정 실패(7회 모두):** 넓은 화면에서는 「뒤로 가기」가 숨는다(`md:hidden`).
  - 재측정 때 데스크톱만 같은 역할의 「목록으로」를 누르게 바꿨다(`DESKTOP_ACTIONS`). 결과는 48ms다.
- **흔들림 재측정:**
  - 본 측정: 흔들림 30건(거의 INP).
  - 1차: 13건 남음.
  - 2차: 6건 남아 `무효`로 적었다.
  - INP는 8ms 단위라 40~60ms대에서 한두 칸만 달라도 범위 30% 기준에 걸린다. 무효 6건도 7회 모두 200ms 이하라 판정(좋음)은 바뀌지 않는다.
- **로딩 흔들림:**
  - 데스크톱 `league`: 첫 회 464ms. 1차 재측정에서 안정(324ms).
  - 데스크톱 `main` 0.6초 지연: 첫 회 504ms. 1차 재측정에서 안정(292ms).
- **기계 부하:** 1분마다 상위 프로세스를 기록했다(`machine-load.txt`, `rerun1/machine-load.txt`).
  - 측정 Chrome 다음으로는 WindowServer 20% 안팎과 배경화면 확장 10% 안팎뿐이었다.
  - 측정 전 돌던 `mediaanalysisd`는 본 측정 중 상위 3개에 나오지 않았다.
- **iOS 프로필:** 처음에는 로그인 화면으로 튕겼다. 앱처럼 토큰을 `localStorage`에 넣는 처리(`nativeSession`)를 더한 뒤 정상으로 열렸다.
