# REF-054 — 이미지 로딩 최적화와 메인 히어로 배경 교체

## 배경 · 목표

배경·장식 이미지의 형식(PNG)·해상도(표시 크기의 1배 또는 4배 이상)·로딩 방식(CSS 배경, 우선순위 없음)이
제각각이라 첫 화면이 늦게 그려지는 화면이 있다. 이미지마다 **역할을 분류해 로딩 정책을 하나로 정하고**,
전후 LCP·전송량을 같은 조건에서 측정해 효과를 수치로 남긴다.
FIX-053 의 이관 항목 1(메인 히어로 배경 분리)을 새 정책의 첫 적용 대상으로 함께 처리한다.

## 범위

- `apps/web/src` 안의 래스터 이미지(webp · png) 전부와 그 렌더링 코드
- 메인 히어로 배경: CSS 그라데이션 + 장식 이미지로 교체 (FIX-053 항목 1 이관)
- 이미지 변환 방법(스크립트 또는 빌드 플러그인)과 측정 절차

## Out of Scope

- SVG 아이콘(`shared/ui/icon`) — 이미 인라인 SVG
- JS 번들 분할 · API 응답 속도 등 이미지 외 LCP 요인 — 측정에서 원인으로 나오면 새 작업으로 뽑는다
- native(Expo) 쪽 이미지

## 용어 정의

| 용어      | 정의                                                                   |
| --------- | ---------------------------------------------------------------------- |
| LCP 후보  | 첫 화면에서 가장 큰 콘텐츠 요소가 될 수 있는 이미지                    |
| 장식      | 정보가 없는 배경·일러스트. `alt=""` 대상                               |
| 표시 크기 | 화면에 그려지는 CSS 픽셀 크기. 원본은 그 2배(고해상도 화면)를 기준으로 |

### 공통 관찰

- `index.html` 에 preload 가 없고, 이미지는 모두 라우트 청크 안에서 import 된다 → **JS 를 받고 렌더링한 뒤에야 요청이 시작된다**
- CSS 배경은 그보다 늦다 (스타일 계산 후). 브라우저 우선순위 힌트도 줄 수 없다
- `loading="lazy"` 를 쓰는 곳이 없다
- 이미지 로딩 중 표시는 화면마다 다르다 (배경색만 있거나, 아무것도 없음)
- **LCP 수치는 아직 측정하지 않았다** — 아래 6번 절차로 기준값을 먼저 잰다

## 전략 (안) — 사용자 확정 전

### 1. 역할별 로딩 정책

| 역할               | 예                                                        | 정책                                                                    |
| ------------------ | --------------------------------------------------------- | ----------------------------------------------------------------------- |
| **LCP 후보**       | 메인 히어로 · 리그 배경 · 레슨 결과 배경 · 공용 우주 배경 | `<img>` 로 그린다 · `fetchPriority="high"` · `loading` 기본값(eager)    |
| 첫 화면 장식(작음) | 마스코트 · 프로필 배너 · 카드 배경                        | `<img>` 또는 CSS 배경 유지 · 우선순위 기본값                            |
| 화면 밖 · 목록     | 행성(챕터·유닛 카드) · 푸터 로고                          | `loading="lazy"` · `decoding="async"`                                   |
| 조건부(상태 화면)  | 퀴즈 로딩 마스코트                                        | 상태 진입 전에 미리 받는다(현행 `fetchPriority` 유지) · 해상도만 줄인다 |

> `fetchPriority="high"` 는 화면당 1개만 둔다. 여러 개면 서로 경쟁해 효과가 사라진다.
> 첫 화면 안에 들어오는 이미지에는 `loading="lazy"` 를 쓰지 않는다. 레이아웃이 끝날 때까지 요청이 미뤄져 LCP 가 늦어진다.

### 2. 형식과 해상도

- PNG 사진·일러스트 → **webp**. 아이콘성 이미지(구글 로고)는 SVG 가 있으면 SVG
- 원본은 **최대 표시 크기의 2배**로 맞춘다 — 4320px · 3840px 원본은 줄이고, 360px 1배 원본은 720px 로 키운다(새 원본 필요)
- 좁은·넓은 화면 이미지가 다르면 `<picture><source media>` 로 **한쪽만** 받는다 (리그 · 히어로는 이미 이 형태)

### 3. 첫 요청 앞당기기

- LCP 후보를 CSS 배경 → `<img>` 로 바꾼다 (공용 우주 배경)
- 그래도 늦으면 preload 를 건다. 해시 파일명이라 `index.html` 에 정적으로 못 쓴다 → 방법은 확인 필요

### 4. 로딩 중 표시

- **이미지 아래에 대표색·그라데이션을 깐다.** 이미지가 늦어도 글자는 즉시 읽히고, 도착하면 그 위에 덮인다
- 컨테이너 크기를 미리 고정해 레이아웃 이동(CLS)을 막는다 (`aspect-ratio` 또는 고정 높이)
- **LCP 후보에는 페이드인을 쓰지 않는다.** `opacity: 0` 동안은 그려진 것으로 치지 않아 LCP 가 오히려 늦어진다
- 스켈레톤은 데이터 영역 전용으로 두고 장식 이미지에는 쓰지 않는다

### 5. 메인 히어로 (FIX-053 항목 1)

- 배경 = CSS `linear-gradient(-57deg, #4721CA 3.59%, #17034E 95.08%)` (Figma `13750:50583`) + 장식 이미지
- 그라데이션이 곧 4번의 로딩 중 표시가 된다 — 장식이 늦어도 인사말이 바로 보인다
- 장식 이미지: 좁은 화면 `main-mobile-decoration.png`(720×532, 16-bit PNG 297KB, Codex 워크트리 `gravit-main-bg-asset`) → webp 변환. 넓은 화면 장식은 아직 없음

### 6. 측정

- `pnpm build` + `vite preview`, Lighthouse 모바일(느린 4G · CPU 4배) · 데스크톱 각 3회 중앙값
- 화면: 로그인 · 메인 · 리그 · 학습 챕터 · 레슨 결과 · 마이그래빗
- 기록: LCP 값 · **LCP 요소** · 이미지 전송량 · CLS
- 인증 화면은 MSW(`VITE_ENABLE_API_MOCKING=true`)로 같은 응답을 고정해 측정한다

### 확인 필요

1. **변환 방법** — ① 일회성 `sharp` 스크립트로 변환해 결과물만 커밋 ② `vite-imagetools` 로 빌드 시 변환(`?w=720&format=webp`, `srcset` 자동). ②는 원본을 그대로 두고 크기별 산출물을 만들 수 있지만 빌드 의존성이 하나 늘어난다
2. **avif 병행 여부** — `<picture>` 로 avif → webp 순서. 용량은 더 줄지만 이미지마다 파일이 두 벌
3. **preload 방식** — 라우트 `head` 의 `<link rel="preload">` / 라우트 `loader` 에서 미리 요청 / 쓰지 않음 (3번 효과를 측정한 뒤 결정)
4. **히어로 그라데이션 색** — 두 색 모두 `tokens.css` 에 없다. 히어로 전용 임의값으로 둘지, 토큰으로 승격할지 (`design-source-policy.md` §6)
5. **히어로 넓은 화면 장식** — 시안 에셋을 받을지, 넓은 화면은 그라데이션만 쓸지
6. **해상도를 키울 원본** — 리그 모바일 · 히어로 좁은 화면 1배 이미지의 2배 원본을 Figma 에서 다시 받을 수 있는지
7. **실행 이슈 분리** — 히어로는 외형이 바뀌는 변경이라 성능 변경과 한 이슈에 섞이면 측정 차이의 원인을 구분하기 어렵다. 한 작업 안에서 실행 이슈를 나누는 것을 권장 (`refactor-checklist.md` §2)
