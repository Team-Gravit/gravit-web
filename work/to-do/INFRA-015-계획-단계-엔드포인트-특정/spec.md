# INFRA-015 — 계획 단계에서 호출할 생성 API 함수를 특정하게 한다

## 배경 · 목표

`MIG-005` Issue 2의 계획은 구현 범위를 이렇게 적었다.

```
- `shared/api/refresh-token.ts` — 재발급 호출, single-flight 큐
```

"재발급 호출"이 **어떤 함수를 부르는 것인지**가 비어 있었다. 그 결과 구현 단계에서 legacy의
`publicApiClient.post('/api/v1/auth/reissue')` 형태를 그대로 따라가, 이미 생성돼 있던
`reissueToken`을 쓰지 않았다.

계획서에 `reissueToken`이라는 이름이 박혀 있었다면 구현에서 헷갈릴 여지가 없었다.
`INFRA-014`가 편집 직전에 막는 하드 차단이라면, 이 항목은 **애초에 헷갈리지 않게 하는 상류
조치**다. 둘은 대체 관계가 아니다.

## 범위

- `.claude/skills/ai-plan/SKILL.md` — 영향 분석 단계에 엔드포인트 특정 항목 추가
- `.claude/skills/refactor-planner/SKILL.md` — 이전 매핑에 같은 항목 추가
- `work/TEMPLATE/plan.md` — 해당 표에 열 또는 절 추가
- `api-convention.md` — 계획 단계 의무임을 한 줄로 참조

## Out of Scope

- 훅·lint 등 자동 검사 추가 — `INFRA-014`가 다룬다
- 이미 작성된 `work/to-do/`·`work/in-progress/`의 기존 `plan.md` 소급 수정
- orval 설정이나 생성 산출물 변경
- API가 없는 작업(순수 UI·문서)에 이 항목을 강제하는 것

## 용어 정의 (Ubiquitous Language)

| 용어            | 정의                                                                 |
| --------------- | -------------------------------------------------------------------- |
| 엔드포인트 특정 | 계획서에서 호출할 API를 경로가 아니라 **생성 함수 이름**으로 적는 것 |
| 상류 조치       | 구현 전 단계(기획·계획)에서 선택지를 좁혀 오류를 예방하는 방식       |

## 확정 명세 · 검증 기준

- [ ] **AC-1** (범위: 통합)
      Given 서버 API를 호출하는 작업의 계획을 `ai-plan`으로 만든다
      When `plan.md`의 영향 분석이 작성된다
      Then 호출할 각 엔드포인트에 대해 생성 함수 이름과 그 파일 경로가 적혀 있다

- [ ] **AC-2** (범위: 통합)
      Given 명세에 대응하는 생성 함수가 없는 엔드포인트가 있다
      When 계획이 작성된다
      Then 그 사실과 대응 방법(명세 확인·재생성·직접 구현 사유)이 `확인 필요`에 남는다

- [ ] **AC-3** (범위: 단위)
      Given 서버 API를 호출하지 않는 작업이다
      When 계획이 작성된다
      Then 이 항목은 `해당 없음`으로 표시되고 빈칸으로 남지 않는다

## 구현 전 확인

- `plan.md`의 어디에 둘 것인가. §2 영향 분석의 표에 열을 늘릴지, 별도 절을 만들지
- `ai-quick`에도 적용할지. 가벼운 요청은 계획 문서를 만들지 않으므로 다른 장치가 필요하다
- 생성 함수 이름을 찾는 표준 명령을 스킬에 예시로 넣을지
  (예: `rg -n "<경로>" apps/web/src/shared/api/generated/`)
