## 3. 구현 계획

### Issue 1 — 첫 화면 데이터 미리 요청

- [x] `[entities]` 첫 화면 쿼리 7개의 쿼리 옵션을 entity에서 내보낸다
  - 생성 옵션을 그대로 쓰는 5개(챕터 · 프로필 · 리그 요약 · 미션 · 추천 유닛)는 생성 `get…QueryOptions`를 도메인 이름으로 재노출한다
  - 404 → `null` 2개(주간 기록 · 최근 학습)는 `queryOptions({ queryKey, queryFn })`를 만들어 내보내고, 훅도 같은 옵션을 쓴다
  - `select`는 훅에만 둔다. 캐시에는 원본 응답이 들어가고 훅마다 변환한다
- [x] `[app]` `/learning` · `/main` 라우트에 `loader`를 추가한다. `context.queryClient.query(옵션).catch(noop)`을 부르고 기다리지 않는다 (`prefetchQuery`는 v6에서 제거 예정이라 쓰지 않는다)
  - 실패는 `.catch(noop)`으로 삼킨다. 실패한 쿼리는 위젯의 `useQuery`가 다시 받아 지금처럼 「다시 시도」 상태를 보인다
- [x] `[app]` 빌드 결과에서 `loader`가 화면 청크가 아닌 라우트 청크에 있는지 확인한다 (`spec.md` 확인 필요 3)
- [x] 테스트 — AC-1 ~ AC-5: `loader`를 실행하면 화면 컴포넌트 없이 요청이 출발하는지, 이어서 화면을 그려도 요청이 한 번인지, 404가 빈 상태로 이어지는지
- [x] 기존 테스트 — AC-6
- [x] 측정 — AC-7: 기준 빌드와 번갈아 5회. `/learning` LCP −0.75s, `/main` 모바일 −0.22s, FCP 모두 개선 (`records/2026-11-10-ref062-issue1.md`)
