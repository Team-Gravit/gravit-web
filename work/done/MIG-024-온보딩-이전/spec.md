# MIG-024 — 온보딩 화면 이전

## 배경 · 목표

`apps/web`의 `/onboarding`은 **빈 화면**이다.

```tsx
// app/routes/_protected.onboarding.tsx
component: () => null,
```

그런데 도달 경로는 이미 살아 있다. OAuth 콜백이 `isOnboarded`를 보고 분기한다.

```tsx
// pages/oauth-callback/ui/oauth-callback-page.tsx
navigate({ to: isOnboarded ? '/main' : '/onboarding', replace: true });
```

**즉 지금 신규 가입자는 로그인 직후 흰 화면에 갇힌다.** `FIX-022`로 콜백 404가 풀리면서
이 경로가 실제로 동작하게 되어 바로 드러난다.

## 범위

| 대상             | 내용                                                     |
| ---------------- | -------------------------------------------------------- |
| 온보딩 입력 화면 | 프로필 색 선택 + 닉네임 입력 + 제출                      |
| 완료 화면        | 「계정 생성 완료!」 + 마스코트 + 홈으로                  |
| 라우트           | `_protected.onboarding.tsx` 연결 + 완료 화면 라우트 추가 |

넓은 화면(WEB 시안)과 좁은 화면(AOS 시안) 양쪽을 구현한다. `MIG-018`과 같은 구조다.

## Out of Scope

- **인증·온보딩 게이트** — `MIG-005` Issue 4다. 완료자의 재진입 차단은 그쪽 범위
- **프로필 수정 화면** — legacy가 같은 `features/profile` 컴포넌트를 재사용하지만 별도 화면이다
- **닉네임 중복 안내 (WEB `O.4`)** — legacy에 없는 신규 기능이고, 서버가 `GLOBAL_4001`
  (포괄 검증 실패)만 주어 중복을 판정할 수 없다. **전용 에러 코드 확보 후 별도 작업**
  (§확인 필요 1)
- **제출 실패 알림** — legacy에 없다(F1). 토스트 체계가 아직 없어 지금 만들면 알림 설계를
  즉석에서 하게 된다. `FEAT-017`에서 로그인 실패와 함께 다룬다

## 동일성 확인 방법

- **라우트 진입** — `/onboarding`에서 아바타·화살표 2개·「닉네임 설정」·「다음」이 보이는지
- **입력 검증** — `ㄱ`(1자) → 안내 문구 / `!!!` → 빨강 / `그래빗`(3자) → 초록
- **버튼 활성** — 닉네임이 유효해지기 전까지 「다음」이 눌리지 않는지
- **색 순환** — 이전 화살표를 처음 상태에서 누르면 마지막 색으로 가는지
- **제출 값** — 첫 번째 색 선택 시 `profilePhotoNumber: 1`이 나가는지 (MSW로 요청 본문 확인)
- **완료 화면** — 제출 성공 후 「계정 생성 완료!」가 뜨고 「홈으로」가 `/main`인지
- **기존 테스트** — 없음 (legacy에 테스트가 없다)

## 확인 필요

0. **오류 문구를 플랫폼 간 통일한다 (사용자 지시 2026-09-10)** — 다만 두 문구는 같은 상태의
   다른 표현이 아니라 **서로 다른 조건**이다. 형식 오류는 클라이언트가 즉시 판정하고
   중복은 서버만 안다. 하나로 합치면 `!!!` 입력에 「이미 존재하는…」이 떠서 사실과 어긋난다.

   | 조건      | 문구                             | 근거              |
   | --------- | -------------------------------- | ----------------- |
   | 형식 오류 | 「사용할 수 없는 닉네임이에요.」 | legacy · AOS 시안 |
   | 중복      | 「이미 존재하는 닉네임이에요.」  | WEB 시안 · 신규   |

   **두 문구를 웹·모바일 양쪽에 똑같이 적용**하는 것으로 해석했다. 확정 대기.

1. **닉네임 중복은 어떻게 알 수 있나** — WEB `O.4`가 「이미 존재하는 닉네임이에요.」를
   요구하는데 **생성 API에 중복 검사 엔드포인트가 없다.** `POST /api/v1/users/onboarding`
   하나뿐이다. **legacy에도 구현이 없으므로 이전이 아니라 신규 기능이다.**

   **확인된 것(2026-09-10)** — 실패 시 서버 응답은 이렇다.

   ```json
   { "error": "GLOBAL_4001", "message": "유효성 검사 실패" }
   ```

   **이 코드로는 중복을 판정할 수 없다.** 어느 필드가 왜 틀렸는지 구분하지 않는 포괄 코드라
   닉네임 형식·`profilePhotoNumber` 범위 등 어떤 검증 실패에도 같은 값이 온다.

   "프론트가 형식을 이미 검사했으니 `GLOBAL_4001`이면 중복이다"라고 추론할 수는 있으나
   **계약이 아니라 짐작이다.** `api-convention.md` §6이 금지한다 — 서버가 다른 이유로 같은
   코드를 던지면 사용자에게 틀린 문구를 보여주게 된다.

   → **백엔드에 닉네임 중복 전용 에러 코드를 요청했다(2026-09-10).** 확보 전까지 이 상태는
   구현하지 않는다.

1-1. **형식 검증과 버튼 비활성은 이미 있다** — 확인 결과 legacy가 클라이언트에서 zod로
`2~8자 · ^[가-힣a-zA-Z0-9]+$`를 검사하고(C2·C3), 유효해지기 전까지 「다음」을 비활성한다(D2).
**생성 타입(`OnboardingRequest`)의 서버 제약과 정확히 일치한다.** 추가 구현이 필요 없다. 2. ~~**좁은 화면에 뒤로 가기가 두 개다**~~ → **해소(2026-09-10). 시안대로 간다** —
상단바 chevron과 하단 「이전」 버튼을 둘 다 둔다. 동작은 legacy의 A8을 따른다
(토큰 삭제 후 `/`로 이동). 넓은 화면에는 두지 않는다. 3. **넓은 화면의 빈 값 상태** — WEB에 해당 프레임이 없다. 사용자 지시(2026-09-10)로
**AOS `O.2`와 동일하게 안내 문구를 띄우되 텍스트 색만 AOS를 참고**하기로 했다.
구현 착수 시 Dev Mode에서 실제 색을 확인한다. 4. ~~**좁은 화면 상단바 제목이 「로그인」이다**~~ → **해소(2026-09-10).** 시안 오류가 아니다.
legacy가 `pageTitle="로그인"`으로 하드코딩돼 있고(A6) 시안이 현행을 그대로 반영한 것이다.
그대로 옮긴다. 5. **제출 실패 시 안내** — legacy에 없다(F1). `FEAT-017`(로그인 실패 알림)과 같은 성격이라
그쪽으로 묶을지 판단이 필요하다.

### 웹에서 브라우저 백을 누르면

넓은 화면 시안에는 뒤로 가기 버튼이 없지만 브라우저 백은 언제든 눌릴 수 있다.
**popstate를 가로채지 않는다.**

콜백이 `replace: true`로 이동하므로 `/onboarding`에서 백을 누르면 인가 페이지(외부)로 나간다.
그 뒤는 우리 제어 밖이지만, 인증·온보딩 게이트가 있으면 결국 제자리로 온다.

```
/onboarding 에서 백
  → 인가 페이지(외부) → 콜백 → 코드 소모됨 → / 로 이동
  → / 는 토큰이 있으니 /main
  → 게이트: isOnboarded false → /onboarding
```

**왜 가로채지 않나** — popstate 가로채기는 브라우저와 싸우는 방식이라 연타·제스처 백에서
새고, 네이티브 WebView에서 더 깨진다. 백을 "온보딩 취소"로 해석하는 것도 위험하다.
백은 "이전 화면"이지 "취소"가 아니라서, 실수로 누른 사용자가 로그아웃된다.

**전제** — 이 흐름의 마지막 단계는 `MIG-005` Issue 4의 게이트다. **이번 작업 범위가 아니다.**
게이트가 붙기 전까지는 백을 누르면 `/main`(아직 빈 화면)에 도착한다. 그 공백은 Issue 4가 메운다.

> 부수 관찰 — 게이트가 붙으면 `/` → `/main` → `/onboarding`으로 두 번 튄다. 동작은 맞지만
> `/`의 `beforeLoad`가 `isOnboarded`까지 보고 한 번에 보내도록 다듬을 여지가 있다. 지금은 아니다.

## 기술 결정 (ADR)

### ADR-1. 프로필 색·닉네임 조각을 어느 레이어에 두나

**맥락** — legacy의 `features/profile`을 온보딩 말고 **화면 3곳이 더 쓴다**(프로필 수정,
프로필 편집 모달, 사용자 편집). 즉 이 조각들은 온보딩 전용이 아니다.

| 안                                                 | FSD 적합성                         | 점진 이전성                         |
| -------------------------------------------------- | ---------------------------------- | ----------------------------------- |
| A. 전부 `features/user-onboarding`에               | ❌ 프로필 수정 이전 시 cross-slice | ❌ 그때 전부 다시 옮겨야 한다       |
| **B. 도메인은 `entities/user`, 동작은 `features`** | ✅                                 | ✅ 프로필 수정이 같은 entity를 쓴다 |
| C. 전부 `shared/ui`에                              | ❌ 도메인 단어가 shared에 들어간다 | —                                   |

**결정 — B.**

```
entities/user/model/profile-colors.ts   19색 팔레트 + 다음/이전 인덱스 순수 함수
entities/user/model/nickname.ts         규칙 상수 + validateNickname()
entities/user/ui/profile-avatar.tsx     색이 적용된 실루엣 (표시)
entities/user/ui/profile-color-picker.tsx  controlled — value + onChange 만 받는다
entities/user/ui/nickname-field.tsx     controlled — value + state + onChange

features/user-onboarding/model/…        디바운스 · 검증 상태 · canSubmit
features/user-onboarding/api/…          onboarding mutation
features/user-onboarding/ui/…           위 조각을 조립하고 제출을 붙인다
```

**Consequences** — entity UI가 5개로 늘어 처음엔 무겁게 느껴진다. 색 선택기를 controlled로
두면 순환 로직이 `model`로 빠져 호출부가 한 줄 늘어난다. 그 대가로 **프로필 수정 이전이
`entities/user`를 그대로 재사용**할 수 있다. `fsd-entities.md` §3의 "표시 전용, 동작은 prop"과 일치.

### ADR-2. 온보딩 껍데기를 공통화할까

**맥락** — legacy `EntryLayout`은 `MIG-018`에서 `SpaceBackground` + `PageHeader`로 쪼개졌다.
온보딩은 거기에 **하단 버튼 영역**이 더 붙는다.

| 안                                         | 판단                                                    |
| ------------------------------------------ | ------------------------------------------------------- |
| A. `shared/ui/layout`에 `EntryLayout` 신설 | ❌ 로그인이 이미 조립 방식으로 갔다. 두 방식이 공존한다 |
| **B. 페이지가 직접 조립한다**              | ✅ 로그인과 같은 방식                                   |
| C. 로그인·온보딩 공통 껍데기 추출          | ❌ 2번 등장이다. 3번째(리그)에 판단한다                 |

**결정 — B.** `refactor-checklist.md`의 "2번 등장은 인라인, 3번째에 추출"을 따른다.
`SpaceBackground`의 주석이 이미 "로그인·온보딩·리그가 함께 쓴다"고 밝히고 있어 배경면은 재사용한다.

**Consequences** — 온보딩과 로그인이 비슷한 조립 코드를 각자 갖는다. 리그 화면을 이전할 때
세 번째가 되므로 그때 추출을 판단한다.

### ADR-3. 완료 화면을 별도 라우트로 둘까

**맥락** — legacy는 `/success` 별도 라우트다(A3). 한 라우트 안 단계 상태로 만들 수도 있다.

**결정 — 별도 라우트를 유지한다.** 동작 계약 `C-4`가 "완료 화면을 거쳐 `/main`으로 간다"이고,
단계 상태로 바꾸면 새로고침 시 완료 화면이 사라져 계약이 깨진다. 경로는 `_protected` 아래
`/onboarding/success`로 둔다.

**Consequences** — 라우트가 하나 늘고 **라우트 트리 재생성이 필요**하다. 완료 화면에 직접
진입하는 경우의 처리(A4)는 그대로 옮긴다.

### ADR-4. 화살표 아이콘을 새로 가져올까

> **2026-09-11 결정 변경 — 가져오는 것으로 바꿨다.** 구현 중 대조해 보니 생성 아이콘
> `chevron-left`·`chevron-right` 가 시안의 화살표와 굵기·형태가 달랐다. `arrow-left.svg`·
> `arrow-right.svg` 를 `entities/user/ui/assets/` 로 반입한다. 아래는 원래 결정이다.

**결정 — 가져오지 않는다.** legacy는 `left-gray-arrow.svg` 등 전용 SVG를 쓰지만
`apps/web`의 생성 아이콘 맵에 `chevron-left`·`chevron-right`가 이미 있다. 색은 `currentColor`로
맞춘다. 마스코트 2종과 프로필 실루엣만 에셋으로 가져온다.
