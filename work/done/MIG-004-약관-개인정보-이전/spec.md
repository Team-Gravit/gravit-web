# MIG-004 — 서비스 이용약관 · 개인정보 처리방침 화면 이전

## 배경 · 목표

`apps/legacy-web`의 정적 법적 고지 화면 2개를 `apps/web`으로 이전한다.

**이 작업의 진짜 목적은 화면 2개가 아니라 이전 파이프라인을 한 바퀴 검증하는 것이다.**
파이프라인 스킬(`refactor-baseline` / `design-diff` / `ai-plan` / `ai-orchestrate` / `ai-validate`)이
아직 없으므로, 손으로 한 바퀴 돌려보고 **거기서 나온 실제 절차로 스킬을 작성한다.**

### 왜 이 화면이 첫 대상이었나

아래 표는 작업 당시 사용한 5문항 평가 기록이다. 현재 구조 변경 착수 판단은 점수제가 아니라
`.claude/rules/refactor-checklist.md`의 필수 게이트 6개를 사용한다.

| #   | 질문            | 답      | 근거                                                                 |
| --- | --------------- | ------- | -------------------------------------------------------------------- |
| 1   | 반복 비용       | Yes     | default export · PascalCase 폴더 · 하드코딩 px — 전형적인 비표준 3종 |
| 2   | 확장 막힘       | Yes     | 이전 파이프라인이 검증돼야 나머지 36개 화면을 시작할 수 있다         |
| 3   | **검증 가능**   | **Yes** | 정적 텍스트라 동작 동일성을 눈으로 확인 가능                         |
| 4   | 범위 제한       | Yes     | 파일 3개 + import 4곳                                                |
| 5   | **리스크 격리** | **Yes** | 인증 게이트 밖. 토큰·orval·라우트 트리 어디에도 안 걸린다            |

> **참고: `login`을 첫 대상으로 검토했다가 보류했다.** 파일 수는 작지만(약 10개)
> `_authenticated` 경로 다수가 게이트에 의존하고 토큰 갱신·OAuth 콜백이 붙어 있다. 당시
> 평가에서 검증·범위·리스크 근거가 부족했다. `MIG-`로는 나중에 다루되,
> **`refactor-baseline`만 먼저 떠두는 것**은 별도로 검토한다.

## 범위

| 대상 | 현재 (legacy)                                     | 목표 (apps/web)                                             |
| ---- | ------------------------------------------------- | ----------------------------------------------------------- |
| 화면 | `pages/terms.tsx` (255줄)                         | `pages/terms/` + `app/routes/terms.tsx`                     |
| 화면 | `pages/privacy.tsx` (246줄)                       | `pages/privacy/` + `app/routes/privacy.tsx`                 |
| 위젯 | `widgets/Footer/Footer.tsx` (47줄)                | `widgets/footer/`                                           |
| 에셋 | `logo-gr.svg` · `logo.svg` · `logo-appcenter.png` | `shared/ui/logo/` (svg) · `widgets/footer/ui/assets/` (png) |

**딸려오는 구조 위반 3종** (`legacy-web-policy.md`의 알려진 패턴):

- `widgets/Footer/` — 폴더·파일 둘 다 PascalCase → `widgets/footer/footer.tsx`
- `export default function Footer()` → named export + `index.ts` 배럴
- Footer import 4곳 갱신 (`terms` · `privacy` · `mains` · `__index`) — 이 중 이번 이전 대상은 2곳,
  나머지 2곳은 legacy에 남는다 (**아래 `확인 필요` 참고**)

## Out of Scope

- 약관·처리방침 **본문 내용 변경** (법적 문구다. 오탈자도 임의로 고치지 않는다)
- `mains.tsx` · `__index.tsx` 이전 (Footer를 함께 쓰지만 이번 범위가 아니다)
- Footer의 디자인 개선 (하드코딩 px를 토큰으로 바꾸는 것 포함 — 시안 확정 후)
- 헤더를 공용 위젯으로 추출 (두 화면이 같은 헤더를 쓰지만 3번째 등장 전까지 인라인)
- `tokens.css`의 레거시 호환 블록 정리

### 토큰 호환성 확인 (이전 시 색이 달라지는지)

| 클래스                       | legacy                      | apps/web                                  | 판정    |
| ---------------------------- | --------------------------- | ----------------------------------------- | ------- |
| `bg-gray-700`                | `--color-gray-700: #5a5a5a` | **동일하게 `#5a5a5a`**                    | ✅ 동일 |
| `text-2xl` / `text-xl`       | Tailwind 기본               | 기본 살아 있음 (`--text-*: initial` 없음) | ✅ 동일 |
| `--header-height`            | 74px                        | **74px 정의됨**                           | ✅ 동일 |
| `bg-white` / `text-white/80` | Tailwind 기본               | 기본 살아 있음                            | ✅ 동일 |

> **두 앱 모두 `--color-gray-*: initial` 후 `gray-700`만 개별 재정의**해 두었다.
> 당시 `apps/web/src/app/styles/tokens.css`에는 이전 화면을 위한 레거시 호환 토큰 블록이 있었다.
> 현재 토큰 상태와 제거 계획은 `docs/design-system/README.md`를 정본으로 확인한다.
> → 이번 이전은 **시각적 회귀 위험이 거의 없다.**

**시안 없음.** 법적 고지 화면이라 Figma 디자인이 존재하지 않는다 (사용자 확인, 2026-08-31).

→ 이번 작업은 **동작·외형을 그대로 옮기는 것**만 한다. 개선 판단을 하지 않는다.
→ `design-diff` 스킬의 "시안 없음" 경로를 처음 밟는 사례이기도 하다.
