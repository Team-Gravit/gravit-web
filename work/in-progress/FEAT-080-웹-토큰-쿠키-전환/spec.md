# FEAT-080 — 웹 리프레시 토큰 쿠키 전환과 로그인 state 검증

## 배경 · 목표

웹은 accessToken과 14일짜리 refreshToken을 `localStorage`에 둔다. 페이지에 XSS가 생기면 두 토큰을 읽어 가서
오래 쓸 수 있다. 서버 #597이 웹 refreshToken을 HttpOnly 쿠키로 옮기고, 로그인 요청에 1회용 `state`를 필수로 했다.

웹을 이 계약에 맞춘다. 토큰을 오래 훔쳐 가는 경로를 없애고 로그인 CSRF를 막는다. 서버 운영 배포에 #597이 함께
나가므로 이 작업이 끝나야 웹 출시와 앱 심사를 진행할 수 있다.

**막지 못하는 것.** XSS가 살아 있는 동안 페이지 안에서 API를 호출하거나 `/reissue`로 새 accessToken을 받는 것은
막지 못한다. 이 작업은 피해 기간을 줄이며, XSS 자체를 없애지 않는다.

## 범위

| 대상                   | 변경                                                         |
| ---------------------- | ------------------------------------------------------------ |
| `entities/auth`        | 웹은 accessToken을 메모리에만 저장, 부팅 시 재발급으로 복원  |
| `shared/api`           | 쿠키 전송, 쿠키 기반 재발급                                  |
| `features/auth-login`  | `state` 저장과 비교, Apple 팝업 `state`, 응답 타입 변경 반영 |
| `features/auth-logout` | 로그아웃 API 호출                                            |
| `pages/oauth-callback` | 콜백 `state` 비교                                            |
| `app/routes`           | 인증 판단 전에 복원 완료를 기다림                            |

**앱(WebView)은 저장 방식을 바꾸지 않는다.** 앱 로그인 API는 계속 본문으로 refreshToken을 주고, 앱을 다시 켜면
그 값이 있어야 세션을 복원할 수 있다. 앱에서 달라지는 것은 로그아웃 API 호출뿐이다. `apps/native`는 수정하지 않는다.

## Out of Scope

- 앱 토큰을 Keychain으로 옮기는 작업. 그전까지 앱 웹뷰의 `localStorage`에는 토큰이 남는다
- CSP 추가, `calendar-heatmap-tooltip.utils.ts`의 `innerHTML` 제거
- 서버 변경: `/reissue` · `/logout` Origin 검사, refreshToken 교체
- 탭 사이 로그아웃 동기화. 다른 탭은 현재처럼 accessToken이 만료될 때 끝난다
- `dest` 제거. 로컬 프록시가 Origin을 지우므로 `dest`가 계속 필요하다
- OpenAPI 생성물 재생성. 사용자가 직접 한다

## 용어 정의

| 용어       | 정의                                                                   |
| ---------- | ---------------------------------------------------------------------- |
| 쿠키       | 서버가 발급하는 `refreshToken` HttpOnly 쿠키. `Path=/api/v1/auth`      |
| 세션 힌트  | 이 브라우저가 로그인했었다는 표시. 토큰이 아니며 `localStorage`에 둔다 |
| 대기 state | 로그인 시작 때 서버에서 받아 저장한 값. 콜백의 `state`와 비교한다      |
| 웹 경로    | `isNativeApp()`이 false인 환경                                         |
| 앱 경로    | `isNativeApp()`이 true인 환경                                          |

## 기술 결정 (ADR)

### ADR-1. 웹 accessToken — 메모리에만 저장

| 안                              | 판단                                                              |
| ------------------------------- | ----------------------------------------------------------------- |
| **메모리 + 부팅 재발급 (선택)** | 저장소에서 바로 읽을 토큰이 없다. 새로고침마다 재발급 요청이 든다 |
| `localStorage` 유지             | 변경이 가장 적지만 XSS가 저장소에서 바로 읽을 수 있다             |
| accessToken도 HttpOnly 쿠키     | 서버가 전 API의 인증 방식을 바꿔야 하고 CSRF 범위가 넓어진다      |

- (+) 저장소에 토큰이 남지 않는다
- (−) 부팅이 비동기가 되어 첫 화면이 늦어질 수 있다. 측정한다

### ADR-2. 복원 시도 조건 — 세션 힌트가 있을 때만

JS는 HttpOnly 쿠키의 존재를 알 수 없다. 힌트 없이 항상 재발급을 부르면 처음 온 방문자도 로그인 화면 전에 요청을
기다리고 401을 받는다.

| 안                   | 판단                                                       |
| -------------------- | ---------------------------------------------------------- |
| **세션 힌트 (선택)** | 비로그인 첫 방문은 요청이 없다. 값 하나를 더 관리해야 한다 |
| 항상 재발급          | 단순하지만 첫 방문 로그인 화면이 느려지고 401이 쌓인다     |

### ADR-3. 로그인 CSRF — 웹에서 `state`를 비교

서버는 `state`가 Redis에 있는지만 확인하고, 이 브라우저가 시작한 로그인인지는 모른다. 공격자가 자기 계정으로
받은 `code`와 `state`를 링크로 보내면 서버 검증을 통과한다. 그래서 웹이 저장한 값과 콜백 값을 비교한다.

| 안                                | 판단                                                             |
| --------------------------------- | ---------------------------------------------------------------- |
| **`localStorage` + 만료 (선택)**  | 모바일에서 제공자 앱을 거쳐 새 탭으로 돌아와도 동작한다          |
| `sessionStorage`                  | 탭이 격리되지만 새 탭으로 돌아오면 정상 로그인도 실패한다        |
| 서버가 state 쿠키로 브라우저 연결 | 가장 견고하지만 서버 변경이 필요하다. 필요하면 후속으로 제안한다 |

- (−) 두 탭에서 동시에 로그인을 시작하면 먼저 시작한 쪽이 실패할 수 있다. 다시 시도하면 된다

### ADR-4. 기존 사용자 — 한 번 다시 로그인

`/reissue`는 쿠키를 새로 발급하지 않아 기존 `localStorage` 토큰으로는 쿠키 방식으로 넘어갈 수 없다. 웹 경로는 부팅
시 옛 토큰을 지운다. 사용자는 배포 후 한 번 다시 로그인한다.

### ADR-5. 로그아웃 실패 — 이 기기의 세션은 그대로 끝낸다

세션과 힌트를 먼저 지우고 로그아웃 API를 호출한다. API가 실패해도 힌트가 없어 새로고침으로 세션이 살아나지 않는다.

- (−) 호출이 실패하면 쿠키와 서버 토큰은 만료까지 남는다. 실패를 로그로 남기고 재시도하지 않는다

## 확인 필요

1. ~~**refreshToken은 사용자당 1개다.**~~ **해결 (2026-11-08).** 서버가 refreshToken을 기기 칸(WEB · ANDROID ·
   IOS)별로 저장한다. 칸은 토큰의 `client` 클레임으로 정해지고, 클레임은 어느 로그인 API로 들어왔는지로 정해진다.
   웹 로그인은 WEB 칸만 덮어써서 앱 세션을 끊지 않는다. 재발급 · 로그아웃도 토큰에서 칸을 찾으므로 이 작업의 코드는
   달라지지 않는다. iOS 앱이 iOS 경로를 쓰도록 바꾼 것은 NAT-025 5회차(#393)다
2. **운영 API 주소.** 개발과 dev 검증은 dev 서버로 한다. 운영 서버에 dev 변경이 아직 반영되지 않았으므로, 운영 배포 전에
   Vercel의 `VITE_API_BASE_URL`이 웹과 같은 사이트인지 확인한다
