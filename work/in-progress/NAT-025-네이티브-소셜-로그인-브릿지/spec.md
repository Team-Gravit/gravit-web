# NAT-025 — 네이티브 SDK 소셜 로그인과 웹↔네이티브 브릿지

## 배경 · 목표

앱(`apps/native`)은 `apps/web`을 WebView 하나로 연다. 로그인 화면(`ACC-01`)도 그대로 나오지만
소셜 버튼을 누르면 웹 흐름대로 **WebView 안에서** 외부 인가 페이지로 이동한다. Google은 embedded
WebView의 OAuth를 차단하고(`disallowed_useragent`), **네이버도 인앱 WebView 로그인을 차단한다**
(2026-09-11 iOS dev client 실측 — 인가 URL 진입 직후 `nid.naver.com/login/ext/error.inapp?inapp_view=true&disp_stat=208`로
이동). 세 provider 중 앱 안 웹 로그인이 되는 건 카카오뿐이며, 카카오도 앱이 깔려 있으면 SDK 로그인이
브라우저 로그인보다 빠르다. 앱에서는 각 사 **네이티브 SDK로 토큰을 받아** 백엔드의 앱 엔드포인트로
로그인한다. iOS는 `/api/v1/oauth/ios…`, Android는 `/api/v1/oauth/android…`를 쓴다 (2026-11-07 분리).

이를 위해 웹과 네이티브가 처음으로 **요청–응답을 주고받는 브릿지**가 필요하다. 로그인은 첫
사용처일 뿐이고, 이후 토큰 보관(`MIG-005` ADR-4의 `AUTH_SIGNED_IN` 등)·FCM 토큰 등록
(`fcm-token-api`, `platform: ANDROID`)·딥링크가 같은 통로를 탄다. 그래서 브릿지는 **로그인만
위해 만들지 않고**, 메시지 종류를 추가할 때 전송 계층을 다시 건드리지 않는 구조로 만든다.

**범위 재정의 (2026-11-04)** — 처음에는 iOS 3개 provider만 다뤘다. 이제 **iOS와 Android 앱 모두**
Google·카카오·네이버 SDK 로그인을 넣고, **Apple 로그인은 웹·iOS·Android 전체에 제공**한다. iOS도
우선 기존 Android 엔드포인트를 쓰고, 동작에 차이가 없으면 서버가 하나로 통합한다. (2026-11-07 개정 —
기기별 리프레시 토큰 칸이 생겨 서버가 iOS 경로를 따로 만들었다. 확인 필요 1) 1차·2차 코드는
당시 stash에서 최신 `develop` 위로 복원했다. 이 범위는 2026-11-04 사용자가 확정했다.

## Out of Scope

- **토큰을 네이티브에 보관·복원하는 것** (`MIG-005` ADR-4 `AUTH_SIGNED_IN`/`AUTH_TOKEN`). 브릿지가 이 메시지를 실을 수 있게 설계하되 구현은 `MIG-005`
- **로그인 실패 사유 표시** — `FEAT-017`. 이 작업은 실패를 **구분해 반환**하는 것까지이며, 사용자에게 무엇을 보여줄지는 거기서 정한다
- **FCM · 딥링크 · 뒤로 가기 등 다른 브릿지 메시지** — 계약의 확장 지점만 남긴다
- **탈퇴 계정 복구(`/restore`) 화면** — 기존 콜백과 같은 `USER_423` → `/restore` 이동만 재사용
- **스토어 출시 설정** (서명·심사 제출 등 배포 설정). SDK 초기화와 로그인에 필요한 앱 설정은 범위
- **웹 토큰의 httpOnly 쿠키 전환** — 이번 출시와 분리한다. 별도 작업으로 다룬다 (확인 필요 7)
- **`originWhitelist` 좁히기와 WebView 이동 제한** — Android의 Apple 방식이 정해진 뒤 별도 작업으로 다룬다 (ADR-6)
- **네이티브 전용 로그인 화면** — `ACC-01` 웹 화면을 그대로 쓴다. 로그인 경로가 둘로 갈리지 않고 화면 수정이 앱 배포 없이 반영된다. 첫 화면 표시가 느리면 네이티브 스플래시로 먼저 대응한다
- **웹 브라우저(앱 밖)의 로그인 동작 변경** — 브릿지가 없으면 지금 흐름 그대로

## 용어 정의 (Ubiquitous Language)

| 용어                          | 정의                                                                                                                                                                                                    |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **브릿지 (bridge)**           | WebView 안의 웹과 네이티브 셸이 `postMessage`로 JSON 문자열을 주고받는 통로 전체. 전송 계층 + 메시지 계약                                                                                               |
| **요청 (request)**            | 웹→네이티브. `id`로 응답과 짝지어지며 **정확히 하나의 응답**을 기대한다                                                                                                                                 |
| **응답 (response)**           | 네이티브→웹. 요청의 `id`를 되돌려 주며 `ok: true`(결과) 또는 `ok: false`(에러) 둘 중 하나                                                                                                               |
| **이벤트 (event)**            | 네이티브→웹. 요청 없이 네이티브가 먼저 보내는 알림 (예: 토큰 복원, 뒤로 가기). `id`가 없다                                                                                                              |
| **봉투 (envelope)**           | 요청·응답·이벤트가 공통으로 갖는 바깥 구조. payload는 메시지 종류마다 다르다                                                                                                                            |
| **핸들러 (handler)**          | 네이티브에서 요청 종류 하나를 처리하는 비동기 함수. 값을 반환하면 성공 응답, 던지면 실패 응답                                                                                                           |
| **브릿지 에러 (BridgeError)** | 웹이 받는 실패의 단일 형태. `code`로 원인을 구분한다 (`TIMEOUT` · `CANCELLED` · `UNAVAILABLE` · `UNSUPPORTED` · `NATIVE_ERROR`)                                                                         |
| **앱 환경**                   | `navigator.userAgent`에 `GravitNative/`가 있는 WebView. 브릿지는 여기서만 동작한다                                                                                                                      |
| **SDK 토큰**                  | 네이티브 SDK가 발급한 provider 토큰. google·kakao는 `idToken`, naver는 `accessToken`. Apple은 서버 API가 정해지면 추가한다                                                                              |
| **앱 엔드포인트**             | 앱 SDK 토큰을 교환하는 경로. 기기 종류는 `APP_INFO`로 묻는다. iOS: `POST /api/v1/oauth/ios?provider=` · `/ios/naver` · `/ios/apple`. Android: `POST /api/v1/oauth/android?provider=` · `/android/naver` |
| **기기 칸**                   | 서버가 리프레시 토큰을 저장하는 WEB · ANDROID · IOS 3칸. 로그인한 경로로 정해지고 토큰의 `client` 클레임에 실린다. 같은 칸에 다시 로그인하면 이전 로그인이 끊긴다                                       |
| **취소 (cancel)**             | 사용자가 SDK 로그인 화면을 닫거나 동의를 거부해 토큰 없이 돌아온 것. 실패이지만 알림 대상이 아니다                                                                                                      |

## 경계 조건과 실패 동작

인터뷰 항목 4·5의 결정이다. 사용자에게 무엇을 보여줄지는 `FEAT-017`이 정하므로, 여기서는
**어떤 결과가 어떤 코드로 웹에 도달하는지**만 고정한다.

| 상황                                                   | 웹이 받는 것                         | 웹의 동작                                                                                                                     |
| ------------------------------------------------------ | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| 앱 환경이 아님 (브라우저)                              | 브릿지를 부르지 않음                 | 기존 웹 리다이렉트 흐름 그대로                                                                                                |
| 앱 환경인데 네이티브가 그 요청 종류를 모름 (구버전 앱) | `BridgeError(UNSUPPORTED)`           | 버튼 잠금 해제 후 토스트로 안내. 웹 인가 페이지로 폴백하지 않는다 (ADR-5)                                                     |
| 사용자가 SDK 화면을 닫음 · 동의 거부                   | `BridgeError(CANCELLED)`             | 버튼 잠금 해제. 알림 없음                                                                                                     |
| SDK 실패 (네트워크 · 설정 오류 · 앱 미설치 폴백 실패)  | `BridgeError(NATIVE_ERROR, message)` | 버튼 잠금 해제. 표시는 `FEAT-017`                                                                                             |
| 네이티브가 응답을 보내지 않음                          | `BridgeError(TIMEOUT)`               | 버튼 잠금 해제. 표시는 `FEAT-017`                                                                                             |
| 앱 엔드포인트가 4xx/5xx                                | axios 에러 (기존 콜백과 같은 형태)   | `USER_423`이면 `/restore`, 아니면 기존 콜백과 동일                                                                            |
| 같은 버튼 연타                                         | —                                    | `FIX-019`의 pending 잠금이 그대로 막는다. 브릿지는 요청마다 새 `id`를 쓰므로 같은 종류의 요청이 겹쳐도 응답이 뒤바뀌지 않는다 |
| 응답 JSON이 깨짐 · 모르는 `id`                         | 무시하고 로그                        | 해당 요청은 결국 `TIMEOUT`                                                                                                    |

**타임아웃 기본값** — 요청마다 지정할 수 있고, 지정하지 않으면 브릿지 기본값을 쓴다.
로그인은 사용자가 SDK 화면에서 오래 머무를 수 있어 기본값보다 길게 준다. 취소는 네이티브가 즉시
알려 주므로 타임아웃은 "네이티브가 죽은" 경우의 안전장치다.

| 값                   | 제안  | 근거                                     |
| -------------------- | ----- | ---------------------------------------- |
| 브릿지 기본 타임아웃 | 10초  | 단순 조회성 요청의 상한. 확인 필요 없음  |
| 로그인 요청 타임아웃 | 120초 | SDK 동의 화면 체류 시간. **확인 필요 3** |

  - nonce 발급 주체. 서버 발급 일회용 값을 제안한다 → **해당 없음**: iOS API가 nonce를 받지 않는다
  - 탈퇴 시 Apple 토큰 철회 처리
  - 이메일이 같은 기존 계정과의 병합 정책, 실패 응답 형식
- [ ] **6. Android의 Apple 로그인 방식.** 보류한다 (2026-11-06 사용자 결정). Expo Android를 배포하지 않아 지금 필요 없다. 앱 핸들러는 Android에서 `UNSUPPORTED`로 답한다. 배포하게 되면 시스템 브라우저로 인가한 뒤 앱으로 복귀하는 흐름을 서버와 정한다
- [x] **7. 웹 토큰의 httpOnly 쿠키 전환을 이번 출시와 분리할지.** → **분리한다.** (2026-11-04 사용자 확정) 나중에 진행할 때는 서버 로그아웃 API가 필요하고, 앱도 쿠키를 쓸지(WebView 유지 여부 선검증) 웹만 쿠키를 쓸지 정해야 한다
- [ ] **8. Apple 버튼 근거.**
  - [x] **형태** → 기존 소셜 로그인 버튼과 같은 형태·아이콘 크기를 쓴다. 시안은 모바일만 있고 넓은 화면은 시안 없음 (2026-11-04 사용자 확인). 넓은 화면은 버튼의 `wide` 규격을 그대로 쓴다
  - [x] **문구** → **「Apple로 시작하기」로 간다.** 심사에서 지적받으면 고친다 (2026-11-04 사용자 확정). Apple HIG는 직접 만든 버튼의 제목을 "Use only _Sign in with Apple_, _Sign up with Apple_, or _Continue with Apple_"로 제한하고 App Review가 이를 평가한다고 적는다. 번역 문구 규칙은 없고, 이 문구는 셋의 직역이 아니라 위험을 안고 간다. 지적받으면 「Apple로 계속하기」를 첫 후보로 본다
  - [ ] **로고** — HIG는 로고 파일 높이를 버튼 높이에 맞추고 Apple 제공 파일로 위치를 잡으라고 한다. `apple.svg`의 출처와 현재 `1em` 크기가 이에 맞는지 구현 때 확인한다
- [x] **9. 앱이 제공자를 처리하지 못할 때.** → 버튼은 항상 그리고 눌렀을 때 토스트로 안내한다. `loginProviders`는 넣지 않는다 (2026-11-04 사용자 확정, ADR-5)

## 기술 결정 (ADR)

결정은 네 개다. ADR-1(전송 계층)이 이 작업의 중심이고, 나머지는 그 위에 얹힌다.

**재정의로 다시 결정할 것** — 범위가 확정되면 `feature-planner` 2단계에서 다룬다. 아래 ADR은 아직 2026-09-11 기준이다.

- **ADR-2 · 계약** — `provider`에 `apple`을 더하는 방법. Apple 응답은 현재 `{ tokenType, token }`에 담기지 않는다. 계약 주석의 규칙상 응답 형태가 바뀌면 새 `type`으로 추가한다

### ADR-1. 브릿지 전송 계층 — 타입드 요청 맵 + id 상관 Promise

**Context** — 지금 스케치(`shared/lib/use-bridge.ts` · `app/webview/webview-provider.tsx`)는
`query` 문자열을 키로 resolve 함수를 보관한다. 같은 종류의 요청이 겹치면 덮어쓰고, 타임아웃과
실패가 없어 네이티브가 응답하지 않으면 Promise가 영원히 걸린다. `shared`가 `app`을 import해
FSD 상향 참조이기도 하다. 로그인 외에 토큰 보관·FCM·딥링크가 같은 통로를 탈 예정이라
"메시지 하나 추가 = 계약 파일 한 줄 + 핸들러 하나"가 되어야 한다.

| 비교 기준            | **A. 직접 구현 — 타입드 요청 맵 + id 상관**                                                                                                | B. 현재 스케치 확장 (query 키 resolve 큐) | C. `@webview-bridge/*` 라이브러리 (1.8.0)                                                                                                                     |

**Decision** — **A.** 세 조각으로 나눈다.

```
계약 (ADR-2)        BridgeContracts { AUTH_LOGIN: { request: {provider}; result: {...} } }
                    BridgeErrorCode = 'TIMEOUT' | 'CANCELLED' | 'UNAVAILABLE' | 'UNSUPPORTED' | 'NATIVE_ERROR'
web  shared/api/bridge
                    isNativeApp()                                — userAgent 'GravitNative/' 판별
                    requestNative(type, payload, { timeoutMs? }) → Promise<result>   실패는 BridgeError
                    subscribeNativeEvent(type, listener)         — 네이티브→웹 이벤트 (이번엔 수신부만)
native bridge/
                    createBridge(handlers)                       — { handleMessage, emit }
                    BridgeHandlerError(code, message)            — 핸들러가 던지면 그 code로 실패 응답
```

동작 규칙:

- 요청 `id`는 요청마다 새로 만든다 (`crypto.randomUUID()`). 같은 `type`이 겹쳐도 응답이 뒤바뀌지 않는다
- 응답은 `id`로만 짝짓는다. 모르는 `id`·깨진 JSON은 버리고 `console.warn`. 해당 요청은 타임아웃으로 끝난다
- 타임아웃은 요청마다 지정하고 기본값 10초. 타임아웃·응답 중 먼저 온 쪽이 이기고 나머지는 무시한다
- 네이티브가 모르는 `type`을 받으면 `UNSUPPORTED`로 응답한다 — 구앱과 신웹의 조합에서 웹이 폴백할 수 있다
- 핸들러가 값을 반환하면 `ok: true`, 던지면 `ok: false`. `BridgeHandlerError`가 아닌 예외는 `NATIVE_ERROR`로 감싼다
- `isNativeApp()`이 거짓이면 `requestNative`는 `UNAVAILABLE`로 즉시 reject한다. 호출부가 앱 밖에서 잘못 부르는 걸 조용히 걸지 않는다
- `message` 이벤트는 iOS는 `window`, Android는 `document`를 대상으로 온다. 둘 다 `window`를 지나므로 `window`의 캡처 단계 리스너 하나로 받는다. 두 곳에 따로 달면 버블링되는 이벤트를 두 번 받는다 (2026-11-05 변경)
- `injectedJavaScriptBeforeContentLoaded`의 기존 에러 리포트 메시지(`{ type, detail, href }`)는 봉투 형식이 아니다. 네이티브 디스패처는 `kind`가 없는 메시지를 기존 로그 경로로 넘긴다

**Alternatives**

| 안  | 내용                                                                                  | 거부 이유                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B   | 현재 스케치를 다듬어 사용                                                             | 요청 상관 `id`가 없어 동시 요청과 늦은 응답을 구분할 수 없고, 타임아웃·에러 형태가 없어 실패를 표현할 수 없다. `shared`→`app` 상향 참조도 구조를 바꿔야 풀린다                                                                                                                                                                                                                                                                                                                                                  |
| C   | `@webview-bridge/react-native` + `@webview-bridge/web` (gronxb/webview-bridge, 1.8.0) | 타임아웃·미지원 판별은 라이브러리가 제공하므로 기능 부족이 이유는 아니다. 거부 이유는 **계약의 위치와 방향**이다 — 계약이 native의 `typeof appBridge`라 web이 native 타입을 import하는 방향이 되고, ADR-2의 중립 패키지·`MIG-005` ADR-4의 메시지 이름 체계와 어긋난다. 취소 vs 실패 구분(`code`)은 어차피 우리 규약으로 써야 한다. 필요한 메시지가 4~5개인데 의존성 2개와 그 유지 상태에 묶이는 비용이 남는다. 호출부 체감은 A(`requestNativeLogin(provider)`)와 C(`bridge.requestLogin(provider)`)가 거의 같다 |

**Consequences**

- (+) 메시지 추가 = 계약 한 줄 + 네이티브 핸들러 하나. 전송 계층은 안 건드린다
- (+) 실패가 `BridgeError.code` 하나로 모여 호출부(`SocialLoginButton`)가 취소·타임아웃·미지원을 `if` 세 개로 가른다
- (+) `FEAT-017`이 표시할 사유가 이미 코드로 구분돼 있다
- (−) **직접 소유하는 코드가 생긴다.** 재연결·재시도·순서 보장은 없다. 네이티브가 응답을 두 번 보내면 두 번째는 버려진다 — 이 규칙을 native 핸들러 작성자가 알아야 한다
- (−) pending Map이 모듈 스코프라 테스트마다 초기화 함수가 필요하다 (`resetBridgeForTest`)
- (−) 웹 페이지가 새로 고쳐지면 pending이 사라진다. 로그인 도중 WebView 리로드는 타임아웃이 아니라 그냥 소실이다. 네이티브가 늦게 보낸 응답은 모르는 `id`로 버려진다 (의도된 동작)

### ADR-2. 메시지 계약의 위치 — `packages/bridge-protocol`

**Context** — 계약을 web과 native가 같이 봐야 한다. 이 레포는 "규칙·훅은 한 벌만 둔다"를
정책으로 갖고 있고, 사본을 뒀다가 이틀 만에 갈라진 전례가 `CLAUDE.md`에 있다.

**Decision** — 워크스페이스 패키지 `packages/bridge-protocol` (`@repo/bridge-protocol`)을 만든다.
내용은 봉투 타입 · `BridgeContracts` 맵 · `BridgeErrorCode` · 봉투 파싱/판별 순수 함수뿐이다.
React·RN·DOM 의존이 없고, 빌드 없이 `.ts` 소스를 그대로 노출한다 (`packages/eslint-config`처럼
"just-in-time" 패키지). web에서는 `shared/api/bridge`만 이 패키지를 import한다.

`AUTH_LOGIN.request.provider`는 `'google' | 'kakao' | 'naver'` 리터럴로 계약 안에 둔다.
web의 `LoginProvider`가 같은 리터럴 유니온이라 그대로 대입된다 — 계약이 features를 알 필요가 없다.

**Alternatives**

| 안                                                                | 내용             | 거부 이유                                                                                                                                                |
| ----------------------------------------------------------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| web `shared/api/bridge`에 두고 native가 `../web/src/...`로 import | 패키지 추가 없음 | native가 web의 내부 경로에 결합된다. web의 tsconfig(`@/` alias, `vite/client` 타입)가 native 컴파일에 끌려 들어오고, web이 파일을 옮기면 native가 깨진다 |
| web·native에 각각 정의                                            | 가장 빠르다      | `CLAUDE.md` "도구별 사본을 만들지 않는다"와 같은 실패다. 에러 코드 하나 추가할 때 두 곳을 고친다                                                         |

**Consequences**

- (+) 계약 변경이 한 곳. 양쪽 `check-types`가 동시에 어긋남을 잡는다
- (−) 패키지 하나 추가: `package.json` · `tsconfig.json` · turbo 파이프라인에 `check-types` 등록. metro가 워크스페이스 심링크를 따라가는지 확인이 필요하다 (Expo 57 metro는 monorepo 기본 지원)
- (−) 프로토콜 버전을 따로 두지 않는다. 구앱–신웹 호환은 `UNSUPPORTED` 폴백으로만 다룬다. 응답 형태가 바뀌는 변경은 새 `type`으로 추가하는 것이 규칙이다

### ADR-3. SDK 토큰을 백엔드로 보내는 주체 — web

**Context** — 네이티브가 SDK 토큰을 받은 뒤, 백엔드 교환을 네이티브가 할지 웹이 할지.

**Decision** — **web.** 네이티브는 SDK 토큰만 응답하고, `features/auth-login/api`가 Android
엔드포인트(orval 생성 `oauth2-0-android-api`)를 호출해 `setSession`한다. `MIG-005` ADR-4
"웹이 세션을 소유"와 같은 방향이고, 기존 콜백의 `isOnboarded` 분기·`USER_423` → `/restore` 처리를
그대로 재사용한다.

**Alternatives**

| 안                                  | 내용                 | 거부 이유                                                                                                          |
| ----------------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------ |
| native가 교환 후 gravit 토큰을 응답 | 네이티브가 완결      | 네이티브에 HTTP 클라이언트·에러 매핑이 또 생기고 세션 생성 경로가 둘이 된다. `USER_423` 같은 분기를 두 번 구현한다 |
| native가 교환 후 이벤트로 세션 주입 | `MIG-005` B안과 동일 | 네이티브 없이는 웹이 동작하지 않는 방향. ADR-4에서 이미 거부된 이유와 같다                                         |

**Consequences**

- (+) 네이티브 핸들러가 SDK 호출 한 가지만 안다. 백엔드가 바뀌어도 앱 업데이트가 필요 없다
- (−) SDK 토큰이 브릿지(JSON 문자열)를 한 번 지난다. WebView 내부 통신이라 노출면은 앱 프로세스 안이지만, 웹 쪽에서 토큰을 로그에 남기지 않도록 주의한다

### ADR-4. iOS SDK 라이브러리

**Context** — Expo 57 · RN 0.86 · `expo-dev-client`(prebuild) 환경. 세 provider 모두
config plugin이 있는 라이브러리가 필요하다 (2026-09-11 npm 확인).

**Decision**

| provider | 라이브러리                                              | 버전   | 토큰                         | 비고                                                                                                               |
| -------- | ------------------------------------------------------- | ------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| kakao    | `@react-native-kakao/core` + `@react-native-kakao/user` | 2.4.6  | `idToken` (OIDC 활성화 필요) | config plugin 있음. 모듈화되어 user 모듈만 설치                                                                    |

**Alternatives**

| 안                                      | 내용                     | 거부 이유                                                                                                                     |
| --------------------------------------- | ------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| `@react-native-seoul/kakao-login` 6.0.4 | 카카오 대안              | 동작하지만 `@react-native-kakao`가 Expo config plugin·모듈 분리·최근 갱신에서 앞선다. 둘 다 같은 팀 생태계라 이전 비용도 낮다 |

**Consequences**

- (−) **네이티브 의존성 3개.** Expo SDK를 올릴 때마다 셋의 호환을 확인해야 한다 (`expo-upgrade` 스킬 절차에 추가)
- (−) Expo Go로는 실행할 수 없다. 이미 `expo-dev-client`를 쓰므로 새 제약은 아니지만, **시뮬레이터에서 카카오톡·네이버 앱 간 이동은 검증할 수 없다.** 실기기 검증 항목이 된다
- (−) Google 16.x는 라이선스가 갈린 패키지다. 유료 "universal" API를 실수로 쓰면 안 된다 — import 경로를 리뷰에서 본다
- (−) 세 SDK의 취소 신호가 다르다 (kakao: 에러 코드 문자열 · google: `statusCodes.SIGN_IN_CANCELLED` · naver: `isSuccess: false` + 메시지). 핸들러가 각각을 `BridgeHandlerError('CANCELLED')`로 정규화해야 하고, 이 매핑이 틀리면 취소가 실패 알림으로 보인다 — 실기기 검증 항목

### ADR-4 개정 — iOS·Android 라이브러리 (2026-11-04 사용자 확정)

**Context** — Android와 Apple이 범위에 들어왔다. 복원한 카카오 2.4.6은 메이저 버전이 하나 뒤처졌고, 아직 어떤 버전도 네이티브 빌드로 검증하지 않아 지금 버전을 지킬 이유가 없다.

**Decision** — 아래로 맞춘다. 버전은 2026-11-04 npm과 Expo 57 `bundledNativeModules.json` 기준이다.

| provider | 라이브러리                                              | 버전                       | 확인한 것                                          |
| -------- | ------------------------------------------------------- | -------------------------- | -------------------------------------------------- |
| kakao    | `@react-native-kakao/core` + `@react-native-kakao/user` | 3.2.0                      | peer: expo ≥52 · RN ≥0.76                          |
| google   | `@react-native-google-signin/google-signin`             | 17.0.0                     | peer: expo ≥52.0.40. 무료 "Original" API만 쓴다    |
| naver    | `@react-native-seoul/naver-login`                       | 5.0.1                      | peer 제한 없음. 호환은 빌드로 확인                 |
| apple    | `expo-apple-authentication`                             | `~57.0.1` (`expo install`) | Expo 57 지정 버전. iOS 전용. 서버 API 확정 후 설치 |

**Alternatives**

| 안                                      | 거부 이유                                                                                   |
| --------------------------------------- | ------------------------------------------------------------------------------------------- |
| 카카오 2.4.6 유지                       | 코드가 이미 있지만 실기기 검증이 없어 지킬 근거가 없다. 나중에 올리면 검증을 다시 해야 한다 |
| `@react-native-seoul/kakao-login` 6.0.4 | 모듈 분리와 Expo plugin에서 앞서지 않는다. 3.2.0이 빌드에 실패하면 대안으로 다시 본다       |

**Consequences**

- (+) 첫 네이티브 빌드부터 Android를 포함한 현재 버전으로 검증한다
- (−) 카카오 메이저 변경의 영향을 아직 모른다. 올릴 때 초기화·로그인 API, plugin 옵션, `KAKAO_CANCEL_ERROR_CODES`를 소스에서 다시 확인한다
- (−) peer 범위는 설치 조건일 뿐 RN 0.86·Expo 57 빌드 성공을 보장하지 않는다. 첫 빌드에서 네 패키지를 함께 확인한다
- (−) 카카오·Google·네이버 라이브러리는 각 사 공식이 아닌 커뮤니티 패키지다 (2026-11-04 npm 저장소 정보 확인). 관리가 멈추면 Expo 업그레이드가 막힐 수 있다. 호출을 `apps/native/bridge/handlers` 안에 가둬 교체 범위를 좁힌다

### ADR-5. 앱의 로그인 제공자 판별 — 사전 판별 없이 눌렀을 때 처리 (2026-11-04 사용자 확정)

**Context** — provider를 추가하면 그 처리 코드가 없는 구버전 앱이 생길 수 있다. 다만 현재 구버전 앱은 없고, 첫 출시에 네 provider가 들어가면 Apple 처리가 없는 앱도 생기지 않는다. 지금 코드는 `UNSUPPORTED`를 받으면 웹 인가 페이지로 폴백하는데, Google·네이버는 WebView에서 차단되고 Apple은 앱에서 쓸 웹 경로도 정해지지 않았다.

**Decision** — 사전 판별을 넣지 않는다. 앱 환경의 로그인 화면은 버튼을 항상 바로 그린다. 누르면 `AUTH_LOGIN`을 요청하고, `UNSUPPORTED`를 받으면 웹 인가 페이지로 폴백하지 않고 토스트 「해당 로그인을 사용할 수 없습니다. 앱을 업데이트 해주세요.」로 안내한다. 이 토스트는 `UNSUPPORTED`에서만 뜬다. 브라우저는 브릿지를 부르지 않는다.

Apple 버튼은 서버가 준비되면 전 플랫폼에 노출한다. Google·네이버·Apple 처리가 없는 앱을 Apple 노출 상태로 출시하지 않는다.

**Alternatives**

| 안                                    | 거부 이유                                                                                |
| ------------------------------------- | ---------------------------------------------------------------------------------------- |
| `APP_INFO.loginProviders`로 미리 판별 | 구버전 앱이 없어 지금은 얻는 것이 없고, 대기 상태·상한 시간·응답 실패 처리가 새로 생긴다 |
| 버튼 영역만 응답까지 대기             | 드문 실패를 대비하려고 모든 사용자가 매번 기다린다                                       |
| 웹이 앱 버전을 비교                   | provider별 최소 버전표를 웹이 들고 있어야 한다                                           |

**Consequences**

- (+) 로그인 화면이 브릿지 응답을 기다리지 않아 대기와 레이아웃 움직임이 없다
- (+) 메시지 계약과 상태가 늘지 않는다. 필요한 것은 토스트 분기 하나다 (`shared/ui/toast` 기존 사용)
- (−) 나중에 새 provider를 추가하면 그 시점의 구버전 앱에서는 눌러 본 뒤에야 안 되는 것을 알게 된다. **새 provider를 추가할 때 `loginProviders` 도입을 다시 검토한다**
- (−) 구버전 앱에서 웹 폴백으로 로그인하는 동작이 사라진다. 이전 경계 조건과 현재 Issue 3의 AC-4·11을 바꿨다. 현재 구버전 앱이 없어 영향받는 사용자는 없다

### ADR-6. 브릿지와 WebView 보안 범위 (2026-11-04 사용자 확정)

**Context** — `createBridge`는 요청을 보낸 페이지의 주소를 확인하지 않고, WebView는 이동할 수 있는 주소를 제한하지 않는다. 이번 작업부터 SDK 토큰이 브릿지로 오가므로, 외부 페이지로 이동한 상태에서 그 페이지가 `AUTH_LOGIN`을 보내면 토큰을 읽을 수 있다. 운영 빌드도 HTTP 통신을 허용한다.

**Decision** — 이번 범위에서 두 가지를 한다.

- 브릿지는 앱이 불러오는 웹의 origin에서 온 요청만 처리한다. 다른 origin의 요청은 핸들러를 부르지 않고 응답도 보내지 않는다
- `NSAllowsArbitraryLoads`와 `usesCleartextTraffic`은 개발 빌드에서만 켠다

**Alternatives**

| 안                                  | 거부 이유                                                                                      |
| ----------------------------------- | ---------------------------------------------------------------------------------------------- |
| 세 설정 모두 별도 작업              | 토큰이 오가기 시작하는 시점에 유출 경로를 남긴다                                               |
| `originWhitelist`까지 이번에 좁히기 | 외부 인가 페이지 이동에 영향을 줄 수 있다. Android의 Apple 방식이 정해진 뒤 별도 작업으로 본다 |

**Consequences**

- (+) WebView가 외부 페이지로 이동해도 그 페이지는 SDK 로그인을 시작하거나 토큰을 받을 수 없다
- (−) 다른 origin의 요청은 응답이 없어 웹에서 `TIMEOUT`으로 끝난다. 앱의 웹 주소가 설정과 다르면 로그인이 타임아웃으로 보이므로 첫 빌드에서 확인한다
- (−) 운영 빌드에서 HTTP 주소가 끊긴다. 서비스 주소가 모두 HTTPS인지 첫 빌드에서 확인한다
- (−) WebView의 이동 제한은 여전히 없다. 브릿지 밖의 위험은 별도 작업이 끝날 때까지 남는다
