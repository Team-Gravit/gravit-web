# REF-072 — 로그인 화면 첫 그리기 단축 (모바일 · 데스크톱)

GitHub Issue: #345 (관련 REF-071 · REF-062 #313)

## 배경 · 목표

로그인 화면(`/`)은 새 사용자와 스토어 심사자가 처음 보는 화면이다. 로그아웃 · 캐시 없는 첫 방문에서
글자가 보이기까지 모바일 실측 약 4.6초가 걸린다. 화면 모양과 동작은 그대로 두고 첫 그리기와 LCP를 줄인다.

| -------- | ------------------------------------------------------------------------------------------------------------------- |
| 도구     | Lighthouse 13.5.0 (Node API) + chrome-launcher. scratchpad에 설치, 저장소 의존성 아님                               |
| 빌드     | 프로덕션 빌드를 `vite preview`로 띄운다. **개발 서버(5173)는 쓰지 않는다** — 번들링이 없어 FCP 31초처럼 의미가 없다 |
| 실측     | 모바일 · `throttlingMethod: devtools` (RTT 562.5ms · 1.47Mbps · CPU 4배를 실제로 건다) · 5회 번갈아 중앙값          |

| 상태     | 매 회차 저장소 비움 (로그아웃 · 캐시 없음)                                                                          |

| 요청                        | 시작 → 끝   | 비고                         |
| --------------------------- | ----------- | ---------------------------- |

| 첫 JS `index-*.js` (172 KB) | 0.7 → 2.4초 |                              |
| CSS `index-*.css` (22 KB)   | 0.7 → 1.5초 |                              |
| 로그인 화면 청크 5개        | 3.2 → 3.8초 | 첫 JS 실행이 끝나야 요청된다 |

## 실험 (코드 커밋 없음, 실험 빌드를 4174에 띄워 4173과 번갈아 측정)

| 실험                                                    | 모바일 실측 (5회)                                          | 모바일 계산 (3회)       | 비고                 |
| ------------------------------------------------------- | ---------------------------------------------------------- | ----------------------- | -------------------- |
| 로그인 화면을 첫 청크에 포함 (`codeSplitGroupings: []`) | FCP·LCP 4.62 → **4.07초** · 점수 65 → 71 · 5회 모두 개선   | 65 → 66점 · FCP −0.25초 | 첫 청크 gzip +3.3 KB |
| 본문 글꼴 제거                                          | FCP·LCP 4.63 → 4.61초 (차이 없음) · SI −0.9초 · TBT −270ms | 66 → 92점 · FCP −3.2초  | 글꼴 전략은 범위 밖  |

- 글꼴은 `font-display: swap`이라 첫 그리기를 막지 않는다. 늦게 도착해 글자가 다시 배치되는 비용이 SI·TBT로 잡힌다
- 계산 방식은 글꼴을 첫 그리기 경로로 잡아 약 3초를 더한다. 계산 방식 점수(외부 점수)를 올리려면 글꼴 작업이 필요하다
- 같은 조건의 puppeteer 직접 측정(5회)도 글꼴 유무 FCP 차이 0.12초로 같은 결론이다
- DevTools 패널에서 1회 실측한 FCP 15.1초는 튄 값이었다. 같은 설정 10회는 모두 4.4 ~ 5.2초였다

### 글꼴 preload를 하지 않는 이유

preload하면 글꼴(638 KiB)이 첫 JS(172 KB)와 같은 시점에 출발해 느린 회선 대역폭을 나눠 쓴다.
글꼴은 첫 그리기를 막지 않는데 JS가 늦게 도착하므로 FCP·LCP가 오히려 늦어질 것으로 본다(미측정).
글꼴이 작아진 뒤(글꼴 작업) 다시 판단한다.

## 목표

| 대상                 | 기준              |    현재 | 목표                                     |
| -------------------- | ----------------- | ------: | ---------------------------------------- |
| 모바일 LCP           | 실측 · 5회 중앙값 |  4.62초 | **3.5초 이하** (1차) · 2.5초 이하 (도전) |
| 데스크톱 LCP         | 계산 · 3회 중앙값 |  1.32초 | **1.2초 이하**                           |
| 데스크톱 배경 이미지 | 전송 크기         | 298 KiB | 화면 크기에 맞는 크기 · 형식             |

- 2.5초는 Core Web Vitals 「좋음」 기준이다. 원래는 실제 사용자 75번째 백분위 기준이며, Lighthouse 모바일 느린 4G(약 1.6Mbps)는 그보다 가혹하다
- 모바일 2.5초는 JS 실행 전에 글자가 보여야 가능하다(첫 JS 도착만 약 2.4초). prerender 조사 후 결정한다

## 범위

1. 로그인 화면 청크를 첫 청크에 포함 (`app/routes/index.tsx`)
2. 구글 로고를 표시 크기의 3배로 축소 (`features/auth-login/ui/assets/google-logo.png`) — 원본 그림을 그대로 줄인다
3. 데스크톱 배경 이미지 전송 크기 축소 — 배경이 보이기 시작하는 시점도 기록한다
4. 첫 JS 도착(2.4초) → 그리기(4.1초) 사이 메인 스레드 작업을 trace로 나누고 미룰 수 있는 초기화를 찾는다
5. prerender(로그인 HTML 미리 그리기) 가능성 · 비용 조사 — 진행 여부는 사용자 판정

## 결과 — 1단계 (범위 1 · 2, 2026-10-29)

변경: `app/routes/index.tsx` `codeSplitGroupings: []` · `google-logo.png` 200×204(33,661 B) → 56×57(4,701 B, 같은 그림을 고품질 축소).
로고는 4 KiB를 넘어 JS에 들어가지 않고 지금처럼 따로 받는다(plan §6 결정 1은 해당 없음). WebP(q90 2,292 B)는 손실 압축이라 브랜드 로고에는 쓰지 않았다.

| 측정                           | 기준(`develop`) | 1단계         | 차이                               |
| ------------------------------ | --------------- | ------------- | ---------------------------------- |
| 모바일 실측 FCP·LCP (5회)      | 4.76초          | **4.25초**    | −0.51초 · 5회 모두 개선            |
| 모바일 실측 점수               | 63              | 67            | +4                                 |
| 모바일 계산 LCP (3회)          | 5.75초 · 65점   | 5.43초 · 67점 | −0.32초                            |
| 데스크톱 계산 LCP (3회)        | 1.32초 · 95점   | 1.27초 · 96점 | −0.05초                            |
| `/terms` 모바일 계산 LCP (3회) | 5.60초          | 5.58초        | 차이 없음 (첫 청크 증가 영향 확인) |
| 첫 청크 gzip                   | 171,401 B       | 174,127 B     | +2.7 KB                            |

- 빌드 결과물: 로그인 문구가 첫 청크에 있고, 로그인 전용 청크 5개가 사라졌다. `routeTree.gen.ts` 변화 없음
- 로고: 표시 크기(모바일 14.7×15)에서 DPR 1 · 3 캡처를 나란히 비교 — 차이 없음
- 수동 스모크(자동화): 로그아웃 `/` → 구글 · 카카오 · 네이버 버튼 3개 표시 / `accessToken`이 있으면 `/` → `/main` 이동. 기준 빌드와 같음
- 테스트: `pages/login` · `features/auth-login` 5개 파일 18개 통과
- 1차 목표(모바일 3.5초 · 데스크톱 1.2초)는 아직이다. 범위 3 ~ 5에서 이어 간다

### 해석할 때 주의할 점

- −0.51초는 RTT 562ms인 느린 4G 조건에서 왕복 1번이 줄어든 값이다. RTT가 수십 ms인 실제 LTE에서는 0.1초 안팎으로 본다(미측정)
- 네이티브 앱은 켤 때마다 `/`를 연다(`apps/native/app/index.tsx` `WEB_URL`). 로그인한 사용자는 `beforeLoad`에서 `/main`으로 넘어가므로 이 변경의 이득이 없고, 첫 청크 증가분(gzip 2.7 KB)만 받는다
- `codeSplitGroupings: []`를 다른 라우트로 넓히면 첫 청크가 다시 커진다. 첫 진입 화면에만, 측정 근거와 함께 쓴다
- 로그인 화면에 무거운 의존성이 추가되면 모든 화면의 첫 청크에 실린다. 지금은 번들 크기 상한 검사가 없어 리뷰에서 지킨다

## 후속

- 데스크톱 새 배경(그라데이션 + 투명 일러스트)과 `<img>` · `srcset` 전환은 디자인 변경이라 이 작업과 분리한다 → `FIX-073` (예정). 이 작업은 그 전후 데스크톱 LCP · SI만 측정한다
- 앱 실제 경로는 `/` → `/main` 리다이렉트다. `/main` 첫 진입도 첫 JS 실행 → 리다이렉트 → 화면 청크 요청 순서라 같은 구조의 대기가 있다. `/main` 작업(REF-062 등)은 이 경로로 측정한다
