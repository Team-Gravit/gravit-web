# FEAT-044 — 문제 카드 부가 조작

GitHub Issue: [#256](https://github.com/Team-Gravit/gravit-web/issues/256)

## 배경 · 목표

FEAT-038(레슨 문제 풀이)이 시안에 있지만 범위 밖으로 미뤈 세 가지 중 **둘**을 구현한다.
`work/done/FEAT-038-레슨-문제-풀이/spec.md`의 확인 필요 10(북마크)·11(선지 가리기)이 근거다.

- **D4** — 문제 카드에 북마크 아이콘
- **D5** — 객관식 선지에 가리기(눈) 아이콘

에셋은 받았고 아이콘 정리는 선행 커밋에서 끝냈다.

## 범위

| 포함                                 | 제외                                            |
| ------------------------------------ | ----------------------------------------------- |
| 객관식 선지 가리기 토글              | 북마크 목록 화면 (`/bookmarked-problems`)       |
| 문제 북마크 토글 + 토스트            | 신고 버튼 (D2) — `report-api` 는 있지만 별 작업 |
| `Problem` 모델에 `isBookmarked` 추가 | 주관식의 가리기 (선지가 없다)                   |

## 확정된 규칙

FEAT-038의 R1~R14를 잇는다. 이번에 추가되는 것만 적는다.

| #   | 규칙                                                                                              |
| --- | ------------------------------------------------------------------------------------------------- |
| R15 | 선지의 **가리기 버튼은 답을 제출하지 않는다.** 선지 본체와 히트 영역이 분리된다                   |
| R16 | 가린 선지는 **선택할 수 없다.** 다시 누르면 되돌아온다                                            |
| R17 | 가린 상태는 **풀이 세션에 보존**된다. 새로고침에는 남고 레슨을 떠나면 사라진다 (R7)               |
| R18 | **제출 후에는 가림이 풀린다.** 모든 선지의 해설을 열 수 있어야 한다 (D9)                          |
| R19 | 북마크는 **낙관적으로** 반영하고 성공·실패를 토스트로 알린다                                      |
| R20 | 북마크 요청 중에는 **버튼을 비활성**한다. 재시도하지 않는다                                       |
| R21 | 가리기 버튼은 선지 번호와 상태를 포함해 **`{n}번 선지 가리기` · `{n}번 선지 다시 보기`**로 읽힌다 |

> **R15의 배경 — R1·R3과 정면으로 충돌한다.** 선지는 누르면 **즉시 제출**되고(R1)
> 되돌릴 수 없다(R3). 눈 아이콘을 선지 버튼 안에 두면 「가리려다 답을 확정」하는 일이
> 벌어지고 복구 수단이 없다. 선지 본체가 `button` 이므로 **가리기 버튼을 그 안에 중첩할 수
> 없다**(중첩 버튼은 유효하지 않은 HTML이다). 형제로 두고 행을 감싸는 구조가 필요하다.

> **R16과 R3의 차이** — 가리기는 제출이 아니므로 R3의 「되돌릴 수 없다」가 적용되지 않는다.
> 실수로 가렸을 때 복구 수단이 없으면 곤란하다.

> **R18의 근거** — 제출 후 선지는 아코디언이 되고(D9) 각 선지가 자기 해설을 갖는다
> (`OptionResponse.explanation`). 가림이 남으면 그 선지의 해설을 영영 못 읽는다.

> **R20의 배경 — 연달아 누를 때의 경합.** 낙관적 갱신 상태에서 두 요청의 응답 순서가
> 뒤바뀌면 캐시가 사용자가 본 것과 달라진다. `toast()` 는 단일 토스트를 대체하므로 문구 쪽은
> 마지막 것만 남지만 캐시는 그렇지 않다. 요청 중 비활성이 경합을 원천 차단하고, 낙관적
> 갱신 덕에 **비활성이어도 아이콘은 이미 바뀐 상태**라 멈춘 느낌이 없다.
>
> `retry` 는 끈다. 사용자가 되돌린 뒤에 늦게 성공하면 상태가 뒤집힌다.

> **가린 선지의 임시 표현** — 선택 버튼 본체만 `opacity-40`으로 낮추고 가리기 버튼은 그대로
> 유지한다. Figma에 가린 상태가 추가되면 다시 대조한다.

## 서버 계약 (확인된 것)

```
POST   /api/v1/bookmarks          { problemId }   북마크 추가
DELETE /api/v1/bookmarks          { problemId }   북마크 삭제
GET    /api/v1/bookmarks/{unitId}                 목록 — 이번 범위 밖
```

**초기 상태는 따로 조회하지 않는다.** `ProblemResponse.isBookmarked: boolean` 이 레슨 문제
응답에 이미 들어 있다.

> ⚠️ **현재 매퍼가 이 값을 버린다.** `entities/problem/model/problem.ts` 의 `toProblem` 이
> `problemId` · `instruction` · `content` 만 옮기고 `isBookmarked` 를 떨어뜨린다
> (픽스처에만 남아 있다). **`ProblemBase` 에 추가하는 것이 선행 작업이다.**

## 문구

`constants-convention.md` §2 — 기획이 바꿀 문구이므로 상수. 키만 영문, 값은 한글
(`i18n-policy.md`).

```ts
BOOKMARK_ADDED_MESSAGE = '북마크에 추가되었습니다';
BOOKMARK_REMOVED_MESSAGE = '북마크가 삭제되었습니다';
BOOKMARK_ADD_FAILURE_MESSAGE = '북마크 추가에 실패했어요. 다시 시도해 주세요.';
BOOKMARK_REMOVE_FAILURE_MESSAGE = '북마크 삭제에 실패했어요. 다시 시도해 주세요.';
```

**실패 문구를 추가·삭제로 나눈 이유** — 공용 문구(`북마크에 실패했어요`)는 삭제 케이스에서
**시도한 것과 반대를 말한다.** 낙관적 갱신이 아이콘을 채워진 상태로 되돌려 놓으므로 화면과
문구가 같이 「추가하려다 실패」처럼 읽힌다.

## 낙관적 갱신의 대상

`isBookmarked` 는 단독 쿼리가 아니라 **레슨 문제 목록 응답 안의 배열 요소**다.

```ts
setQueryData(레슨문제키, (previous) => ({
  ...previous,
  problems: previous.problems.map((problem) =>
    problem.problemId === problemId ? { ...problem, isBookmarked: next } : problem,
  ),
}));
```

키는 **orval 생성 팩토리로 만든다** (`api-convention.md` §2). path parameter 가 URL 문자열에
박히므로 레슨별로 정확히 지정해야 한다(§4).

## 확인 필요

1. **어투를 통일할지.** 성공은 `~되었습니다`(합니다체), 실패는 `~했어요`(해요체)로 섞여 있다.
   실패 쪽은 기존 `제출에 실패했어요…`와 맞춘 것이다.
2. **가린 선지의 최종 시각 표현.** 시안(D5)에 눈 아이콘은 있으나 **가려진 뒤의 상태 프레임**을
   확인하지 못했다. Figma 확인 전까지는 선택 버튼 본체에 `opacity-40`을 적용한다.
3. **화면 ID 대응** — FEAT-038이 못 채운 항목. `INFRA-031` 에서 확정한다.
