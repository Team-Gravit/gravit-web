# NAT-011 — 앱 스플래시 화면(O.0) 구현

## 배경 · 목표

`apps/native`는 앱을 켜면 스캐폴드 잔재인 흰 배경 스플래시(`assets/splash.png`)를 1초간 보여준 뒤
곧바로 내려버린다. WebView가 `apps/web`을 다 불러오기 전이라 그 사이 **흰 화면**이 남고, 사용자는
앱이 멈춘 것처럼 느낀다. `app/_layout.tsx`의 TODO(`실제 초기 로딩 작업이 추가되면 완료 콜백에서
상태를 갱신한다`)가 가리키는 것이 이 구간이다.

Figma AOS `O.0`을 그대로 재현한 브랜드 스플래시를 만들고, **WebView가 로드될 때까지** 그 화면을
유지해 앱 실행부터 첫 화면까지 끊김 없이 잇는다. 로그인(`O.1`) 이전에 사용자가 처음 보는 화면이라
인증 게이트(`MIG-005`)보다 먼저 자리를 잡아야 한다.

## 플랫폼 전제

> ⚠️ **레포의 겉모습과 반대다.** 이 절을 읽지 않고 파일만 보면 판단이 거꾸로 간다.

**출시 타깃은 iOS 단독이다.** `apps/native/android/`가 있고
`aaec0ce feat(native): configure Android development build` 커밋까지 있지만, 이는 개발 환경이
Windows라 로컬에서 iOS를 빌드할 수 없어 **실기기 테스트용으로 Android를 빌드해 둔 것**이다.
`android/`는 `.gitignore` 대상(CNG 산출물)이라 팀에 공유되지도 않는다.

| 플랫폼      | 위치                    | 이 작업에서의 요구 수준                         |
| ----------- | ----------------------- | ----------------------------------------------- |
| **iOS**     | 출시 타깃               | `O.0` 시안과 일치해야 한다                      |
| **Android** | 개발 실기기 테스트 전용 | 동작만 하면 된다. **시안 일치를 요구하지 않음** |

Figma에 AOS 시안만 있고 iOS 시안이 없는 것은 **시안 제작 사정이지 타깃을 뜻하지 않는다.**
`O.0`의 레이아웃을 iOS에 그대로 적용한다.

향후 안드로이드 담당자가 이탈하면 크로스 플랫폼을 모두 지원해야 할 가능성이 있다. 따라서
**iOS 전용 선택이 Android 지원을 영구히 막는 경우 그 사실을 ADR에 남긴다.**

### 검증 전제 — 이번 작업은 Android로만 검증한다

**출시 타깃은 iOS인데 이번 검증은 Android로만 한다.** 어긋나 보이지만 의도된 것이다.

개발 환경이 Windows라 `expo run:ios`가 돌지 않고, `eas.json`이 없어 클라우드 빌드 경로도 없다.
Apple Developer 계정 문제도 아직 해결되지 않았다 (2026-09-04 기준). 따라서 iOS 실기 검증은
EAS Build 셋업 이후로 미룬다.

| 검증 대상                                 | Android로 확인 | 비고                                                   |
| ----------------------------------------- | :------------: | ------------------------------------------------------ |
| `onLoadEnd` → 스플래시 해제, 흰 화면 제거 |       ✅       | 이 작업의 핵심 목적                                    |
| 무응답 상한(10초) 동작                    |       ⚠️       | 자동 검증 불가. URL을 막고 수동으로 확인한다           |
| Android 정적 스플래시 배경·로고 슬롯      |       ✅       | 개발 테스트 전용이라 시안 일치는 요구하지 않는다       |
| 페이드아웃 (`setOptions({ fade: true })`) |       ✅       | 정적 스플래시 자체 연출                                |
| **iOS 정적 스플래시 전체화면 그라디언트** |     **❌**     | iOS 전용 경로. 이번에 확인 불가                        |
| **iOS 스플래시의 로고 유무·위치**         |     **❌**     | 위와 같음. 현재 이미지에 로고가 없다 (Changelog 09-08) |

iOS 설정과 에셋은 **이번에 함께 작성하되 「미검증」으로 표시**한다. 빼두면 출시 타깃에 스플래시
설정이 아예 없는 상태가 되고, 나중에 다시 결정 근거를 복원해야 한다. `checklist.md`와
`docs/implementation-status.md`에 미검증 사실을 명시한다.

### 자동 테스트를 쓰지 않는 이유

**`apps/native`에는 테스트 러너가 없다.** `test` 스크립트도, jest/vitest 설정도, 테스트 파일도
없고 테스트 관련 devDependency가 하나도 없다. turbo의 `test` 태스크는 스크립트가 없는 native를
건너뛴다.

하네스를 세우려면 러너를 골라야 하는데, 레포 표준은 Vitest(`test-policy.md`)인 반면 React
Native 0.86은 Flow 타입이 붙은 소스를 배포해 Vitest로 물리기가 까다롭고 Expo 정석은 `jest-expo`다.
**모노레포에 러너를 둘 둘지는 ADR이 필요한 구조 결정**이므로 스플래시 구현과 같은 계획에 섞지
않는다 (`refactor-checklist.md` §2). `INFRA-013`으로 분리한다.

따라서 이번 작업의 AC는 전부 **`수동`(Android 실기 시나리오) 범위**다. `단위`·`통합` 레이블은
쓰지 않으며, 레이블 정의는 `issues.md`의 「범위 레이블」에 있다. 단, ADR-1대로
~~타이밍 로직을 `hooks/use-splash-gate.ts`로 분리해~~ **ADR-6으로 그 훅이 사라졌다.** 남은 타이밍은
`app/index.tsx`의 상한 타이머 하나뿐이라, 하네스가 생기면 테스트만 얹으면 되는 상태로
남긴다. `test-policy.md` §6에 따라 이 미검증 사실을 숨기지 않고 여기에 남긴다.

> EAS Build의 **iOS 시뮬레이터 빌드는 Apple Developer 계정 없이도 가능**한 것으로 알려져 있다.
> 계정 문제가 길어지면 이 경로를 먼저 확인해 볼 가치가 있다 — 다만 실행할 Mac 또는 클라우드
> 시뮬레이터가 따로 필요하다. 후속 작업에서 판단한다.

## 범위

**`apps/native`만 건드린다.** `apps/web`은 변경하지 않는다.

| 대상                            | 변경                                                                                   |
| ------------------------------- | -------------------------------------------------------------------------------------- |
| `apps/native/app.json`          | `expo-splash-screen` 플러그인 재구성 (iOS 전체화면 이미지 / Android 배경·아이콘 슬롯)  |
| `apps/native/app/_layout.tsx`   | 자동 숨김 차단(`preventAutoHideAsync`), 페이드 옵션, placeholder 상태 제거             |
| `apps/native/app/index.tsx`     | `hideAsync()` 호출 시점 소유 — `onLoadEnd` · `onError` · 10초 상한                     |
| `apps/native/assets/`           | `splash-gradient.png`(iOS) · `splash-logo-square.png`(Android) 추가, `splash.png` 제거 |
| `docs/implementation-status.md` | `O.0` 행의 「네이티브 구현」을 `—` → 구현·검증 상태로 갱신                             |

**시안 근거** — Figma `hu4c6qCEMB62qHXk2v8Gsl` / AOS `O.0` (`12898:23224`, 360×740).
배경 `linear-gradient(64.04deg, #8100B3 0%, #DD00FF 100%)`, 로고 176×153 (`12898:23226`).
시안의 상태바(`상태바`)와 하단 `Tab Bar`는 **안드로이드 시스템 크롬 목업**이라 구현 대상이 아니다.
타깃은 iOS이므로 이 두 목업은 iOS의 상태바·홈 인디케이터 영역으로 읽는다 (「플랫폼 전제」 참고).

로고 세로 중심은 화면 전체 중앙이 아니라 **시스템 크롬을 뺀 영역의 중앙**이다
(시안의 `top: calc(50% - 12.5px)` = 357.5px ≈ 콘텐츠 영역 중앙 358px). 시안의 24px·48px은 AOS
목업 수치이므로, iOS 구현에서는 `useSafeAreaInsets()`의 실제 inset을 뺀 영역의 중앙으로 옮긴다.

## Out of Scope

- **오류·재시도 화면** — `onError`에서 즉시 스플래시 숨김을 호출한다. 로드 종료·실패 신호가 없으면
  `WebviewPage` effect의 타이머 등록 후 10초에 숨김을 호출한다. 오류 화면은 별도 `NAT-` 작업이다
- **로그인·인증 게이트** — 토큰 복원 여부를 스플래시 유지 조건에 넣지 않는다 (`MIG-005`)
- **`apps/web`의 로딩 화면** — 브라우저 단독 접속에는 스플래시가 없다. `O.0`은 AOS 전용 시안이다
- **스플래시 애니메이션** — 시안에 모션 정의가 없다. 페이드아웃 외의 연출을 만들지 않는다
- **`tokens.css`의 그라디언트 각도 불일치 수정** — 웹 토큰은 45°, 시안 `O.0`은 64°다.
  네이티브는 `tokens.css`를 쓰지 않으므로 이번 작업과 무관하다. `FIX-007`에 얹는다
- **Android 정적 스플래시의 시안 일치** — Android는 개발 테스트 전용이다 (「플랫폼 전제」).
  단색 배경으로 두고 `O.0` 재현을 요구하지 않는다
- **앱 아이콘·adaptive icon 교체** — 스캐폴드 잔재지만 스플래시와 별개 항목이다
- **iOS 실기 검증과 EAS Build 셋업** — Windows 환경·Apple Developer 계정 미해결로 이번에 불가능하다
  (「검증 전제」). iOS 설정은 작성하되 미검증으로 남기고, 검증은 `INFRA-012`에서 한다
- **native 테스트 하네스 구축** — 러너 선택이 ADR이 필요한 구조 결정이다 (「자동 테스트를 쓰지 않는
  이유」). `INFRA-013`에서 정한다

2단계 ADR에서 추가로 확정한 제외 항목이다.

- **`react-native-svg` 도입** — 로고를 PNG로 받는다 (ADR-3). native에 벡터 수요가 더 생기면 그때
  별도로 판단한다
- **`react-native-reanimated` 사용** — 설치돼 있지만 사용처가 없다. 페이드아웃은 내장 `Animated`로
  한다 (ADR-3)
- **`apps/native`의 FSD 레이어 적용** — 훅과 steiger가 `apps/web/src/`만 검사한다. 도구가 지키지
  않는 규칙을 늘리지 않는다 (ADR-3)
- **Android `windowBackground` 그라디언트 config plugin** — Android 12+ 정적 스플래시 배경은
  `format="color"`라 그라디언트를 못 넣는다. `postSplashScreenTheme`의 `windowBackground`에
  그라디언트 드로어블을 넣는 우회가 가능하지만, Android는 개발 테스트 전용이라 그 비용을 쓰지
  않는다 (ADR-2)

## 기술 결정 (ADR)

### ADR-1 — 스플래시 오버레이를 화면 지역 상태로 소유한다 (폐기)

> ⛔ **2026-09-08 폐기 — ADR-6으로 대체.** Alternatives의 「정적 스플래시만 연장」 안을 실제로 채택했다. 거기 적힌 트레이드오프(기기 종횡비에 따른 로고 위치)는 그대로 남는다.

**Context**

확정 전제 2·3에 따라 정적 스플래시와 JS 오버레이 2단 구성을 쓰고, 준비 완료 신호는 WebView의
`onLoadEnd`다. 그 신호가 오버레이의 표시 여부까지 도달하는 경로를 정해야 한다. 현재
`apps/native`의 라우트는 `app/index.tsx` 하나뿐이고, `_layout.tsx`는 placeholder `isLoaded`
상태만 들고 있다.

**Decision**

`app/index.tsx`가 준비 상태를 소유하고, 오버레이를 WebView 위에 절대배치로 겹친다.

| 파일                            | 책임                                                                          |
| ------------------------------- | ----------------------------------------------------------------------------- |
| `app/_layout.tsx`               | `SplashScreen.preventAutoHideAsync()` 호출과 `Stack` 구성만. placeholder 제거 |
| `app/index.tsx`                 | 준비 상태 소유. `WebView.onLoadEnd`에서 `markReady()` 호출                    |
| `components/splash-overlay.tsx` | 그라디언트 배경 + 로고. 표시 여부를 모르고 `opacity`만 받는 표시 전용         |
| `hooks/use-splash-gate.ts`      | 최소 노출·최대 대기 판정. 순수 타이밍 로직이라 단위 검증 대상                 |

**Alternatives**

| 안                                                    | 거부 이유                                                                                                                                                                                                                                                                                  |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 루트 레이아웃이 소유하고 Context로 `markReady()` 하향 | 소비자가 `index` 하나뿐이라 Provider 계층이 순수한 간접비다. 라우트가 늘어날 계획도 없다 — `MIG-005`의 인증 게이트는 WebView 안쪽 웹 라우팅이라 native 라우트를 늘리지 않는다. 필요해지면 그때 올리는 비용이 작다                                                                          |
| `app/splash.tsx` 라우트 + `router.replace('/')`       | 전환 시점에 WebView가 언마운트되면 로딩이 처음부터 다시 시작된다. **"WebView 로딩 중 흰 화면을 없앤다"는 이 작업의 목적 자체를 깬다.** 페이드아웃도 Stack 전환 애니메이션에 종속돼 최소 노출 시간을 제어하기 어렵다                                                                        |
| 정적 스플래시만 연장 (JS 오버레이 없음)               | iOS는 전체화면 이미지를 지원하므로 그라디언트와 로고를 구워 넣고 `hideAsync()`만 늦추는 것이 기술적으로 가능하다. 그러나 storyboard 이미지는 `scaleAspectFill`로 잘려 **기기 종횡비마다 로고 위치가 밀린다.** 오버레이는 safe area 기준으로 로고를 정확히 놓는다. 확정 전제 2와도 충돌한다 |

**Consequences**

- ✅ 라우트가 하나인 현 구조에서 파일 4개로 끝나고, 타이밍 로직이 훅으로 분리돼 단위 검증이 된다
- ✅ WebView가 계속 마운트된 채 뒤에서 로딩되므로, 오버레이가 내려가는 순간 첫 화면이 이미 준비돼 있다
- ⚠️ **native 라우트가 늘어나면 각 화면이 스플래시를 따로 알아야 한다.** 두 번째 라우트가 생기는
  시점에 Context 승격을 재검토한다
- ⚠️ `index.tsx`가 WebView 설정과 스플래시 연결을 함께 갖는다. 지금은 둘 다 얇지만 WebView 옵션이
  더 늘면 분리 신호로 본다

### ADR-2 — iOS 정적 스플래시는 전체화면 그라디언트 이미지, Android는 단색

**Context**

`O.0`의 배경은 `linear-gradient(64.04deg, #8100B3 0%, #DD00FF 100%)`다. 정적 스플래시가 이걸
그릴 수 있는지는 플랫폼마다 다르고, **이 프로젝트의 실측 결과**는 다음과 같다.

`apps/native/android/`의 병합된 리소스에서 확인한 attr 선언:

```xml
<attr format="color"     name="windowSplashScreenBackground"/>
<attr format="reference" name="windowSplashScreenAnimatedIcon"/>
```

`windowSplashScreenBackground`가 `format="color"`라 **Android 12+ 정적 스플래시 배경에는 드로어블을
넣을 수 없다.** 드로어블을 받는 `windowSplashScreenAnimatedIcon`은 화면 중앙의 원형 마스크 아이콘
슬롯이라 배경으로 쓸 수 없다.

iOS는 다르다. `expo-splash-screen@57`의 플러그인 타입(`plugin/build/types.d.ts`)에
`IOSSplashConfig.enableFullScreenImage_legacy`와 `resizeMode: 'cover' | 'contain'`이 있고,
`withIosSplashScreenStoryboardImage.js`가 이 플래그에 따라 이미지를 화면 전체에 고정한다.
즉 **iOS는 전체화면 그라디언트 이미지가 가능하다.**

「플랫폼 전제」대로 출시 타깃은 iOS이고 Android는 개발 테스트 전용이므로, 두 플랫폼에 같은 수준의
시안 일치를 요구할 이유가 없다.

**Decision**

- **iOS 정적 스플래시** — 전체화면 그라디언트 이미지. `enableFullScreenImage_legacy: true` +
  `resizeMode: 'cover'`. ~~로고는 굽지 않는다 — 로고는 오버레이만 그린다~~
  → **오버레이가 폐기돼 로고를 그리는 층이 사라졌다** (ADR-6). 현재 iOS 스플래시에는 로고가 없다
- **Android 정적 스플래시** — 단색 `#8100B3`. 시안의 그라디언트 시작색 그대로이고, **Figma에 없는
  파생값을 만들지 않는다.** 개발 테스트 전용이라 시안 일치를 요구하지 않는다
- 배경색은 `app.json`의 `expo-splash-screen` 플러그인에만 반영한다. `android.adaptiveIcon`의
  `backgroundColor`는 앱 아이콘 항목이라 건드리지 않는다

**Alternatives**

| 안                                                    | 거부 이유                                                                                                                                                                                                                       |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 양 플랫폼 모두 단색 `#AF00D9` (그라디언트 중간값)     | **Figma에 없는 색을 만들어내는 선택이다.** iOS가 전체화면 이미지를 지원하는 이상 근사할 이유가 없다. 초안에서 이 안을 골랐던 것은 타깃을 Android로 잘못 전제했기 때문이다 (Changelog 2026-09-04 3행)                            |
| iOS 정적 스플래시에 로고까지 구운 이미지              | `scaleAspectFill`은 기기 종횡비에 따라 이미지를 잘라낸다. iPhone SE(16:9)와 Pro Max(19.5:9)에서 **로고 위치가 서로 다르게 밀린다.** 그라디언트는 잘려도 티가 안 나지만 로고는 난다. 로고는 오버레이가 safe area 기준으로 그린다 |
| Android도 `windowBackground` 그라디언트 config plugin | `postSplashScreenTheme`의 `windowBackground`에 그라디언트 드로어블을 넣으면 Android도 재현할 수 있다. 그러나 `android/`가 CNG 산출물이라 config plugin을 새로 써야 하고, **개발 테스트 전용 플랫폼에 쓸 비용이 아니다**         |
| `react-native-svg`로 그라디언트                       | 로고를 PNG로 받기로 해 SVG를 쓸 다른 이유가 없다. 배경 하나 때문에 런타임 의존성과 metro transformer 설정을 늘리지 않는다                                                                                                       |

**Consequences**

- ✅ **iOS에서 정적 → 오버레이 전환에 색 점프가 없다.** 두 구간이 같은 그라디언트를 그린다
- ✅ Figma에 없는 파생 색을 만들지 않는다. 쓰는 값이 전부 시안의 실제 값이다
- ⚠️ **`enableFullScreenImage_legacy`는 "will be removed"로 표시된 플래그다.**
  (`plugin/build/types.d.ts`: _"Legacy transition helper, will be removed."_) Expo SDK를 올릴 때
  제거되면 이미지가 `imageWidth` 기준으로 중앙 정렬돼 **그라디언트가 작은 사각형으로 쪼그라든다.**
  다행히 조용히 깨지지 않고 눈에 확 띄는 형태라 업그레이드 시 바로 잡힌다. SDK 업그레이드 작업의
  확인 항목으로 남긴다
- ⚠️ **Android 정적 스플래시는 시안과 다르다.** 의도된 것이지만, 나중에 Android가 출시 타깃이 되면
  이 결정을 다시 열어야 한다. 그때 필요한 것은 위 Alternatives의 config plugin 안이다
- ⚠️ 전체화면 이미지는 기기 종횡비에 따라 잘린다. 그라디언트라 시각적 손상은 없지만 **각도가
  종횡비만큼 미세하게 달라진다.** 64.04°를 픽셀 단위로 보장하지는 않는다

### ADR-3 — 로고는 PNG 3배수, 페이드아웃은 RN 내장 `Animated` (폐기)

> ⛔ **2026-09-08 폐기 — ADR-6으로 대체.** 로고 PNG 3배수와 `Animated` 페이드는 오버레이 전용이었다. 페이드는 `SplashScreen.setOptions({ fade: true })`가 대신한다.

**Context**

`O.0`의 로고(`12898:23226`, 176×153)는 엠블럼 위·워드마크 아래로 쌓인 단색 흰색 조합이다.
`apps/web/src/shared/ui/logo/`의 워드마크(`372×91`, `100×24`)와 **구성이 달라 재사용할 수 없고**
새로 받아야 한다. `apps/native`에는 SVG를 쓰는 곳도, 애니메이션을 쓰는 곳도 아직 없다.

**Decision**

- **로고** — Figma에서 PNG `@1x/@2x/@3x`(176×153 / 352×306 / 528×459)를 내보내 `assets/`에 두고
  `Image`로 렌더한다
- **페이드아웃** — React Native 내장 `Animated` + `useNativeDriver: true`.
  `react-native-reanimated`는 쓰지 않는다
- **컴포넌트 배치** — `apps/native/components/`와 `apps/native/hooks/`. Expo 관례를 따르되 파일명은
  프로젝트 전역 규칙대로 kebab-case

**Alternatives**

| 안                                                        | 거부 이유                                                                                                                                                                                    |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SVG + `react-native-svg` / `react-native-svg-transformer` | 런타임 의존성 2개와 metro transformer 설정이 늘어난다. native에서 벡터가 필요한 곳이 이 로고 하나뿐이라 비용이 이득을 넘는다. 다른 화면에서 벡터 수요가 생기면 그때 도입한다                 |
| `react-native-reanimated` (4.5.1 설치돼 있음)             | **`package.json`에만 있고 실제 사용처가 없다.** opacity 하나는 내장 `Animated`가 native driver로 UI 스레드에서 처리한다. 첫 사용처를 단순 페이드로 만들면 이후 워크릿 규약까지 따라오게 된다 |
| `apps/native`에도 FSD 레이어 적용                         | FSD 훅(`fsd-layer-check.mjs`)과 steiger는 **`apps/web/src/`만** 본다. native에 레이어를 흉내 내면 도구가 지키지 않는 규칙이 하나 더 생긴다                                                   |

**Consequences**

- ✅ 새 런타임 의존성이 `expo-linear-gradient` 하나로 끝난다
- ✅ `components/`·`hooks/` 배치가 native의 첫 사례로 남아 다음 `NAT-` 작업이 참조할 기준이 된다
- ⚠️ **PNG 3장을 관리해야 한다.** 시안의 로고가 바뀌면 다시 내보내야 하고, 배수 누락은 저해상도로
  조용히 드러난다
- ⚠️ 로고가 래스터라 176×153 외의 크기로 쓰면 흐려진다. 이 작업 범위에서는 고정 크기 한 곳뿐이다

### ADR-4 — 최소 노출 1000ms · 최대 대기 10초 (폐기)

> ⛔ **2026-09-08 폐기 — ADR-6으로 대체.** 최소 노출 1000ms는 폐기. 최대 대기 10초만 `hideAsync()` 상한으로 성격을 바꿔 `app/index.tsx`에 남았다.

**Context**

준비 완료(`onLoadEnd`)가 언제 올지 모른다. 즉시 오면 로고가 깜빡이고, 영원히 안 오면 사용자가
스플래시에 갇힌다. 두 방향의 하한과 상한이 모두 필요하다.

**Decision**

`hooks/use-splash-gate.ts`에 상수로 둔다.

- `MIN_VISIBLE_MS = 1000` — 현재 `_layout.tsx`의 `SplashScreen.setOptions({ duration: 1000 })`과
  같은 값이라 정적 구간과 리듬이 맞는다
- `MAX_WAIT_MS = 10000` — 준비 완료가 없어도 10초에 오버레이를 내린다

두 값 모두 `constants-convention.md`의 "기획이 바꿀 정책값"에 해당해 상수로 뽑는다.

**Alternatives**

| 안                             | 거부 이유                                                                                                                  |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 최소 600ms / 최대 8초          | 8초 시점에 웹뷰가 아직 준비되지 않으면 그때부터 흰 화면이 드러난다. 느린 네트워크에서 이 작업이 없애려던 상태로 되돌아간다 |
| 최소 1500ms / 최대 15초        | 빠른 네트워크에서도 항상 1.5초를 기다려 앱이 느리게 느껴진다. 15초는 사용자가 이미 앱을 껐을 시간이다                      |
| 상한 없이 준비 완료만 기다린다 | 서버 장애나 오프라인에서 영구 감금된다. 확정 전제 4와 충돌한다                                                             |

**Consequences**

- ✅ 빠른 로딩에서는 1초, 느린 로딩에서는 실제 소요 시간만큼 노출돼 체감이 자연스럽다
- ⚠️ **최대 대기로 내려간 뒤 무엇이 보이는지는 이 작업이 책임지지 않는다.** 오버레이가 걷히고
  미완성 WebView가 드러난다. 오류·재시도 화면은 Out of Scope이고 별도 `NAT-` 작업이다
- ⚠️ 두 값 다 실기 측정이 아니라 판단으로 정했다. 실기에서 체감이 어긋나면 상수 하나만 바꾼다
- ⚠️ 두 상수의 기준 시각은 **`use-splash-gate`가 마운트된 시점**이지 앱 프로세스 시작 시점이 아니다.
  그 앞에 정적 스플래시와 JS 번들 로드 구간이 따로 있다. AC의 측정 기준도 여기에 맞춘다

### ADR-5 — 로드 실패는 준비 완료로 치지 않는다 (폐기)

> ⛔ **2026-09-08 폐기 — ADR-6으로 대체.** 실패·성공 구분이 오버레이 유지 시간을 정하는 구조 자체가 사라졌다. 현재는 `onError`에서 곧바로 스플래시를 내린다.

**Context**

확정 전제 3은 준비 완료 신호를 WebView의 `onLoadEnd`로 정했다. 그런데
**`react-native-webview`의 `onLoadEnd`는 로드에 실패해도 발생한다.** 성공과 실패를 구분하지
않으면 오프라인·서버 다운 상황에서 실패 시점에 곧바로 `markReady()`가 불려, 최소 노출 1초만 채우고
오버레이가 내려간다. 오류 화면은 Out of Scope이므로 그 뒤에 **깨진 WebView가 그대로 드러난다.**

이 경우 `MAX_WAIT_MS`는 `onLoadEnd`가 아예 오지 않는 무한 로딩만 담당하게 되어, 확정 전제 4
(「최대 대기 시간 경과 시 오버레이를 내린다」)가 실패 상황에서 사실상 작동하지 않는다.

**Decision**

`onError`와 `onHttpError`가 발생한 로드는 준비 완료로 치지 않는다. 실패해도 오버레이는 최대 대기
시간(`MAX_WAIT_MS`)까지 유지된 뒤 내려간다.

| WebView 콜백  | `use-splash-gate`의 처리  |
| ------------- | ------------------------- |
| `onLoadEnd`   | `markReady()` 호출        |
| `onError`     | 무시 — 준비 완료가 아니다 |
| `onHttpError` | 무시 — 준비 완료가 아니다 |

**Alternatives**

| 안                                                  | 거부 이유                                                                                                                                                                                                                                                     |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `onLoadEnd`를 성공·실패 구분 없이 그대로 쓴다       | 실패를 빨리 알린다는 장점이 있지만, **오류 화면이 없는 지금은 "빨리 알리는 것"이 깨진 WebView를 1초 만에 보여주는 일이다.** 흰 화면을 없앤다는 이 작업의 목적과 정면으로 어긋난다. `MAX_WAIT_MS`도 무한 로딩 전용으로 축소돼 확정 전제 4의 의미가 남지 않는다 |
| 실패 전용 상한을 따로 둔다 (예: `FAIL_WAIT_MS` 3초) | 감지된 실패와 무응답을 구분해 각각 다른 대기를 주는 것이 이론상 더 정확하다. 그러나 **어느 쪽이든 사용자가 보게 되는 다음 화면은 똑같이 깨진 WebView다.** 상한을 나눠 얻는 이득이 없는데 타이밍 상수가 3개로 늘고 훅의 상태 분기가 하나 더 생긴다             |
| 실패 시 재시도 후 판정한다                          | `reload()` 1회 재시도는 실질적 개선이지만 오류·재시도 화면과 함께 설계해야 의미가 있다. Out of Scope인 별도 `NAT-` 작업의 영역이다                                                                                                                            |

**Consequences**

- ✅ 확정 전제 4가 실제로 작동한다. `MAX_WAIT_MS`가 무응답과 실패를 모두 담당한다
- ✅ 실패 시에도 브랜드 화면이 유지돼, 오류 화면이 생기기 전까지 깨진 WebView 노출이 10초 늦춰진다
- ⚠️ **오프라인 사용자는 브랜드 화면을 10초 본 뒤에야 상황을 알게 된다.** 이 작업 범위에서는
  의도된 트레이드오프이고, 오류·재시도 화면이 생기면 그 작업에서 이 대기를 다시 짧게 조정한다
- ⚠️ `onHttpError`는 하위 리소스가 아니라 메인 문서의 HTTP 오류에서만 발생한다. 웹이 200을 주고
  화면만 비어 있는 경우는 여전히 준비 완료로 판정된다. 그 구간은 이 작업이 책임지지 않는다

### ADR-6 — 정적 스플래시 하나로 끝낸다 (JS 오버레이 폐기)

**Context**

ADR-1은 정적 스플래시 + JS 오버레이 2단 구성을 골랐고, 그 위에 ADR-3(로고 PNG·`Animated`
페이드), ADR-4(최소 노출·최대 대기), ADR-5(실패 판정)가 쌓였다. 구현 단계에서 사용자가
[expo-splash-screen 문서](https://docs.expo.dev/versions/latest/sdk/splash-screen/) 기준으로
다시 만들어 빌드와 실행을 확인했다. development build 첫 실행에서 흰 화면이 관찰됐고
reload에서는 정상 동작했다. **흰 화면 원인은 미확정이며, release 빌드 실기 설치 후 콜드 스타트를
확인하기 전까지 흰 화면 제거 완료로 판정하지 않는다.**

**Decision**

정적 스플래시 하나만 쓴다. JS가 그리는 스플래시 화면을 만들지 않는다.

| 층                   | 담당                                                                      |
| -------------------- | ------------------------------------------------------------------------- |
| `app/_layout.tsx`    | `preventAutoHideAsync()` + `setOptions({ duration: 1000, fade: true })`   |
| `app/index.tsx`      | `hideAsync()` 소유 — `onLoadEnd` · `onError` · 10초 상한 타이머           |
| `app.json` (iOS)     | `splash-gradient.png` 전체화면 `cover` (ADR-2 유지)                       |
| `app.json` (Android) | 배경 `#8100B3` + 아이콘 슬롯 `splash-logo-square.png` (`imageWidth: 150`) |

폐기되는 결정: **ADR-1**(오버레이 소유 구조) · **ADR-3**(로고 PNG 3배수·`Animated` 페이드) ·
**ADR-4**(최소 노출 1000ms) · **ADR-5**(실패는 준비 완료가 아님). 최대 대기 10초는 성격이 바뀐 채
남았다 — 오버레이 해제 상한이 아니라 **`hideAsync()` 상한**이다.

**Consequences**

- ✅ 파일 4개(`hooks/`·`components/`·로고 PNG 3장·`expo-linear-gradient`)와 타이밍 상태 기계가
  통째로 사라졌다. `apps/native`에 남는 것은 `app/` 두 파일과 `app.json`뿐이다
- ✅ 정적 스플래시에서 JS 오버레이로 넘기는 단계가 없어졌다. 스플래시에서 WebView로 넘어갈 때
  흰 화면이 없는지는 release 빌드에서 별도로 확인한다
- ⚠️ **로고 위치를 safe area 기준으로 제어할 수 없다.** ADR-1이 오버레이를 고른 이유가 이것이었다.
  iOS는 `scaleAspectFill`이라 기기 종횡비마다 밀리고, Android는 시스템 아이콘 슬롯이 위치를 정한다
- ⚠️ **현재 iOS 스플래시에는 로고가 아예 없다.** `splash-gradient.png`가 그라디언트만 담고 있다.
  `O.0` 재현을 요구하려면 이미지에 로고를 굽거나 별도 수단이 필요하다 (미해결)
- ⚠️ 최소 노출 하한이 없어 웹이 캐시에서 즉시 뜨면 스플래시가 짧게 스쳐 지나간다. 실기 체감에서
  문제가 되면 그때 하한을 다시 넣는다
- ⚠️ 로드 실패(`onError`)에서 곧바로 스플래시를 내린다. ADR-5가 막으려던 "깨진 WebView 즉시 노출"이
  다시 가능해졌다. 오류 화면 작업(별도 `NAT-`)이 이 구간을 가져간다
